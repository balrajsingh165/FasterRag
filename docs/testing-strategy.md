# testing-strategy.md — Testing Pyramid, Eval Harness, CI Gates

Doctrine: **a claim without a measurement is a bug** ([reliability.md](reliability.md)). Every capability in [differentiators.md](differentiators.md) names its acceptance test here or in the FMEA ([failure-modes.md](failure-modes.md)); every performance claim traces to the [benchmark ledger](benchmarks.md).

## 1. Testing pyramid (all layers required)

> **Build status (2026-08-09 claims audit, TASK-0238; mutation layer revised 2026-11-04; load harness 2026-11-07; load and soak suites 2026-11-11).** "Required" is the target, not a report. Layers **1.1–1.6, 1.9 and 1.10 are built**; 1.1–1.6 and 1.9 run in CI on every push or PR and **1.10 runs nightly** (§1.10). Layers **1.7 (load) and 1.8 (soak) now both carry tests** — `pytest -m load` and `pytest -m soak` each collect, and neither runs in CI. What each one does and does not prove is in its own section, and the distinction that governs both is **harness versus measurement**: the Locust generator of §1.7 is a benchmark that grades nothing and has never been pointed at fasterRag, while the marked suites assert hardware-independent behaviour (boundedness, conservation, typed refusal, absence of trend) and assert **no time at all**, because TASK-0350 measured this project's hosted runner at 2.07x variance on an identical commit. The **24 h run itself has never been performed** — the shipped soak harness was proven on a short run and the long one still needs the reference hardware TASK-0084 waits on, which is the part of TASK-0243 that stays open. **No load or soak measurement exists, so the benchmark ledger holds no entry from either and no row of [slo.md](slo.md) has been baselined.**

### 1.1 Unit tests

- Fast, isolated, no network/containers; mirror the `src/` layout under `tests/unit/`.
- **Coverage gate ≥ 85% on `core/`, `adapters/`, `workers/`** — CI fails below the gate.

### 1.2 Property-based tests (Hypothesis) — every chunker

Invariants asserted for `fixed`, `recursive`, `semantic`, `layout`, `late` on arbitrary generated documents:

1. Concatenating chunks (minus configured overlap) reconstructs the source text.
2. No empty chunks.
3. Character offsets are monotonic and in-bounds.
4. Configured overlap is respected.
5. No chunk exceeds `chunk_size` beyond tokenizer-boundary tolerance.

### 1.3 Golden-file parser tests

Messy PDFs, complex tables, and scanned/OCR documents parsed → structured output snapshot-compared against committed golden files (reading order, table cells, headings, metadata). Any diff is a reviewed change, never silent.

### 1.4 Integration tests (testcontainers)

- A real Qdrant instance exercised in **Docker-managed mode** and **remote host:port mode** (both 6333 and 6334 paths, `prefer_grpc` both ways, API-key auth on/off).
- Ingest → query round-trips over small corpora; journal resume; DLQ routing.
- Marked `-m integration`; run in CI on every PR.

### 1.5 Adapter contract suite

**One shared test suite that every `VectorDBAdapter` implementation must pass** (`create_collection`, `upsert`, `search`, `update`, `delete`, `health`, filter push-down, batch semantics, idempotent upserts). Three adapters currently pass it against a running store — **Qdrant, pgvector and Chroma** — which is what turns "any vector DB" from an assertion into evidence across three different storage paradigms; **Milvus and Weaviate subclass the suite and every case in it skips**, because the machine it was built on has no server and no Docker daemon, so for those two the suite is written rather than passed. It is not yet a promise tested across all six backends named in [scope.md](scope.md): one (Pinecone) is unbuilt and two are untested (TASK-0049, TASK-0243). Third-party adapters registered via entry points run the same suite ([python-api.md](python-api.md)). Embedding and LLM adapters have equivalent (smaller) contract suites.

### 1.6 Retrieval eval harness

- Metrics: **recall@k, MRR, nDCG** (retrieval) and **faithfulness** (generation grounding).
- Dataset fixtures committed under `tests/eval/datasets/`; golden Q&A sets generatable from a corpus (shared machinery with Autopilot, D6).
- Runs as `pytest -m eval`, via `fasterrag benchmark --suite eval`, and in CI as the `eval-gate` job.
- **Regression gate (D7)**: blocks every change whose recall@k drops > `eval.recall_tolerance` or nDCG drops > `eval.ndcg_tolerance`, measured against the committed baseline for a dataset. Implemented in `services/regression.py`; wired into CI on 2026-11-02 (TASK-0244) as the `eval-gate` job — see §2 gate 6 for exactly what that job measures, what it pins, and what it does not cover.

**The verdict is three-valued**, in the same vocabulary `scripts/compare_nightly.py` uses for the nightly benchmark: `within-tolerance`, `regressed`, `not-comparable`. A gate that reported green because it could not compare anything would be the vacuity defect this repository treats as a bug, so `not-comparable` is its own outcome and fails CI exactly as `regressed` does. Only the reason, and therefore the fix, differs.

**Comparability is an enumerated fingerprint, not the lockfile hash.** One hash was answering two questions. `index.lock` asks *"has the index drifted from the config that built it?"*, where any difference counts because the index really was built under the old config — `core/identity.retrieval_config_hash` still answers that, unchanged and deliberately broad. A baseline asks *"is this result comparable to the recorded one?"*, where only settings that change what retrieval returns count. Under the broad hash, adding a knob whose default preserved behaviour retired every recorded baseline, which is how `chunking.token_counter`, `chars_per_token`, `semantic_percentile`, `retrieval.bm25_k1` and `bm25_b` — plus the identity-version-3 change to the digest function itself — retired the 2026-08-02 handbook baseline.

`services/regression.py` therefore records `COMPARABILITY_FIELDS` as **values rather than a digest**, so a refusal names the field that moved; a field a baseline does not mention is read as that field's current default, which is what lets a behaviour-preserving addition leave a baseline alive. The two errors are not symmetric — too broad retires good baselines, which is annoying and visible; too narrow silently compares runs that are not comparable, which is dangerous and invisible — so the enumeration errs broad, every deliberate omission is listed in `BEHAVIOUR_NEUTRAL_FIELDS`, and `tests/unit/services/test_comparability.py` fails the build when a setting appears in neither list. `COMPARABILITY_VERSION` covers the one case the "absent means default" rule cannot: a new field whose default does *not* preserve behaviour retires every older baseline when the version is bumped.

**Golden-set schema** — shared by the eval harness, the regression gate (D7), and Autopilot (D6), so the three can never diverge. JSONL, one record per line:

```json
{"id": "q_0001", "query": "What does the vendor agreement say about termination?",
 "relevant_chunk_ids": ["c_9f2", "c_a01"], "relevant_document_ids": ["d_112"],
 "answer_reference": "Either party may terminate with 30 days written notice.",
 "metadata": {"department": "legal"}, "source": "human", "created_at": "2026-07-29"}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `id` | str | ✅ | Stable query id, unique within the set. |
| `query` | str | ✅ | The question. |
| `relevant_chunk_ids` | list[str] | ✅ (may be empty for adversarial records) | Ground-truth chunks; basis for recall@k/MRR/nDCG. |
| `relevant_document_ids` | list[str] | — | Document-level ground truth (used when chunk ids churn across re-chunking). |
| `answer_reference` | str\|null | — | Reference answer; basis for faithfulness scoring. `null` + empty chunk ids = adversarial "unanswerable" record for D5 testing. |
| `metadata` | object | — | Filter context the query should run with. |
| `source` | str | ✅ | `human` \| `autopilot` (generated sets are marked; human-reviewed promotion flips the value). |
| `created_at` | str | ✅ | ISO date. |

Golden sets are versioned files; a set edit that changes scores is reviewed like code, and archives export them (`golden-set.jsonl`, [archive-format.md](archive-format.md)).

### 1.7 Load tests — **a benchmark that has never been run, plus a marked suite that asserts** (TASK-0243)

*Specified:* scripted scenarios (query-only, ingest-only, mixed) at stepped concurrency; publish p50/p95 **with the exact hardware spec** into the benchmark ledger. No load number is ever quoted without its hardware line.

*As built:* the harness lives in `tests/load/` and is driven by `python -m tests.load.run_load`. It is **tooling, not a result.** It has never been pointed at a fasterRag instance, there is no load number anywhere in this repository, and [benchmarks.md](benchmarks.md) holds no entry from it. The provable-claims policy is the reason it was committed before it could be run: *"'fastest' may only be claimed relative to a named baseline we measured ourselves, with the harness committed to this repo."* The harness is that precondition; the measurement waits on the isolated reference hardware TASK-0084 needs, because a load number taken on a shared developer workstation is noise that the methodology forbids citing ([performance.md](performance.md) §3 rule 5).

**Locust, not k6.** k6 is a single static binary and a faster generator per core, and it was still the wrong choice here. Its scripts are JavaScript, and a JavaScript runtime cannot reuse what this harness reuses — the committed golden-set loader, the machine fingerprint in `services/benchmark.py`, the Prometheus parsing the SLI derivation needs — so k6 would mean a second implementation of each, and a second implementation of a measurement rule is how two numbers that disagree get published. Locust is `pip install`-able from `tests/load/requirements.txt`, the same command this project already uses; CI and the reference rig need no out-of-band binary. A contributor without it gets a typed refusal naming the install command rather than `command not found`. The cost, stated rather than hidden: Locust's generator is Python and one process is GIL-bound, so at high request rates the generator saturates before the system does — an error in the direction that makes fasterRag look slow, which is why the operator procedure requires watching the generator's own CPU and scaling it with `--processes`, and why every report records the generator's hardware next to the system's. `locust==2.47.0` was installed and run on this project's own Windows / Python 3.14 development machine before being chosen — against a stand-in server, not against fasterRag — which is the check that disqualified mutmut in §1.10: a tool the maintainer cannot run locally produces reports nobody can reproduce.

| Scenario | Drives | Exists to show |
|---|---|---|
| `query` | `/v1/retrieve`, `/v1/query`, and streamed `/v1/query` | read-path latency with no writer contending |
| `ingest` | `POST /v1/ingest` plus polling each job to a terminal state | sustained write throughput, measured on completed work rather than on accepted requests |
| `mixed` | both, as separate user pools (read-weighted 4:1 by default) | the case the other two cannot show: query latency while the embedding pool and the index are busy |

**What it measures, matched to [slo.md](slo.md) §1 rather than invented.** Query availability, p95 retrieval latency excluding generation, p95 time-to-first-token, ingestion throughput, error rate, cache hit rate, and DLQ depth — all seven rows, each labelled with the row it comes from. Three carry bounds that are part of the measurement and are printed with it: the retrieval SLI is the sum of the non-`generate` keys of the response's `timings_ms`, and the shipped code emits `retrieve` and `assemble` only, so the embed/fuse/rerank split slo.md's definition names **cannot** be broken out; ingestion throughput is reported in docs/min only, because `fasterrag_ingest_throughput` carries `documents_per_second` and `chunks_per_second` and no token unit, so the tokens/sec half of that SLI is **not measurable** from the shipped metrics; and availability and cache hit rate are defined over rolling 30-day and 24-hour windows, so a run reports an input to the SLO and never the SLO itself.

**It cannot report a number it did not measure.** This is the T12 vacuity class, and a load generator is unusually good at it: pointed at a dead endpoint it produces zero requests, zero failures and a p95 of zero, which is internally consistent and reads as a fast system. The harness refuses instead, at five separate points. A preflight proves the target is reachable, ready, actually fasterRag (its `/metrics` must carry `fasterrag_requests_total`), and able to answer this scenario's exact requests with a usable `timings_ms` — and it runs twice, once in `run_load.py` and once inside Locust's own `test_start`, so `locust -f` directly cannot walk past it. A dataset with no queries, or an ingest scenario with no corpus, is refused before anything starts. An SLI's value is `float | None` and `None` renders as `not measured`; there is no path that turns an absent measurement into `0.0`, and the percentile helper returns `None` on an empty sample where Locust's own returns `0`. The audit then refuses a run with zero requests, a run missing an endpoint its scenario requires, a latency figure below the 1,000 samples [performance.md](performance.md) §3 rule 4 fixes, a p95 of zero over real requests, a failure ratio over the threshold, or a run the rate limiter shaped (over 5% `429`, which measures the limiter and not the system). Every refusal has its own non-zero exit code, so a caller reading nothing but `$?` still cannot mistake an empty run for a fast one.

**It never reports a pass.** Every SLO target in [slo.md](slo.md) is TBD-until-measured, so there is nothing to grade against; the verdict vocabulary is `valid-sample` or `invalid`. A ledger draft is emitted only for a run that was valid, ran the three warmed repetitions the methodology fixes, *and* was launched with `--isolated` — the operator's assertion that the machine under test carried no co-tenant load, which no program can detect from inside. Without all three the draft is replaced by an itemised refusal naming every missing condition. A run on a laptop therefore cannot accidentally become a benchmark entry.

The guards are unit-tested in the ordinary CI lane by `tests/load/test_load_harness.py`, with no load generator installed and no target running: an unreachable port, a live server that is not fasterRag, an empty dataset, an empty stats document, a zero p95, a short throughput window, and a ledger draft refusing itself. That is deliberate — the property those tests assert is what makes the eventual measurement trustworthy, so it is checked on every push rather than only on hardware nobody has yet.

**What has actually been run.** On 2026-11-07 the whole pipeline was exercised end to end against a throwaway HTTP stand-in that imitates the REST surface — not against fasterRag — purely to prove the tool works: the preflight chain, both user pools, SSE first-token timing, the metrics deltas, the percentile derivation, and four refusals (unreachable target exits 2, missing Locust exits 5, too few samples exits 3, and `locust -f` run by hand against a dead target still exits 2). **Every latency it printed was the stand-in's own invented sleep on a contended developer laptop. None of it is a measurement of anything, and none of it appears in any document.** That is the whole distinction this section turns on: the harness has been shown to run, and fasterRag has not been measured.

*Not built:* stepped concurrency is driven by the operator re-running at each step rather than by a load shape inside the harness; there is no `LoadTestShape`. Nothing here runs in CI (§2).

#### 1.7a The `load` marker — what a load test can honestly assert off a rig (2026-11-11)

**The Locust harness above is a benchmark, not a test**, and calling it one was the gap. It reports SLIs, refuses an invalid sample, and grades nothing — its verdict vocabulary is `valid-sample` or `invalid` by design. A benchmark cannot go red when the system misbehaves under concurrency, which is exactly what the FMEA rows citing "a load test" wanted from it. So the two halves are now separate and named separately: the benchmark keeps its place above and earns a [benchmarks.md](benchmarks.md) entry the day it runs on a rig, and `tests/load/test_saturation.py` carries the `load` marker and asserts.

**It asserts no time, and it never will.** TASK-0350 measured a hosted runner at **2.07x on an identical commit**, so an absolute latency bound is a flap with a date on it. What survives that variance is behaviour under saturation, and the suite asserts three such properties: **boundedness** (queue occupancy is set by `workers.queue_depth`, not by how much work is offered — FMEA row 10's built rung, checked both on `BoundedQueue` directly and through the real `IngestionService` over a corpus that overfills it, with the ceiling read from every depth transition rather than polled, since a poll that misses the peak turns a breach into a green run); **conservation** (every item offered is accepted or typed as refused, and none is dropped — a storm that silently loses work is indistinguishable from a fast one); and **typed refusal** (a concurrent request storm answers with no 5xx, and every 4xx is `application/problem+json` carrying a `code`).

**What it cannot reach, so that a green run is not over-read:** one interpreter with doubles at the vendor edges says nothing about cross-process contention, connection-pool exhaustion, or a real store under concurrent writers. Those need TASK-0084's hardware and the benchmark above pointed at it. It also does **not** prove FMEA row 10's `429 QUEUE_FULL` clause, because that clause describes an unbuilt mechanism rather than an untested one: `BoundedQueue.offer` — the only code that raises `QUEUE_FULL` — has **zero callers under `src/`**, since the pipeline uses `await put` and waits. Nothing runs in CI (§2).

### 1.8 Soak test — **harness built and proven short 2026-11-11; the 24 h run has never happened** (TASK-0243)

*Specified:* 24 h sustained ingest + query at moderate load; assert **no memory growth and no file-descriptor growth** (RSS and fd counts sampled and trend-tested), no queue leakage, no journal bloat.

*As built:* `tests/soak/` holds the harness and `pytest -m soak` runs it. It drives the real ingestion pipeline in a loop for `FASTERRAG_SOAK_SECONDS` (default 120), sampling RSS and the process's open-handle count every `FASTERRAG_SOAK_SAMPLE_INTERVAL_S`, and then **regresses on the series** rather than subtracting its endpoints. Nothing differs between the proving run and the 24 h run but that one variable, which is the point: the long run is a hardware booking, not a piece of engineering.

**Why a regression and not a before-and-after.** Two samples have no notion of noise, so an allocator holding a free list at the second reading is indistinguishable from a leak — and `tests/soak/test_trend.py` holds a case where exactly that subtraction reports a large rise in a sawtooth with no growth in it. The rule is **Theil–Sen** (median of pairwise slopes, so one garbage collection cannot set the trend) plus a **permutation test** against the same samples shuffled in time, which needs no assumption about a distribution that is not normal and no constant chosen by a human. A finding must then clear two bars — distinguishable from a reordering of itself **and** accounting for more than 10% of the process's own baseline RSS over the window observed. Handles carry a budget of zero, because a descriptor count does not scale with the machine.

**Growth is counted over the window observed, never over the documented one.** The first version multiplied the slope by 24 h; its own calibration test killed it, because a two-minute slope amplified 720-fold makes every series material and sends the whole nominal 5% false-positive rate straight to red. The 24 h figure is still printed, labelled an extrapolation.

**Every verdict prints what the run could not have seen.** `detectable` is the smallest growth that run had the power to call — the 95th percentile of the null slope distribution over the same window. A short run's is large, and printing it is the difference between "no leak" and "no leak this run could have found".

*Not built:* the 24 h run itself, which needs TASK-0084's isolated hardware — a soak on a shared developer workstation measures its neighbours. The harness also runs against doubles at the vendor edges (a discarding vector store, a hash embedder), deliberately, because a recording double makes RSS rise with the corpus by construction; the cost is that it cannot see a leak inside a vendor client, which is where the two most valuable ones live — an HTTP pool that never recycles, and the per-batch model reload of FMEA row 8. Queue leakage and journal bloat are not yet separately asserted. Nothing here runs in CI (§2).

**What has actually been run, and what it found.** Two 120 s runs on 2026-11-11, on the development workstation while nine other agent sessions were compiling and testing this same tree — the opposite of the conditions a soak needs, which is why what follows is **not citable and appears in no ledger**. Both passed, and the interesting half is *how*: the handle count never moved in either (slope exactly 0, p = 1.0, 304 handles throughout), while RSS rose both times with p = 0.001 — about +21 kB/s in the first and +37 kB/s in the second, a trend each run could plainly see, since the detection floors were ~85 kB and ~246 kB against rises of 2.5 MB and 4.4 MB. They passed because those rises sit well inside a budget of a tenth of the process's ~630 MB baseline, not because nothing moved, and the figures differ by 1.8x between two runs of the same code on the same machine, which is the co-tenant variance the methodology warns about rather than a measurement of fasterRag. **Whether that rise is warm-up that flattens or a leak that continues, a two-minute run cannot say** — and deliberately no warm-up window is discarded, because a knob that drops the first samples is a knob that hides a leak. Settling it is what the 24 h run on TASK-0084's hardware is for.

**The detector's own tests run in the ordinary lane** (`tests/soak/test_trend.py`, unmarked): a seeded 1 MB/s leak is detected, a one-descriptor-per-cycle handle climb is detected, flat noise and a sawtooth are not, the false-positive rate over 40 flat series stays at or under a tenth, and a series shorter than 12 samples is refused rather than judged. A leak detector that cannot be shown to fail is green forever, and nothing about it would be checked if it only ever ran on hardware nobody has.

### 1.9 Chaos suite (scripted, repeatable — D12)

| Injected fault | Asserted behavior |
|---|---|
| Kill an embedding worker mid-batch | Job resumes from the queue; **no duplicate vectors** (idempotent upserts). |
| Stop the Qdrant container | *Specified:* circuit opens; degraded `cache_only` responses with `degraded: true`; automatic recovery when it returns. **As built:** the breaker opens and recovery is automatic, but the `cache_only` rung does not exist (TASK-0159), so the suite asserts a retryable `RETRIEVAL_FAILED` instead — see [failure-modes.md](failure-modes.md) §observed behavior. |
| Feed a corrupt/malformed document | Routed to DLQ with reason code; pipeline continues. |
| Slow LLM (latency injection) | `reliability.timeouts.llm_ms` triggers; degradation ladder serves `extractive` mode. |
| Disk-full during ingest | Clean halt with typed error; resumable from the journal checkpoint after space is freed. |
| Configuration mutated under a built index | Drift is reported and the moved field is named; a legal edit the index does not depend on is **not** reported. |
| Network partition to a provider (vector DB and LLM legs, plus a name that cannot resolve) | The call ends on *our* configured timeout rather than hanging; the failure is typed and retryable, renders as a problem document with a trace id and never a generic 500; the breaker opens and admits one probe after its reset timeout. (Closing on a healed peer is asserted in `tests/unit/core/test_breaker.py`, not here — no chaos case heals the partition and drives a real call through it.) |
| Reranker that will not load, will not fit in memory, or dies mid-query | The D4 ladder absorbs it: the query answers in `degraded` mode on the first-stage ordering instead of failing, and keeps doing so for every later query rather than only the first. The fault surfaces on a query and never at boot, because the model is loaded lazily on first use. Two bounds are pinned as limits rather than promises: a missing `rerank` extra degrades silently the same way, and a working reranker over the same wiring must still report `full`. |

Every scenario is a script in the repo; observed behavior is recorded in [failure-modes.md](failure-modes.md). Reliability anyone can re-run.

Every row injects its fault at the closest honest code seam, so the whole table runs on any machine — the partition row included, which is why it uses a local socket that accepts the connection and then never writes, rather than a container or a firewall rule. The first five rows live in `tests/chaos/test_chaos.py`; the last three are large enough to own their modules, `tests/chaos/test_config_mutation.py`, `tests/chaos/test_network_partition.py` and `tests/chaos/test_reranker_down.py` (8 cases, 2026-11-04, TASK-0289). `tests/chaos/test_reindex_under_load.py` adds the reindex-under-continuous-query-load drill as a fifth module (8 cases, 2026-11-02; all three TASK-0241 ✅). The reranker module injects below the service's own `Reranker` Protocol, which is what distinguishes it from the unit suite's scripted double: one case drives the real `CrossEncoderReranker` against the real `sentence_transformers` with a repository id the hub library rejects locally — no network, no weights, no GPU, skipped when the optional `rerank` extra is absent — and the rest patch `load_cross_encoder`, the single seam between this package and the model stack, with the shape a real failure arrives in. The two environmental rows — stop-Qdrant and disk-full — additionally have **real-fault variants** in `tests/chaos/test_real_faults.py`, marked `integration` because they need a Docker daemon and skip cleanly without one: a throwaway Qdrant really stopped with `docker stop`, and the real journal writing onto a tmpfs with a hard size limit. The seam-level cases prove how fasterRag responds to those conditions; the variants prove that what the operating system actually reports is what it responds to.

The config-mutation row is worded narrowly on purpose. Its mutation set is derived from the live schema rather than listed by hand, and it is exhaustive over **single-field** edits of the subset the lock hashes; multi-field edits are not enumerated, and drift arriving by a route other than configuration is sampled with one scenario each. It does not establish "zero false negatives" in general, and [differentiators.md](differentiators.md) D1 states the same bound.

One honesty note about the suite's own audit: `test_chaos.py` carries a self-audit case that
enumerates the five scenarios defined in that module only. It used to assert that the suite
was complete against this table, and that claim is withdrawn in the case's own docstring,
because the dict it checks is hand-written. It therefore does not see the four scenarios
that own their modules, so it would not notice if one of them were deleted. The scenarios
run and pass; it is the audit that is behind, and extending it is an open task.

### 1.10 Mutation testing — **built 2026-11-04**, runs nightly

`scripts/mutation_run.py`, driven by the `mutation` job in `.github/workflows/nightly.yml`. It automates what this repository was already doing by hand: TASK-0193, TASK-0208, TASK-0211, TASK-0229 and TASK-0232 each record a maintainer breaking a line and confirming exactly one test went red. A habit protects whatever somebody remembered to break.

**Neither mutmut nor cosmic-ray, and why.** Both were installed and tried here against Python 3.14.7 on Windows, the machine this repository is developed on.

- `mutmut` 3.8.0 installs and then refuses to run: it prints *"To run mutmut on Windows, please use the WSL"* and exits without mutating anything. A nightly survivor that the maintainer cannot reproduce locally is a report, not a gate.
- `cosmic-ray` 8.7.0 installs cleanly on 3.14, but it parses with `parso` 0.8.7, which raises a **false `SyntaxError` on valid code in this tree** — the parenthesized `with` statement in `src/fasterrag/services/archive.py` (lines 211–214), legal since Python 3.10 and accepted by `ast.parse`. It also takes one global `test-command` per session, so running only the tests that cover a module means one session, one SQLite database and one report per target, re-stitched by a script of ours anyway.

The runner is therefore purpose-built on `ast`, which by construction parses exactly what the interpreter parses, following the same pattern as `scripts/trim_docstrings.py` and its before/after structure comparison. It is stdlib-only and adds no dependency.

**Target set, explicit and configurable.** Mutating 27k lines produces a run that never finishes and a report nobody reads. `DEFAULT_TARGETS` names six, each paired with the tests that are supposed to defend it: `core/retrieval`, `core/chunking`, `core/identity.py`, `core/breaker.py`, `services/regression.py`, `core/rate_limit.py`. `--only` narrows it; `--targets-file` replaces it.

**Operators.** Comparison swaps (including `is`/`is not` and `in`/`not in`), arithmetic swaps, `and`/`or`, `not`-removal, numeric-literal perturbation and boolean-literal flips. String literals are deliberately **not** mutated: they are overwhelmingly error codes and messages here, and mutating them manufactures survivors no behavioural test should be asked to kill. Every candidate passes three guards before it counts — it must still parse, it must differ from the original under `ast.dump`, and it must occupy the same number of lines, so a reported line number is the line a reader will find.

**Output is a survivor list, not a score.** A surviving mutant is a claim that some line can be changed without any test noticing, so every survivor is printed with file, line, column, operator and the exact `before -> after` substitution, into the run's `$GITHUB_STEP_SUMMARY` as well as a JSON artifact. A score on its own is noise.

**Fail-or-report, deliberately asymmetric.** A **survivor is a warning**, not a job failure: the set includes equivalent mutants (a perturbed constant nothing can observe) and timing-dependent ones, and a nightly that goes red on those is switched off within a week. The answer to "a report nobody reads is how the FMEA table rotted" is to put the survivors on the run page rather than to build a brittle gate. A run that **could not be performed fails the job** (exit code 2): a target whose own suite was already red kills every mutant for free and would otherwise report a perfect score — the vacuity defect the trap registry calls T12.

**A survivor ratchet makes the job able to fail, which until 2026-11-11 it was not** (TASK-0382). Warning on survivors and nothing else left a job that reported eleven undefended lines and concluded success, which is the class of defect that let the nightly benchmark measure nothing for 83 days (TASK-0314). `python scripts/mutation_run.py --check-ratchet artifacts/mutation.json` runs as a step of its own after the campaign and holds each target to the `CEILING` constant in that script: **more survivors than the ceiling, or any kill the clock or a signal rather than a test produced, exits 1 and fails the job.** The design, argued in the script's module docstring: the ceiling is **per-target**, because a total lets one target rot behind another's improvement; it records **counts rather than mutant identities**, because the seeded sample is redrawn whenever a target file's mutant count changes and an identity ratchet would fire on every refactor; and it carries **no slack**, because slack is a raise granted in advance. It was measured, not chosen — nightly runs 42419161973, 42468563494, 42603353729 and 42800995556 (2026-11-07 to 11-10, three commits, all at `--budget 10 --seed 0`) report the identical split `retrieval 1, chunking 5, identity 2, breaker 1, regression 0, rate-limit 2` of 60 executed, with zero timeouts. The ±1 noise the ledger records (TASK-0330/0331) is the archive suite's `tracemalloc` assertions, which defend no module in `DEFAULT_TARGETS`.

**The per-mutant memory cap is wired and calibrated** (TASK-0362). The nightly runs with `--memory-mb 2048`, which TASK-0321 shipped and left unused. The number is measured, and the measurement matters because `RLIMIT_AS` bounds **address space** while the artifact's `peak_child_rss_bytes` reports **resident** size: for these six targets the two differ by about a factor of three, so a cap read off the 337 MiB the nightly last reported would have turned every baseline into `not-run`. Measured 2026-11-11 under WSL Ubuntu-24.04 (Python 3.12.3) by running each target's real suite under `ulimit -v`, the same limit the runner sets: **all six pass at 896 MiB and above, all six fail below it**, and between 640 and 768 MiB the interpreter does not fail cleanly at all — a corrupted `ast` import, a `SIGABRT`, a `SIGINT`. 2048 MiB is 2.3× that knee and an upper bound rather than a reading from the hosted runner, which has four cores to that machine's sixteen and so reserves fewer glibc arenas. **The one pathology a cap cannot convert is now reported rather than absorbed**: a cgroup OOM kill arrives as `SIGKILL` from outside the process, POSIX reports it as a negative return code, and a negative return code is not zero — so until 2026-11-11 it was counted as a mutant some test caught. A signalled child is still counted as a kill, for the `executed == killed + survived` reason, and is named by signal exactly as a timeout is. The calibration produced one unprompted: at 768 MiB the `rate-limit` child aborted with `SIGABRT` instead of raising `MemoryError`. **Per-target peaks** (TASK-0363) now sit beside the run-level one, because the operator's question while calibrating is *which* target approached the cap; `getrusage(RUSAGE_CHILDREN)` is a high-water mark nothing resets, so the series only rises and the reports name the target where it rose rather than implying six independent readings.

**The ratchet lowers itself and never raises itself.** A run below its ceiling prints the exact replacement block to paste into `scripts/mutation_run.py`; a run above it prints the diagnosis and no block, because a tool that hands back a loosened ceiling is a rubber stamp. Raising a number is a hand edit in a reviewed diff, and a test asserts no entry stands above the four nights that measured it. The gate is vacuity-guarded by reusing the runner's own `decide()` rather than re-deriving it: a missing, empty or unparseable artifact, a partial one, a ceiling target that did not run, a target with no ceiling, a stored verdict that disagrees with its own counts, and a run that executed nothing each exit 2 instead of reporting a held ratchet.

**Nothing under `src/` is ever written.** The tree is copied once per run and the copy is mutated; pytest is pointed at the copy with `-o pythonpath=` (emptying the ini setting that would otherwise put the real `src` first) plus `PYTHONPATH`.

**Two bounds, stated rather than implied.** A target whose named tests do not import its source reports *every* mutant as surviving — loud, but it is a mis-wired target rather than an untested module, and only a reader can tell the two apart. And a survivor is a statement about the test suite, never by itself proof of a defect.

**A third bound, found by a defect the layer could never have caught** (TASK-0329, 2026-11-11). A mutant is an *edit to a line that exists*. The archive writer's security defect was an **omission**: `checksums.sha256` listed four members and the manifest was not one of them, so the member the vector-copy guard reads went unverified and a rewritten `embedding.model` passed every check. No operator was flipped and no branch was inverted, so no mutant in the catalogue corresponds to the bug, and a target at 100% kill rate would have reported nothing. Mutation testing grades the tests that exist against the code that exists; a missing entry in a list, a member nobody enumerates, and a guard that was never written are outside the method by construction. Finding those is what reading the writer against its specification is for — which is how this one was found.

**What has actually been measured, exactly.** The catalogue generates **420 mutants over the six targets' 18 files**. On 2026-11-04, on a Windows dev machine shared with other work, **four of the six targets were run exhaustively**: `identity` (20 mutants, 7 killed, 13 survived), `breaker` (34, 20 killed, 14 survived), `regression` (40, 26 killed, 14 survived) and `rate-limit` (40, 18 killed, 22 survived) — **134 mutants, 71 killed, 63 survived, 183 s wall clock**. The remaining two targets, `retrieval` (52 mutants) and `chunking` (234), **have not been measured**: their suites are the slow ones and the unbounded run over all six was still executing when it was stopped. No mutation score is claimed for them, and none is claimed for the tree.

One result is **not reproducible between two runs of the same target on the same code**: `breaker` reported 13 survivors in one run and 14 in another, differing by `core/breaker.py:43` (`CLOSED = 0` → `1`). That is unexplained, and it is precisely the reason a survivor count is a warning here rather than a gate.

### 1.11 Live provider checks (credential-gated)

`tests/eval/test_live_providers.py`, under the `eval` marker. Every other provider test substitutes a fake client, which proves the adapter issues the request it intends to and proves nothing about whether the vendor accepts it. [integrations.md](integrations.md) and the README advertise OpenAI, Anthropic, Cohere, Ollama and any OpenAI-compatible endpoint; before this layer existed, exactly one of those — the OpenAI generator — had ever been exercised against the real API, by hand, once.

Each advertised provider gets the smallest call that can keep the promise: one short generation, or one short embedding, asserting a well-formed typed `Completion`/`EmbeddingResult` and the token accounting the adapter claims to populate. One full run with every credential present costs **eight requests** of a few dozen tokens each — five generations (OpenAI, Anthropic, Cohere, Ollama, `openai_compatible`) and three embeddings (OpenAI, Cohere, Ollama); the two Ollama checks go to a local server and cost nothing. The HuggingFace embedder is local and is covered against real weights by `tests/eval/test_real_models.py` instead.

**What this layer establishes, and what it does not.**

- A provider counts as verified **only** when its own check ran and recorded evidence of a response. Verification is derived from the recorded responses, not from a counter kept beside them, so no provider that was never called can be counted.
- **A green `pytest -m eval` run with no credentials present proves nothing about any provider.** Every check skips, and a skip is not a pass. This is the misreading the trap registry calls T12, and it is the shape of the failure that hit the Redis suite on 2026-10-26 — a probe weaker than the assertion it gated, reported as green.
- Two things make that misreading structurally hard. Each provider has its own test, so pytest's own `SKIPPED` line is the record and there is no aggregate that could launder it; and the run's summary test is green **only** when every provider was reached, skipping with the full per-provider table otherwise. **CI runs `-rs` as of 2026-11-08** (TASK-0328), so that record is printed on the run page rather than available only to somebody who re-runs the suite by hand; §3.1 has the counts.
- A missing credential never fails the suite. The maintainer can run with one key, with all of them, or with none. A credential that is *present but rejected* does fail — that is a real finding, not an absence.
- **The gate is an explicit opt-in, not a credential (TASK-0341, 2026-11-09).** Every probe skips unless `FASTERRAG_LIVE_PROVIDER_TESTS` is set to `1`, `true`, `yes` or `on`, *and* the provider's own gate below is satisfied; the skip reason names the variable and the exact command. The environment is not a statement of intent — a developer with `OPENAI_API_KEY` exported for unrelated work, or any process that loaded a `.env` on the way past, could previously spend money by typing a test command, which is what happened. The marker filter in `pyproject.toml` keeps these out of a bare `pytest`; this gate is what stands behind that filter when someone runs `pytest -m eval` on a machine that has keys. A full billed run is therefore `FASTERRAG_LIVE_PROVIDER_TESTS=1 pytest -m eval -rs`.
- Gating: hosted providers gate on their key variable (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `COHERE_API_KEY`); Ollama has no credential, so it gates on `OLLAMA_HOST` naming a running server. Gating Ollama on nothing would mean a connection attempt, and a failure rather than a skip, on every machine without it. `openai_compatible` gates on three variables — `FASTERRAG_LIVE_OPENAI_COMPATIBLE_URL`, `..._KEY` and `FASTERRAG_LIVE_MODEL_OPENAI_COMPATIBLE_LLM` — because the schema requires both a base URL and a key, and a gateway names its own models, so there is no default model id to guess; it skips rather than guessing one. A missing provider SDK skips the same way, naming the extra to install. Every skip reason names both the provider and the variable, so a skipped run is legible rather than invisible. **Status (2026-10-29): none of the eight live bodies has ever been executed against a real provider** — no credential has been available to any run, so a green `pytest -m eval` proves only that the gating held. The gating logic itself is pinned by `tests/eval/test_live_provider_gating.py`, which deliberately carries no `eval` marker so it runs in the `not integration and not eval` job — the job that cannot skip (T12).
- Model ids go stale. Each check's model can be overridden with `FASTERRAG_LIVE_MODEL_<PROVIDER>_<LLM|EMBEDDINGS>` so a retired id is a configuration change, not a code change.

**`reports_token_usage` is a claim about the vendor, not about our code (TASK-0312, 2026-11-08).** Until this change the Cohere and Ollama embedding checks both carried `reports_token_usage=False` and asserted `total_tokens is None`, which pinned *absent accounting* as though it were the design: Cohere returns billed units in `meta.billed_units` that `CohereEmbedder` was discarding. Cohere's flag is now `True` and its billed units reach the cost path. Ollama's stays `False` for a genuine reason, and the flag can no longer be set to `False` without one — `LiveCheck` refuses to construct without a `usage_note`, which for Ollama records that the legacy `/api/embeddings` route the client's `embeddings()` call issues returns a bare `{"embedding": [...]}` with no `prompt_eval_count`. (`/api/embed` does return one; moving to it is a server-version change rather than an extraction fix, and is filed separately.)

Because a live probe only runs with a credential, the flags are additionally pinned against the adapters by `tests/unit/adapters/embeddings/test_usage.py` in the ordinary CI job: each adapter is driven with a response hand-built to the vendor's documented shape and asserted to report usage exactly when its flag says it does. Neither the `cohere` nor the `ollama` SDK is installed in this environment, so those fakes follow the published API references rather than the installed package's types — the live probes remain the only thing that can check a shape against the vendor, and they have still never run.

**On gate 3's scope.** The threshold is applied to `core/`, `adapters/`, and `workers/` specifically, not to the repository. **Per-test coverage contexts, and the trap inside the measuring instrument.** `--cov-context=test` labels each recorded line with the test that executed it, which is how a vacuity sweep answers "which tests actually entered this branch". Under coverage's default `sysmon` core on CPython 3.12+ that labelling is **silently incomplete**: `sys.monitoring` stops reporting a line once it has been seen, so only the *first* context to reach a line keeps credit for it, and when the first visitor is module import or a session fixture the credited context is the empty string and a query for test contexts returns **zero**. Coverage announces this only as a `no-sysmon-context` warning in a run that otherwise exits green. Two passes of the TASK-0335 sweep produced false "0 tests" results from exactly this before it was found (TASK-0348). Measured on this tree 2026-11-11, coverage 7.15.4 / CPython 3.14.7, over `tests/unit/core/chunking` with `--cov-context=test`: `core/chunking/layout.py:49` is entered by **22** tests, and the default core credits **1**. `[tool.coverage.run] core = "ctrace"` in `pyproject.toml` now pins a core that records every visit, and `tests/test_coverage_records_contexts.py` proves the pinned core labels both of two contexts entering one line, that the default core still does not, and that the pin is present at all. **`COVERAGE_CORE` in the environment overrides the pin**, so a run that sets it to `sysmon` is back in the trap — check for the warning. No committed tooling or CI step uses `--cov-context` as of 2026-11-11; it is an ad-hoc audit tool, which is precisely why the trap had nowhere to be caught.

**On gate 6's scope — what the `eval-gate` job establishes, and what it does not.** The job starts a Qdrant service container, ingests `tests/eval/datasets/handbook/corpus` with the real `BAAI/bge-small-en-v1.5` embedder, scores it with `fasterrag benchmark --suite eval`, and acts on the three-valued verdict: `within-tolerance` passes, `regressed` and `not-comparable` both fail, with the measured report printed either way. It does **not** read the exit code alone — code 5 cannot tell "recall fell" from "nothing was comparable", and those need different answers from a human.

Three settings are pinned rather than inherited, each of them a value `tests/eval/datasets/handbook/baseline.json` records field by field. `retrieval.rerank=false`, because the shipped default names a 2.2 GB cross-encoder and a push gate cannot download one per run — **so the gate covers retrieval and fusion and does not cover the reranker.** `retrieval.top_k=5`, because the baseline measured recall@5. `chunking.token_counter=estimate`, because `auto` uses the embedding model's tokenizer when it happens to be cached on the machine and silently estimates when it is not, which would make chunk boundaries depend on a runner's cache state. The gate therefore measures a pinned eval configuration and not the shipped defaults, and the `policies` dataset is not scored by it at all.

**Baseline provenance, stated exactly.** The recorded numbers are the 2026-08-02 measurement and have not been re-measured; no machine available to the 2026-11-02 change could run the harness end to end (no Docker daemon, so no Qdrant), and inventing numbers is not an option the provable-claims policy leaves open. What *was* recovered is the configuration behind them: the baseline carried only an opaque `retrieval_config_hash`, and a search over candidate configurations found the single one whose hash under that commit's digest function is the recorded `17c2897…` — `retrieval.top_k=5`, `retrieval.rerank=false`, otherwise that commit's defaults, with `token_counter` necessarily `estimate` because `core/chunking/tokenizer.py` did not yet exist. A 256-bit preimage match is proof, not inference, so the fingerprint now in the file is **derived rather than re-recorded**, and the file's `config_hash` is left at its original value as the provenance it came from. The `policies` baseline (`ae2c592…`) was recovered the same way and differs only in `retrieval.top_k`, which is why one pinned configuration cannot serve both datasets. The gate has never run on a runner, so whether current code still reproduces those numbers is unknown until its first CI run; a `regressed` verdict there is a finding to investigate, not a reason to relax the tolerance.

**Installing from the lockfile — one job, deliberately (TASK-0398).** `uv.lock` is validated by `uv lock --check`, audited daily by `security.yml`, and until now was installed from by **nothing**: every job ran `pip install -e ".[dev]"`, an unpinned resolve at job time. Measured on this tree 2026-11-11, for `.[dev]` on linux/CPython 3.12 the lockfile and a same-day fresh resolve name the **same 145 packages** and disagree on the version of **42** of them (`mypy` 2.4.1 against 2.4.0, `ruff` 0.17.4 against 0.17.3, `pydantic` 2.14.3 against 2.14.1, nine OpenTelemetry distributions), while the maintainer's venv disagrees with the lock on **85 of its 170** installed packages, holds 12 the lock does not, and runs CPython **3.14.7** against CI's 3.12. Three resolutions, no two equal — which is how `main` went red on 2026-11-08 with every local signal green (CI's resolve had `httpx2`, the venv had only `httpx`, and `starlette.testclient` binds whichever is present). The **`must-run` job now runs `uv sync --locked --extra dev` and is the only job that does.** It is a canary, not a rollout: it `needs: [quality, windows]`, so the lint, type and both test verdicts are already posted when it starts and its red cannot be mistaken for theirs; it has four steps that can fail — install, download, collect, check — so a red names its own cause; and its install is the same package set the converted jobs would get, with a collection step that imports the whole test tree. The price of that `needs` is stated rather than discovered: the job is **skipped** when either lane fails, so the canary reports only on runs that were already green and the conversion decision counts green runs, not elapsed days. The rest stay on `pip install` until there are several — and then convert together for `.[dev]` on ubuntu, because `windows`, the two torch jobs and the bare-`.` job each add an axis this canary does not test.

**Extras already scope the lock, so `uv sync` does not drag CUDA into every job.** From the lock's own recorded wheel sizes for linux x86_64 / cp312: bare `.` is 49 packages and **64 MB**, `.[dev]` is 145 packages and **194 MB** with no `torch`, no `triton` and no `nvidia-*`, and `.[dev,rerank]` is 181 packages and **3.2 GB** — a cost the `models` and `eval-gate` jobs already pay under `pip` today, and one that only `--all-extras` (what the dependency audit exports, correctly) would inflict on a job that needs none of it. Resolving `.[dev]` from the lock took **6 ms** against **8.7 s** for the equivalent fresh resolve.

**Where upstream breakage lands after this, checked rather than assumed.** Pinning moves "a bad release reds the next push" to "a bad release appears when someone runs `uv lock --upgrade`", and two existing jobs already absorb most of that. `security.yml` audits `uv export --all-extras` with pip-audit **daily**, a strict superset of every job's extras, so an advisory against a pinned version surfaces within 24 hours whether or not anyone pushes. `nightly.yml` installs `.[dev,rerank,huggingface]` and `.[dev]` with **unpinned** `pip` every night and runs the eval harness and the mutation suite on them, so a release that breaks imports or behaviour still reds a run daily — and `ci.yml`'s `branch-verdict` job fails the next push on it. The uncovered remainder is exact and small: **nightly runs neither `ruff` nor `mypy`**, so if `quality` is converted later, a new `ruff`/`mypy` release that would fail this tree is seen by nothing until the lock is upgraded. That is the one signal a full conversion costs, and it is worth naming in whatever authorizes it. What the lockfile does **not** fix is the interpreter: `requires-python = ">=3.12"` admits the 3.14.7 dev venv, that is a second axis, and no gate can close it because CI never sees that machine — see [CLAUDE.md](https://github.com/balrajsingh165/fasterrag/blob/main/CLAUDE.md)'s Commands section for the one line a developer runs instead.

**`metadata` on a golden record is a retrieval *filter*, not annotation.** The harness passes it straight to `retrieve(filters=...)`, so a descriptive key that no chunk payload carries filters every candidate away and the run scores a flat `0.0` — indistinguishable from total retrieval failure. Keep it `{}` unless you are deliberately scoping the query.

#### 3.1.1 The stack was run, and it found three adapter defects (2026-11-11, TASK-0396)

Everything above was written on a machine with no Docker daemon. This section is the first run on one that has it — Docker Desktop 29.7.2, Windows 11, `main` at `79657ef` — and it is kept separate from the paragraphs above so the before and after stay legible.

**The file did not come up as written.** `docker compose up` failed on upstream's own image: `minio/minio:RELEASE.2023-03-20T20-16-18Z` → *"pull access denied for minio/minio, repository does not exist or may require 'docker login'"*. Not that tag — `docker manifest inspect minio/minio:latest` answers *"unauthorized: authentication required"*, so the whole Docker Hub repository is closed to anonymous pulls, while `redis:7.4.2-alpine` and `quay.io/coreos/etcd:v3.5.18` pulled anonymously in the same session; `quay.io/minio/minio` answers 401 and `bitnami/minio` is gone. A CI job cannot log in to a third party's registry to run a test. Milvus does not need the segment store at all for this purpose: `COMMON_STORAGETYPE: local` keeps segments on the container's disk, which is what a disposable stack wants anyway, and it was verified before being committed — container healthy on `/healthz`, `get_server_version()` → `2.5.14`, and a create / insert / search round trip returning the inserted vector at distance 1.0. **The MinIO service is deleted and the stack is one container smaller.**

**Then the suites ran, and both adapters failed on first contact with a real server**, which is the outcome the paragraph above predicted:

| Suite | First real run | After the fixes |
|---|---|---|
| `tests/integration/milvus` | **2 failed, 7 passed, 37 errors** in 75 s | **46 passed** in 129 s |
| `tests/integration/weaviate` | **hung indefinitely** at 57%, killed after 12 min | **54 passed** in 147 s |
| `tests/integration/test_redis_rate_limit_server.py` (new) | — | **9 passed** in 8 s |

Three defects, each invisible to the unit tier because each test double disagreed with the real client:

1. **Milvus: no collection could be created at all.** `schema.description = description` → `AttributeError: property 'description' of 'CollectionSchema' object has no setter`. `description` is read-only in pymilvus 3.x and goes in at construction; this one line accounted for all 39 non-passing cases. The double accepted the assignment because it had declared `description` as a plain writable attribute.
2. **Weaviate: `iterate_points` never terminated.** `_walk` paged with `islice(cursor, batch_size)`, and `islice` calls `iter()` on its argument — Weaviate's `_ObjectIterator.__iter__` **rewinds the walk to the first page**. So every page restarted the collection: 400+ gRPC round trips for a *one-object* collection, re-yielding the same objects forever. A full-collection walk is what snapshots, export and re-embedding are built on. The cursor is now advanced with `next()`, which does not re-enter `__iter__`. The double returned a plain `iter(list)`, which is harmless to re-enter, which is exactly why 95% coverage proved nothing here.
3. **Weaviate: `restore_snapshot` could never clear a collection.** The "match everything" filter was `fr_id != ""`; a real server tokenizes the empty string to nothing and refuses the whole batch delete with *"invalid search term, only stopwords provided"*. It is now an id filter against the nil UUID, which no tokenizer touches and which a UUIDv5 object id can never equal. Four candidate filters were tried against the server and two were rejected by it; the two that worked are recorded in the commit.

**Both test doubles were made faithful in the same change**, so each defect is now reachable from the unit tier: `FakeSchema.description` is a read-only property, and `FakeObjectIterator.__iter__` rewinds. With the old `islice` loop against the corrected double the walk never empties; with `next()` it empties after one page.

**A fourth finding, which the paragraph below had written off as unreachable.** `test_invalid_credentials_are_not_retryable` was expected to assert nothing against an open door. It failed instead: the client still sends the API key, Weaviate answers **HTTP 401** (*"oidc auth is not configured"*), and the adapter classified that as `EMBED_PROVIDER_ERROR` with **`retryable=True`** — a caller retrying a rejected credential forever. None of the adapter's auth phrases (`unauthorized`, `forbidden`, …) appear in a real server's wording. The status code is now checked before the prose, and the case returns `VECTOR_DB_AUTH_FAILED`, `retryable=False`. **So the stack buys 46 of 46 Milvus and 54 of 54 Weaviate cases, not the 44/52 estimated above** — an open server rejects a bad credential differently, not never.

**Redis: `FakeRedis` and a real server agree, which is the finding (TASK-0290).** `tests/integration/test_redis_rate_limit_server.py` runs `RedisRateLimiter` against `redis:7.4.2-alpine` over a real socket, each case in its own UUID namespace so it is safe to point at a server that is not empty. All nine cases pass, including one that drives the same sequence of decisions through both a real server and `FakeAsyncRedis` and asserts the two decision lists are identical, and one that asserts the `MULTI`/`EXEC` reply shape is `[1, True]`. **No divergence was found** — the fixed-window `INCR` + `EXPIRE` arithmetic, the TTL, and the server-side eviction behave identically. That is a weaker result than a divergence would have been, but it is now measured rather than assumed. Still unproven and stated in that module: timeouts, resets, partitions, failover and pool exhaustion, so the fail-open path remains reachable only by injection; and the two limiters sharing a ceiling share a server but still one interpreter, so cross-process sharing — the reason the backend exists — is untested.

**Not verified by any of this:** no run happened on Linux or in CI, so these are Windows numbers from one machine; the compose stack's Milvus now stores segments locally rather than on S3, so no S3-backed Milvus has been exercised; nothing was measured about pull time or cold-start cost on a GitHub runner; and `pgvector`, `chroma` and `qdrant` were not re-run, so the coverage inversion above is corrected only for the two adapters named here.

**GitHub's `services:` block cannot host it**, which is why this is a compose file and not four `services:` entries: `services:` offers no way to override an image's command, and etcd (`etcd -advertise-client-urls=...`), MinIO (`minio server /minio_data`) and Milvus (`milvus run standalone`) each need one. So the CI shape is a `docker compose ... up -d --wait` step, `--wait` load-bearing because Milvus's own healthcheck allows it a 90-second `start_period` and a suite that starts first would skip with a connection error — this defect, returning as a race. The job to add, which is **not in `ci.yml` and has never run**:

```yaml
  vector-backends:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install -e ".[dev]"
      - run: docker compose -f deploy/compose.test-backends.yml up -d --wait
      - run: curl -sf http://localhost:9091/healthz && curl -sf http://localhost:8080/v1/.well-known/ready
      - run: pytest -m integration -rs --junitxml=contract.xml tests/integration/milvus tests/integration/weaviate
        continue-on-error: true
      - run: python scripts/check_contract_ran.py contract.xml   # fails on a skip, not only on a failure
      - if: always()
        run: docker compose -f deploy/compose.test-backends.yml down -v
```

The last step before teardown is the one that matters: **pytest exits 0 when every selected test skips**, so a job that only reads the exit code would reproduce, one level up, the defect it was added to fix (trap T12). The guard reads the JUnit report and fails on a skipped case, an empty report, or no report.

#### 3.1.2 `check_contract_ran.py`: the guard, and the exit code it does not trust (TASK-0396)

`scripts/check_contract_ran.py` is that step, written and proved on 2026-11-11. It was the piece §3.1 named as missing, and it is worth having whether or not the job above ever lands, because the hole it covers is not hypothetical.

**The hole, reproduced rather than argued.** With no Milvus running, `pytest -m integration tests/integration/milvus --junitxml=…` printed `1 passed, 45 skipped` and **exited 0**. A CI step reading that exit code reports success for a suite that measured nothing — which is precisely what the `integration` job has done on every push. Pointed at that same report, the guard exits **1** and prints each skipped case with its reason (`no Milvus at http://localhost:19530 (MilvusException … server unavailable)`). Pointed at the report of the fixed 46-case run, it exits **0** and prints `46 of 46 cases executed`.

**What it fails on:** `skipped` (any `<skipped>` case), `empty` (a report with zero cases — what a bad path argument or a collection error produces), `missing` (no report, since pytest writes `--junitxml` even when it fails, so an absent one means the step never reached pytest), `unreadable` (not parseable XML, or a root that is not `<testsuites>`/`<testsuite>` — a truncated artifact must not read as a pass), and `too-few` under the optional `--expect-at-least`, counted over *executed* cases so a skip can never help a report clear its own floor.

**What it deliberately does not fail on: a failure or an error.** A contract case that ran and failed is a *result* — it reached the server, which is all this gate asks — and the job's own pytest step goes red for it. Counting it twice would make this gate's message the one a reader debugs when pytest's is the better one. The counts are printed either way, so the summary line stays honest about what ran.

**What it cannot do:** it reads a report, so it cannot distinguish a suite that skipped from one that was never selected — `empty` answers both and the remedy differs — and it does not know which suites *should* be in a report, so pointing it at a run that selected one suite instead of two passes. `--expect-at-least` is the blunt instrument for that, and it is a count rather than a roster. `tests/unit/scripts/test_check_contract_ran.py` pins all fifteen behaviours, the vacuity guard's own included.

**What the stack does NOT buy, stated rather than left to be discovered.** Both servers run open — Milvus with authorization off, Weaviate with anonymous access on — so neither rejects a bad credential, and `test_invalid_credentials_are_not_retryable` is exactly the case both suites override `misconfigured_adapter` to reach. Against this stack it asserts nothing it could not assert against an open door. So the file buys **44 of 45** Milvus and **52 of 53** Weaviate cases, not all of them. The alternative puts an API key and a Milvus `authorizationEnabled` override into committed YAML, which CLAUDE.md does not allow and which pins both suites to a key nobody rotates; turning auth on with the key read from the environment is the follow-up.

**Cost, now part-measured (2026-11-11, one Windows machine, not a runner).** Image sizes are measured, from `docker images` after the run: `milvusdb/milvus:v2.5.14` **2.78 GB**, `cr.weaviate.io/semitechnologies/weaviate:1.28.4` **263 MB**, `quay.io/coreos/etcd:v3.5.18` **86.2 MB**, `redis:7.4.2-alpine` **61.1 MB** — **3.19 GB** on disk in total, dominated by Milvus, and more than the 2.5 GB previously estimated. Suite wall clock is measured: Milvus **129 s** for 46 cases, Weaviate **147 s** for 54, the real-Redis module **8 s** for 9; the three together, in one pytest invocation, **132 s and 207 s for 116 cases** on two runs of the same code — the spread is machine load, not the suites, and the slower figure is the safer one to plan with. `docker compose up -d --wait` on already-pulled images, from a `down -v`, reached all four healthy in **17.5 s** — Milvus reported healthy **5 s** after its container started, because dropping MinIO took the object-store handshake out of its boot. That is far under the 90 s this document previously assumed and well under the `start_period: 120s` the healthcheck still allows, which is now headroom rather than a wait. What is still **not** measured is the only part that differs most on a GitHub runner: cold pull time for 3.19 GB, and whether `ubuntu-latest` starts Milvus faster or slower than this machine. Against run 42972651661's `integration` job (38 s install, 65.11 s for 281 executing cases, **2 m 21 s** for the job), the measured halves add **2.5 to 3.7 minutes** (17.5 s bring-up + 132-207 s of suites), so the earlier **6-12 minute** estimate now looks high at its top end: on a runner the remaining unknown is almost entirely the cold pull of 3.19 GB.

**Why it is not wired yet, said plainly.** Both adapters shipped with "never run against a real server" recorded honestly, so the first run is as likely to find an adapter defect as to go green; switching 98 never-executed cases on, on the push path, in one commit, is the big-bang change CLAUDE.md forbids. A separate `workflow_dispatch` workflow was the obvious middle ground and was **written and then withdrawn**: `ci.yml`'s `branch-verdict` job discovers every file in `.github/workflows` and treats *no completed run on `main`* as red, so a new workflow would have turned that gate red on the next push and again on its own first, expected-red run. The honest sequence is: dispatch the job above by hand once, read what the adapters actually do against a real server, fix what it finds, **then** add it to the `integration` job in the same commit as the ledger entry that says it runs. Until that happens the two suites do not run on the push path, and this document says so.

**Where that sequence now stands (2026-11-11).** Its middle steps are done, off CI: the stack was run by hand, the adapters were read against a real server, and the four things it found are fixed (§3.1.1). What remains is the last step — adding the job above to `ci.yml` — and it is **deliberately left for a human**, unchanged, for the reason this paragraph already gives: that commit switches ~100 never-executed cases onto a path CI gates on, and it should be made by someone who has decided to accept the measured cost above on every push. Two things should be settled in the same decision. First, the `vector-backends` job must keep both the `continue-on-error: true` on the pytest step and the `check_contract_ran.py` step after it, because without the guard the job reads only an exit code and **pytest exits 0 when every selected case skips** — the defect one level up (§3.1.2). Second, nothing new should be added under `.github/workflows/`: a second workflow file turns `branch-verdict` red, which is why the `workflow_dispatch` middle ground was withdrawn and why this job belongs inside `ci.yml` when it lands.

### 3.2 `must_run`: a skip that fails the build (TASK-0349)

`-rs` makes a skip legible to a reader who looks. It does not make one impossible to ignore, and the census in §3.1 took a progress-dot diff against a local collection count to produce — once, by hand. `@pytest.mark.must_run` is the other half: a claim about one test, *this one executes somewhere in CI*, that the `must-run` job in `ci.yml` makes cost something.

**The rule is RAN AT LEAST ONCE, never "ran everywhere", and the distinction is encoded rather than flattened.** `test_a_symlink_out_of_an_allowed_root_is_refused` cannot run on a Windows account without `SeCreateSymbolicLinkPrivilege`; skipping there while running on Linux is the correct outcome and stays green. Skipping on **both** is the bug, because the confinement guard's symlink leg is then unverified everywhere. Each lane reports its own verdict, the verdicts are kept apart, and a finding prints all of them.

**How the evidence crosses jobs.** `tests/conftest.py` writes one JSON document per pytest invocation when `FASTERRAG_MUST_RUN_REPORT` names a destination — which marked tests that invocation collected, and whether each ran or skipped. The `quality` (ubuntu) and `windows` unit lanes upload theirs; the `must-run` job downloads both and runs `scripts/check_must_run.py`. The roster is collected separately, by `pytest -m must_run --collect-only`, because a lane can only report on tests it collected: a test marked `must_run` and left in a tier CI never runs would appear in no report at all, and "absent everywhere" must not read as "nothing to check". A document records whether its invocation ran tests or only collected them, so neither can be mistaken for the other.

**Which tests earn it, and why not more.** A marker on every test is a marker that means nothing — the set is meant to stay small enough that a human can read it, and today it is **17 cases**:

- the two symlink confinement cases in `tests/unit/services/test_sources.py`. Security-relevant (the escape they refuse reads a file outside every allowed root), each carries a real conditional `pytest.skip`, and that skip is legitimate on one platform — which is exactly the shape the gate has to get right;
- four functions in `tests/eval/test_live_provider_gating.py`, which parametrization expands to fifteen node ids: the ones proving `FASTERRAG_LIVE_PROVIDER_TESTS` is checked *before* the credential, and the counterpart proving an explicit opt-in still lets a probe through. TASK-0341 made that module deliberately unmarked so it could not skip — a convention one line of `pytestmark` can undo, with a billed call at the other end of it. The marker is what turns the convention into a gate.

Deliberately **not** marked: the Milvus and Weaviate contract suites, whose skip is honest, loud and about provisioning rather than test integrity (§3.1); the live-provider probes themselves, which *must* be able to skip — that is the whole opt-in design; and every Docker-gated integration fixture. The criterion is narrow: a test earns the marker when it is the only executable proof of a security- or money-relevant invariant **and** it has a plausible way to skip silently on every platform.

**The gate is not vacuous, and the hole was obvious.** A missing artifact, an empty reports directory, a roster carrying zero marked tests, reports holding not one outcome between them, a collect-only document passed as evidence, a report from a writer version this reader does not know, or a lane reporting a node id the roster lacks — each is a **failure**, named separately, never a pass. A gate that cannot tell "clean" from "never ran" is worse than no gate (rebuild-playbook trap T12), and `tests/unit/scripts/test_check_must_run.py` pins all of it, including the asymmetric case that must stay green.

**What it cannot do:** decide which tests deserve the marker; judge verdicts (a marked test that ran and failed is `ran` here, and its own job goes red); or see a lane that does not set `FASTERRAG_MUST_RUN_REPORT` — a marked test in such a lane fails as `ran-nowhere`, which is the right answer, and the fix is to wire the lane rather than unmark the test.
