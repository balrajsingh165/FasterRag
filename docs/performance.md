# performance.md — Performance Goals & Measurement Methodology

> Provable-claims policy applies: **a claim without a measurement is a bug.** Everything in this file is a **goal** or a **method** until the [benchmark ledger](benchmarks.md) holds a measured entry for it. SLO targets derive from these measurements only after the baseline run on documented reference hardware ([slo.md](slo.md)).

## 1. What we measure

| Metric | Definition | Measured by |
|---|---|---|
| End-to-end latency p50/p95 | `POST /v1/query` receipt → final token (non-cached, non-degraded) | query benchmark suite; histogram `fasterrag_request_duration_seconds` |
| Per-stage latency | embed / retrieve(dense) / retrieve(bm25) / fuse / rerank / assemble / generate, p50/p95 — the **retrieval vs generation** split | `fasterrag_stage_duration_seconds`; per-query `timings_ms` |
| Time-to-first-token (TTFT) | request receipt → first SSE `token` event | `fasterrag_ttft_seconds` |
| Ingestion throughput | docs/sec and tokens/sec sustained over ≥ 10 min | ingest benchmark suite; `fasterrag_ingest_throughput` |
| Retrieval quality | recall@k, MRR, nDCG on named eval datasets | eval harness (`pytest -m eval`, `fasterrag benchmark --suite eval`, `scripts/measure_rerank.py`) |
| Faithfulness | grounding score distribution of generated answers | eval harness |
| Cache hit rate | semantic + embedding cache hits / lookups | `fasterrag_cache_events_total` |
| Cost per query | Σ provider token costs / queries | `fasterrag_cost_usd_total` |

## 3. Methodology (the rules every measurement follows)

1. **Hardware is part of the number.** Every run records the exact spec: CPU model + cores, RAM, GPU model + VRAM, storage class, OS; recorded automatically by `fasterrag benchmark --ledger`.
2. **Datasets are named and versioned.** Eval/benchmark datasets live under `tests/eval/datasets/` with a manifest (doc count, token count, source, license). No number without its dataset name.
3. **Warm/cold discipline.** Latency suites report cold-start and warmed (caches primed, model loaded) separately; cache-hit metrics are never mixed into non-cached latency percentiles.
4. **Percentiles over averages.** p50/p95 (p99 where sample size permits); minimum 1,000 samples per latency figure.
5. **Isolation.** Benchmarks run with no co-tenant load; background jobs disabled; three repetitions, median run reported, all runs attached.
6. **Baselines are measured, not quoted.** "Fastest" claims require a named competitor/baseline measured by us with the same harness, dataset, and hardware, harness committed to this repo.
7. **Regression tracking.** A nightly workflow (`.github/workflows/nightly.yml`) runs the eval harness and **the ingest suite only** (see *What the nightly does and does not measure* below), fetches the previous night's artifact, compares the two with `scripts/compare_nightly.py`, and uploads ledger-format artifacts — tonight's numbers plus the comparison — with 30-day retention. What it compares, exactly: the warmed median `p50_ms`, `p95_ms`, `p99_ms` (lower is better) and `throughput_per_sec` (higher is better) of every suite the two runs share. A metric that moved more than **125%** in the worse direction fails the job; an improvement never does. That tolerance was 10% until 2026-11-11 and is now a measured quantity, derived from this runner's own spread on an unchanged tree — see *A 3 ms measurement with a 10% tolerance is a flap risk*, below, which records the measurement, what the new number cannot see, and why it may not be widened again.
   - **Three outcomes, not two.** *Regressed*, *within tolerance*, and *not comparable* — no previous artifact, a different runner, a different dataset, a missing or zero metric. "Not comparable" **fails the job** and is never reported as a pass, because a gate that goes green having compared nothing is worse than no gate. It was mapped to a job-summary warning until 2026-11-08 while `ci.yml`'s eval gate exited 1 on the identical verdict, and that asymmetry is what let the measure job report success on 2026-11-07 (run 42359949403) having written a zero-byte `benchmark.json` (TASK-0314). This mirrors the retrieval regression gate (`services/regression.py`), which refuses a baseline recorded under a different embedding model and blocks rather than passes when no baseline exists.
   - **It does not append to the ledger and does not file a bug.** That is a decision, not an omission. [todo.md](todo.md) is this repository's only task file, and these numbers are not citable (shared runner — see rule 5 above), so a job writing entries from them would be a machine building a second task list out of measurements the methodology forbids citing. A regression fails the nightly job, which is already a notification; a human decides whether it earns a task or a run on real hardware.
   - **Verification status (2026-11-08, TASK-0323).** `scripts/compare_nightly.py` is covered by unit tests in `tests/unit/scripts/test_compare_nightly.py`, including the not-comparable cases. The workflow wiring around it is **no longer unobserved**: run **42419161973** (`workflow_dispatch` on `main` at `0c7f81a`) performed the previous-run lookup, downloaded run 42359949403's artifact, and compared — exercising every step of the fetch path on a real run. The run is **red, as designed**: the baseline it found was the previous night's zero-byte document, and the comparison said `[not-comparable] previous/benchmark.json is not a readable benchmark document` rather than waving it through.
   - **What the nightly does and does not measure.** The `measure` job runs `fasterrag benchmark --suite ingest` — parse and chunk, through `estimate_sources`, over `tests/eval/datasets/handbook/corpus`. It does **not** measure retrieval, embedding, indexing or generation, and it opens no socket to any backend: run 42419161973 recorded `ingest | dataset "6 documents, 632 tokens" | median p50 3.05 ms, p95 3.21 ms, throughput 325.112/s` on a 4-core x86_64 Azure runner, and nothing else. The Qdrant service that was declared in that job until 2026-11-08 was never contacted by anything in it and has been deleted; a declared dependency nothing uses tells a reader the job reached a backend it never reached, which is the same class of defect as the eighty-three days of measuring nothing.
   - **Open: the query suite is unmeasured, and that is a gap rather than a result.** The suite this job exists for — the one carrying the latency percentiles this document is about — answers a question through the configured LLM (`openai/gpt-4o-mini`), and a hosted runner holds that key only as a placeholder. Two endings are available and **the decision is the maintainer's** (TASK-0323):
     - *Supply a credential.* A repository secret (`OPENAI_API_KEY`) restores `--suite query` against a real provider. **Buys:** a nightly end-to-end latency series, and the Qdrant service block earns its place again. **Costs:** paid tokens on every scheduled run; a number dominated by provider round-trip time, which §Scope already says is not fasterRag's to control; and a secret readable by any workflow in the repository.
     - *Run an offline model.* `ollama` is the only provider needing no credential. **Priced out 2026-11-08, from the vendor's own published figures rather than from a run** — nothing below has been executed on a runner: the Linux installer bundle `ollama-linux-amd64.tar.zst` is **1,543,547,172 bytes** (v0.40.15, GitHub release assets API), and the `ollama/ollama:0.40.15` container is **worse** at 3,392,421,545 compressed bytes for linux/amd64 (Docker Hub), so the tarball is the cheaper route. The smallest usable weights are `smollm2:135m` at **271 MB**, `qwen2.5:0.5b` at **398 MB** and `llama3.2:1b` at **1.3 GB** (ollama.com library pages). **Cacheable:** yes — `~/.ollama/models` is an ordinary directory and fits easily inside GitHub's documented **10 GB per-repository** cache budget; a nightly cadence also stays inside the **7-day** unused-cache eviction window, so the cache stays warm. The runtime bundle is the awkward half: 1.44 GiB compressed, unmeasured extracted, and large enough that caching it needs the GPU libraries pruned first. **What this would actually buy is the problem.** A 0.5B model generating on a 4-core shared runner measures CPU token throughput, not fasterRag; the resulting `query` numbers would share a suite name with every other query measurement in this repository while measuring something else entirely, and `compare_nightly.py` would compare them night over night as though they were the same thing. **Recommendation: do not take this option to produce a latency series.** It is worth taking only to make the query *path* execute nightly — a smoke test that generation still works end to end — and if it is taken for that, the suite should be named so that nothing mistakes it for the query benchmark.
     - **Not measured, stated plainly:** the download time of any of the above on a hosted runner, the extracted size of the ollama bundle, and the cache save/restore time. Confirming them needs one `workflow_dispatch` run that installs ollama, pulls `qwen2.5:0.5b` and prints `/usr/bin/time` plus `du -sh`; no such run has been made.
   - **A 3 ms measurement with a 10% tolerance was a flap risk; the tolerance is now 125%, and the number is measured (2026-11-11, TASK-0350).** The corpus is 6 documents and 632 tokens, and the warmed median is about 3 ms, so the old 10% was 0.3 ms — inside shared-runner noise. The size of that noise is no longer a guess, and it is much larger than the task that filed it assumed.
     - **The controlled experiment.** Three `workflow_dispatch` runs of the **identical commit `882a07e`**, inside twenty minutes (42973481640, 42973944898, 42974619023), recorded warmed median p50 of **1.98 ms, 2.87 ms and 1.39 ms** — a **2.07× spread, 106.5% adverse**, against a tree that did not change by one character. The gate failed the middle run outright: *"ingest.p50_ms moved from 1.98 to 2.87, 44.9% worse, beyond the 10.0% tolerance"*. Throughput on the same three runs: 487.8, 339.6 and 701.7 ops/s.
     - **The full sample.** Seven runs of the same workload over five days: 3.05, 2.17, 3.03, 3.07, 1.98, 2.87 and 1.39 ms (42419161973, 42468563494, 42603353729, 42800995556, 42973481640, 42973944898, 42974619023). Mean **2.51 ms**, sd **0.67 ms**, **CV 26.5%**, worst adverse move **120.9%**. The gate had already produced one false red in production on 2026-11-09 (42603353729, "39.6% worse") between two commits whose only ingest-path difference is a log line inside an exception handler — and that night's 3.03 ms sits between a 3.05 before it and a 3.07 after it, so the unusual number was the **baseline**, not the run that failed.
     - **Why the tolerance moved and the corpus did not.** The variance decomposes: repetitions *within* a single run agree to **0.19–2.54%**; three runs of one commit differ by up to **106.5%**; the full sample by **120.9%**. Corpus size only touches the first term — the measurement is already precise, and three repetitions agreeing to a few tenths of a percent prove the limit is not timer quantisation. The dominant term is a multiplicative host-speed difference that scales with the corpus and survives enlarging it unchanged: a **10× larger corpus would still have shown 1.39 against 2.87**, because both would grow by the same factor. Enlarging the corpus would cost minutes of nightly runtime and buy nothing.
     - **Why not an absolute floor.** At this corpus size a floor is the same percentage wearing a different hat. The same-commit pair above moved **1.48 ms**, so a floor that suppresses it is ≥1.5 ms, which against a 1.39 ms run *is* a 107% tolerance. The floor restates the percentage in units that hide where it came from.
     - **Why not require a regression to reproduce twice.** It costs a day of detection speed, and against the measured data it does not work either: every false red observed here came from an unusually *fast baseline*, not an unusually slow current run, and a second slow run reproduces the same false verdict against the same baseline.
     - **Where 125% comes from, and why it is not the observed maximum.** Setting the tolerance to the worst move yet seen (120.9%) would be fitting a bound to seven samples. The spread is multiplicative, so the variate is log(p50): mean **0.8838**, sd **0.3026** over the seven runs. A comparison draws *two* independent samples — baseline and current — so a two-sided 2σ band spans **exp(4 × 0.3026) = 3.35×**, i.e. a **235% move**, and that is the tolerance this instrument honestly supports. 125% is deliberately tighter than that bound, because a gate set at 235% fires at nothing and the extra insensitivity buys no honesty this section does not already state. The residual false-red rate is therefore real and is published here rather than hidden: **the next night's baseline is 1.39 ms**, the lowest of the seven, and a 3.07 ms night against it lands at 120.9% — inside 125% by four points.
     - **What 125% buys and loses.** It buys a gate that stops failing for the runner it was assigned, and therefore survives long enough to be read. It loses everything finer than a **2.25× slowdown**. On this instrument that is not a choice between tolerances: a 2.07× spread on one commit means **no tolerance exists that both detects a real regression and stays quiet**, and pretending otherwise is what the 10% number was doing. What remains is a smoke alarm — an accidental quadratic or a re-introduced model load would still trip it — worth its zero cost on that basis alone.
     - **The regression verdict was never the valuable part of this job.** What TASK-0314 actually caught was 83 days of measuring *nothing* while reporting success. The checks that catch that — the benchmark-produced-a-document step, the not-comparable verdict failing the job, the crashed-versus-judged distinction, `if-no-files-found: error` — are unaffected by any tolerance and remain the job's real output. Widening the tolerance does not weaken them.
     - **This tolerance is not to be widened again.** Seven samples cannot bound the tail, so another false red is possible. If one arrives, the answer is the instrument, not a larger round number.
     - **The fix this defers.** A **paired** measurement — benchmark the working tree and a fixed reference commit in the same job on the same VM — cancels host speed and would let the tolerance return to single digits, since the within-run term is under 3%. It is not taken here because a workflow change cannot be verified before it is committed (`workflow_dispatch` runs the file already on the ref), and an unverifiable rewrite of the repository's only measurement job does not belong beside a tolerance fix. **Not established:** whether the spread is CPU generation or co-tenant contention. That matters, because pairing cancels the first completely and the second only partly, and nothing in this repository records which it is — the benchmark fingerprint stores `cpu: "x86_64"`, an architecture, so `compare_nightly.py`'s machine-mismatch guard cannot see a host change at all. The runner's CPU model is now printed to the job summary as the first step toward answering it.

## 4. Harness

- `fasterrag benchmark --suite ingest|query|eval|all --dataset <name> --ledger` orchestrates the suites and emits ready-to-commit ledger entries. **Built.**
- `scripts/compare_nightly.py --previous <a.json> --current <b.json> [--tolerance 0.10]` compares two `fasterrag benchmark --json` documents and exits `0` within tolerance, `1` regressed, `2` not comparable. **Built**, and usable by hand on any two artifacts, not only by the nightly job. It detects a *change* between two runs; it produces no ledger entry and makes neither run citable.
- `scripts/measure_rerank.py [--dataset <dir>] [--model <cross-encoder>] [--chunk-size <n>] [--json <path>]` prices the rerank stage across candidate `retrieval.rerank` defaults: the harness's own recall@k / MRR / nDCG@k per configuration, plus each cross-encoder's on-disk size, cold load time, and per-query rerank latency. **Built**, and run — see BENCH-0003 in [benchmarks.md](benchmarks.md), which is **not citable**, for two separate reasons: a shared developer workstation, *and* quality deltas that fall inside the committed golden sets' own noise. It reuses `fasterrag.core.evals.evaluate` rather than defining a second notion of retrieval quality, substitutes an exact in-process store for the vector database (so the comparison between configurations holds while the absolute numbers are not a Qdrant reproduction), never downloads weights without `--allow-download`, and decides nothing: it exists to give TASK-0175 a number instead of an expectation, and its most useful finding is which number the repository still cannot produce.
- `scripts/measure_cost_governor.py [--charges 10000,100000,1000000] [--tenants <n>] [--samples <n>] [--window-seconds <s>] [--json <path>]` prices a tenant's rolling spend window: bytes held, cost of the `check` that reads it, cost of the `record` that charges it, and the eviction walk, for the shipped bucketed `CostGovernor` beside a transcription of the per-charge structure it replaced. **Built**, and run — see BENCH-0005 in [benchmarks.md](benchmarks.md), which is **not citable** (shared workstation, dirty tree). Both designs are measured in one process so the comparison is paired, and the harness cross-checks that they report the identical in-window total, which is what makes bucketing an approximation of *when* spend expires rather than of *how much* was spent. It decides nothing: it gave TASK-0366 a measurement where the ledger had an inference.
- `python -m tests.load.run_load --target <url> --scenario query|ingest|mixed --users <n> --duration <s> --dataset <dir> --sut-hardware "<spec>" [--isolated] [--repetitions 3] [--processes <n>] [--json <path>] [--ledger-draft]` drives the concurrency scenarios with Locust and reports the [slo.md](slo.md) §1 SLIs. **Built 2026-11-07 and never run against fasterRag** (TASK-0243): there is no isolated reference hardware (TASK-0084) and no load number anywhere in this repository. The tool exists because the provable-claims policy requires the harness to be committed before a comparative claim can be made from it, not because a measurement has been taken. What it measures, what it refuses, and why Locust rather than k6 are in [testing-strategy.md](testing-strategy.md) §1.7; the procedure for running it is §5 below. It never reports a pass — its verdict is `valid-sample` or `invalid` — because every SLO target is still TBD-until-measured.
- `FASTERRAG_SOAK_SECONDS=<s> FASTERRAG_SOAK_SAMPLE_INTERVAL_S=<s> pytest -m soak` runs the soak harness for a configurable duration, sampling RSS and open handles and trend-testing the series (Theil–Sen plus a permutation test, [testing-strategy.md](testing-strategy.md) §1.8). **Built 2026-11-11 and proven only on a short run**: the 24 h run the specification names has never been performed, and on a shared workstation it could not be — a soak measures whatever else the machine is doing. It produces no ledger entry, because it grades resource *trend* rather than speed, and it asserts no latency at all.
- The reference-hardware baseline run happens at build-phase slice S11; until then this document contains **no measured numbers by design**.

## 5. Load-run operator procedure

Written for whoever has the hardware, which at the time of writing is nobody. Follow it in order; a step skipped is a run that cannot be cited, and §5.4 says so explicitly rather than leaving it to judgement.

### 5.1 The machines

Three roles, and the first rule is that the first two are **not the same machine**. A load generator competing with the system for cores measures the contention, and the error runs in the direction that makes fasterRag look slow.

| Role | Requirement |
|---|---|
| System under test | Dedicated, idle except for fasterRag and its backends. No desktop session, no other containers, no co-tenant VM. Fixed CPU governor (`performance`, not `ondemand`), swap off or irrelevant, and the exact spec recorded — it is passed to `--sut-hardware` by hand, because nothing on the generator can detect the machine at the other end of a URL. |
| Load generator | A separate box on the same wired LAN segment, with headroom to spare. Watch its own CPU during the run (`top`, `psutil`, anything): if the generator saturates, raise `--processes` until it does not, or the numbers describe Locust. |
| Backends | Qdrant (or the configured vector DB), any embedding/LLM providers, and the journal store. A remote LLM makes the end-to-end figures provider-dominated, which is exactly why the headline SLI excludes generation. Record whether providers were local or remote; it changes what the run means. |

A run across a VPN, a laptop on battery, a cloud instance with burst credits, or any machine shared with another workload is a tool exercise, not a measurement. Say so in the report rather than discarding it quietly — a known-bad run is evidence about the harness.

### 5.2 Running it

1. Install the generator: `pip install -r tests/load/requirements.txt`. Nothing else is needed; the harness's other modules are standard library only.
2. Put a key in the environment if the target has auth on: `export FASTERRAG_LOAD_API_KEY=...`. It is never a flag — a command line is visible in shell history and in every process listing on the box.
3. Pick the dataset. Any directory under `tests/eval/datasets/` works: the queries come from its committed `golden.jsonl` and the ingest corpus from its `corpus/`. The dataset name is part of the number, so a run against an uncommitted corpus cannot be recorded.
4. Point it at a **throwaway collection**. The ingest and mixed scenarios write, and the preflight writes one document of its own. Never run against an index whose contents matter.
5. Run each scenario separately — `query`, then `ingest`, then `mixed` — at each concurrency step you care about. Stepping is done by re-running with a larger `--users`, not by a load shape inside the harness. Record every step, including the ones past the knee; where throughput stops rising is the most useful thing a load test tells you.
6. Pass `--isolated` only if §5.1 actually held. It is an assertion, and it is the switch that decides whether a ledger entry may exist.
7. Keep the defaults for `--repetitions` (3), `--warmup` (60 s) and `--min-samples` (1,000) unless you are deliberately producing a non-citable exploratory run. They are §3's rules 3, 4 and 5 in mechanical form.
8. Read the exit code. `0` means the run produced a valid sample — *not* that the system is fast. `2` preflight refused, `3` the run was vacuous, `4` too many failures or the rate limiter shaped the run, `5` Locust is not installed.

### 5.3 Recording a result in the ledger

Only once real hardware exists. `--ledger-draft` prints either a [benchmarks.md](benchmarks.md) entry in this repository's format or an itemised refusal naming every condition that is not met.

1. Run the scenario to a `valid-sample` verdict with `--isolated` and three warmed repetitions.
2. Take the draft, allocate the next `BENCH-` id, and **rewrite the claim line yourself.** The harness fills in method, dataset, hardware, date, numbers and commit; it deliberately does not write the claim, because what a number licenses is a human judgement. A p95 is a p95: it is not "the fastest RAG" unless a named competitor was measured by us, on this hardware, with this dataset, and that harness is committed too.
3. Attach all three repetitions (`--json`), not only the median. A reader needs the spread.
4. Only then may a `TBD-until-measured` row in §2 above or in [slo.md](slo.md) §1 be replaced, in the same change, with the target derived from it and a link to the entry. [todo.md](todo.md) tick required.

### 5.4 What makes a run invalid

Any one of these, and the run is not a measurement. The first six the harness detects and refuses on its own; the last four it cannot see, and they are the operator's responsibility.

- The preflight failed: the target was unreachable, not ready, not fasterRag, or could not answer the scenario's requests.
- Zero requests were recorded, or a scenario recorded none against an endpoint it requires.
- A latency figure rests on fewer than 1,000 samples, or a p95 came back as zero over real requests.
- The failure ratio exceeded `--max-failure-ratio` (1% by default).
- More than 5% of requests were rate-limited — the run measured `security.rate_limit`, not the system.
- Fewer than three warmed repetitions, or no `--isolated` assertion: both block the ledger draft.
- **Anything else was running on the system under test.** Undetectable from here; this is what `--isolated` asserts.
- **The generator saturated.** A p95 that stops moving as `--users` rises, with the generator's CPU pinned, is Locust's number.
- **The index was not in a known state.** Warm caches from a previous run, or a collection of a different size, make two runs incomparable even on identical hardware.
- **The configuration moved.** Chunking, retrieval or rerank settings are part of the measurement; `config.yaml` must be committed or recorded with the entry.
