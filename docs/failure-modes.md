# failure-modes.md — FMEA (Failure Modes and Effects Analysis)

Every anticipated failure, its detection signal, automatic mitigation, recovery procedure, and **the test that proves it**. Tests reference [testing-strategy.md](testing-strategy.md) (unit/integration/chaos/property suites); chaos scenarios are scripted and repeatable (D12). Error codes are the stable problem `code`s from [api-reference.md](api-reference.md).

> **How to read the last column, and what enforces it.** Each entry names the suite in words and then cites the test itself in backticks, as a path from the repository root, optionally narrowed with `::` to the class or function inside it. Anything else in backticks anywhere in a row — a configuration key, a problem `code`, a metric, a symbol — is prose evidence, not a citation, and nothing tries to resolve it; a citation is exactly a backticked token beginning `tests/`. A row whose proof was never written says **no test** in that column instead of naming one, and says what is covered instead, because a row that names a suite nobody wrote is worse than a row that admits it has none: it stops anyone from looking. That had happened four times before this convention existed, most recently to row 18. `tests/unit/docs/test_fmea_parity.py` now holds every citation in this file against the tree, requires every row to carry either a citation or the **no test** marker, and holds the marked rows against an exemption list that it also keeps minimal, so neither half of the column can rot quietly.

D12 requires that the injected faults and their observed behavior are recorded, not merely
asserted in a test file. The suite is `tests/chaos/test_chaos.py` plus the three scenarios
large enough to own a module, `tests/chaos/test_config_mutation.py`,
`tests/chaos/test_network_partition.py` and `tests/chaos/test_reranker_down.py`, all run with
`pytest -m chaos`. D2's reindex-under-query-load drill,
`tests/chaos/test_reindex_under_load.py`, runs under the same marker but is not a §1.9 row and
is logged separately below. The reranker-down module is a row 18 scenario rather than a §1.9
row, and is logged in its own section below for the same reason.

| Scenario (testing-strategy.md §1.9) | Observed | Date |
|---|---|---|
| Kill an embedding worker mid-batch | Re-writing the same batch produced 6 upsert calls carrying only 3 distinct point ids — the deterministic id makes the second write a replace, so no duplicate vectors reach the index | 2026-08-01 |
| Stop the Qdrant container | `health()` reports unhealthy; every operation raises `RETRIEVAL_FAILED` classified `retryable=True`, which is what lets the breaker act on it rather than treating it as a permanent fault; the adapter serves again as soon as the backend answers | 2026-08-01 |
| Feed a corrupt/malformed document | Recorded in the DLQ with `reason_code: PARSE_FAILED` and its attempt count; a sibling document in the same job still reached `indexed`, so one bad file did not stop the pipeline | 2026-08-01 |
| Slow LLM (latency injection) | Degraded to `extractive` with `degraded: true`, serving the retrieved passages and their citations rather than returning nothing | 2026-08-01 |
| Disk-full during ingest | The journal raises rather than corrupting state; the trace store, which writes *after* a query has been answered, swallows the failure and loses the record instead of failing the request; a checkpointed job resumes from index 499 at 500 | 2026-08-01 |
| Configuration mutated under a built index | Every single-field edit of the hashed subset — enumerated from the live schema, not listed by hand — was reported as drift *and* named at least one field; the four chunker fields the lock stores by name carried both the old and the new value. None of the legal edits outside the hashed subset reported drift, and re-validating the same configuration unchanged reported none either. Mutated corpus content, new weights behind an unchanged model name, and an index built under an older `IDENTITY_VERSION` were each reported by one sampled scenario; an absent lockfile is correctly not drift | 2026-10-25 |
| Network partition to a provider | The call ended on `reliability.timeouts.vector_db_ms` rather than hanging — asserted as a bound in both directions, never as a latency figure, the lower bound being what distinguishes a partition from a refused connection. The failure arrived as retryable `RETRIEVAL_FAILED` rendered as a 503 problem with a trace id and never `INTERNAL`; `health()` reported unhealthy with a detail instead of raising. Failure opened the breaker, and the next query was shed with retryable `CIRCUIT_OPEN` inside a bound far below the timeout it would have paid had it been sent — that bound is what proves it was shed rather than attempted. After the reset timeout the breaker admitted exactly one probe; the probe failed against the still-partitioned peer and re-opened it rather than granting a fresh threshold of doomed calls. Closing is asserted at the breaker with a scripted success, not against a healed socket, because a listener that swallows bytes cannot be turned into a working backend; the real-container restart covers the healed half. The same partition against the generation leg was classified the same way, which is what row 35's "any provider" needs; an unresolvable `.invalid` host took the same path | 2026-10-25 |

**Scope of this run.** Every scenario injects its fault at the closest honest seam — an
adapter raising what the real failure raises, a directory that genuinely cannot be written,
a configuration the real schema validated and a lock read back from a real disk, or a real
TCP listener that accepts and then goes silent. Simulating a *symptom* is legitimate;
simulating the *handling* would prove nothing, and where one step of a scenario is scripted
rather than injected — the breaker's healing — the row above says so.
Recovery *times* per scenario are not yet recorded; that needs the isolated hardware
TASK-0084 is blocked on.

## Observed behavior — reranker down

Row 18's rung, logged here rather than in the §1.9 table because it is a failure mode of this
document's own numbering and not one of testing-strategy.md's seven scripted faults. The suite
is `tests/chaos/test_reranker_down.py` (8 cases, `pytest -m chaos`). It drives the real
`RetrievalService` and the real `CrossEncoderReranker` over a scripted shortlist, so the only
failure domain in the run is the reranker.

| Fault | Observed | Date |
|---|---|---|
| The real `sentence_transformers` refusing a model name it cannot resolve | The library's own `OSError` is classified `RERANK_FAILED`, non-retryable, naming the model and chaining the cause — and the chained cause is not one of ours, which is what shows the translation happened rather than the error having been ours all along. The query is still answered: `hybrid_only`, `degraded: true`, the fused order intact and every `rerank_score` left unset | 2026-11-02 |
| A model that will not fit in memory (`RuntimeError`, the shape torch raises) | Same rung, and the loader was reached exactly once, so the degradation is the reranker's failure and not a reranker that was never consulted | 2026-11-02 |
| A model that loads and then dies while scoring | Same rung, with the model loaded and `predict` called before it failed: the mid-query seam and the load seam degrade identically, which is what row 18 claims and what had never been run | 2026-11-02 |
| The same fault on a second query | Degraded again, and the loader was called twice: a failed load is retried rather than cached, so the rung cannot quietly turn fatal on query two | 2026-11-02 |
| A reranker that works, over identical wiring | `full` mode and the shortlist reordered. The control case: without it every row above would also pass against a service that had simply stopped reranking | 2026-11-02 |
| The `rerank` extra absent (`ConfigError`) | **A limit, not a guarantee.** Also degraded to `hybrid_only`, on every query, with only a warning line — see the as-built note above. Pinned as built so that changing it is a visible diff | 2026-11-02 |
| A reranker constructed but never queried | No load attempted. Row 18's detection column used to say "at startup or first query"; loading is lazy, so only the second ever happens, and the column now says so | 2026-11-02 |

**What this does not prove.** No weights are downloaded and no model is executed, so this is
evidence about *our* classification and degradation and not about any particular
cross-encoder. Nothing here is timed and no figure above is a measurement. The out-of-memory
cases inject the exception's shape rather than exhausting real VRAM, which a test cannot do
reproducibly; the one case that uses the real library is a load *refusal*, not a load.

## Observed behavior — reindex under continuous query load

Not a failure mode and not a §1.9 row, but D2's acceptance scenario, logged here for the same
reason the rows above are: a promise that "re-embedding never takes queries down" is prose
until a query has actually been *inside* the rebuild. The suite is
`tests/chaos/test_reindex_under_load.py` (8 cases, `pytest -m chaos`). It drives the real
`RetrievalService` and the real `plan_reindex`/`swap` against a double that resolves the
alias on every search, the way Qdrant's server does, and the drill asserts the window was
genuinely crossed rather than hoping the scheduler crossed it.

| Scenario | Observed | Date |
|---|---|---|
| Queries running continuously across a blue/green rebuild and swap | Every observation carried exactly one generation and the *complete* id set of that generation, so no query was served a half-built collection; both generations were observed across the drill, and at least one query resolved the alias strictly between the first write into the new collection and the swap, which is what makes the run non-vacuous | 2026-10-29 |
| The same drill, counting dropped queries | Zero typed failures and more observations than the three the drill waits for after the swap: the load was served throughout rather than the loop having stalled | 2026-10-29 |
| Where the alias pointed during the rebuild | The served name resolved to the old collection at every batch boundary of the build and moved only at the swap — the mechanism behind the row above, asserted separately so a change can break one without hiding the other | 2026-10-29 |
| The eval gate rejecting the new build | No swap, no dropped query, and every query still answered from the old collection: the gate runs before the swap, so a regression is never detected by serving it | 2026-10-29 |
| A served name that resolves to nothing | Raised typed `NOT_FOUND` rather than returning an empty hit list, and rendered as a problem document with a trace id, never a generic 500 — an empty context is the failure that reaches the caller as a confident empty answer | 2026-10-29 |
| A **hybrid** query straddling the swap | **A limit, not a guarantee.** Each retrieval leg resolves the served name independently, so a swap landing between the dense and sparse legs returns one result assembled from both generations. This is the built behaviour, pinned so that it is measured rather than assumed; it bounds D2's "a query sees either the old collection or the new one" to a single leg | 2026-10-29 |

**What this does not prove.** Nothing here runs a live backend, so it is evidence about *our*
orchestration — that no code path points the alias at a collection still being filled, and
that the query path reads through the alias rather than pinning a physical name — and not
about Qdrant's own server-side behaviour under concurrent writes. No timing figure above is a
latency measurement and none backs a benchmark claim. The suite's one wall-clock constant is
a deadlock backstop so a hang fails loudly; the pacing itself is an event handshake with no
clock in it.

## Observed behavior — real-fault run

The two environmental scenarios above are also run against the operating system itself, which
is a different question: the seam-level cases prove how fasterRag responds to a stopped
backend or a full disk, while these prove that the condition the OS actually produces is the
one it responds to. A double raises the exception its author expected; a stopped container
takes its published port with it, and a full filesystem returns `ENOSPC` from a syscall a
client library has to translate first. The suite is `tests/chaos/test_real_faults.py`, run
with `pytest -m integration`, and it skips when no Docker daemon is present.

| Fault, as really produced | Observed | Date |
|---|---|---|
| `docker stop` on a live Qdrant holding an indexed point | The adapter raises a typed retryable `RETRIEVAL_FAILED` — the same code the scripted double raises, which is what TASK-0226 corrected — rendered as a 503 problem document with a trace id and never a generic 500, and `health()` reports unhealthy with a detail rather than raising through the readiness probe. The failure is bounded but **not uniformly fast**: four consecutive runs measured 44.2 ms, 5040.9 ms, 36.1 ms, 5043.9 ms, because Docker Desktop's port proxy sometimes accepts the connection and hangs instead of the kernel refusing it, in which case the bound is our own `reliability.timeouts.vector_db_ms` (5 s) rather than the OS's. What is proven is the bound, not a latency figure | 2026-08-09 |
| `docker start` on the same container | The backend answers again with no intervention and the search returns the same point id — the named volume kept the data across the stop | 2026-08-09 |
| Journal writes onto a tmpfs mounted with a hard 512k limit, filled to zero free bytes | 516,096 bytes of filler took the filesystem to `free_bytes: 0`. Starting a **new** job then failed with the OS's own `ENOSPC` (errno 28, `[Errno 28] No space left on device`) rather than silently losing the record — but **checkpointing the already-running job still succeeded**, and that asymmetry is the mechanism, not luck: `_write_atomically` renames the live record over the stale `.previous` copy before writing, freeing a file the same size as the one it is about to write, while a new job frees nothing. Removing that rename made the checkpoint fail too, which is how the mechanism was confirmed. The record stayed readable throughout, so the halt is clean and "resume from the last checkpoint" is reachable on the very disk that caused the halt; deleting the filler is the whole recovery — the journal created a new job immediately and the earlier one was still there to resume | 2026-08-09 |

**The gap this run found that the seam-level run could not.** Row 33's promise that the OS
write error becomes a typed `IngestionError` does not hold: the raw `OSError` escapes
`Journal._write_atomically` untranslated (TASK-0234). The scripted suite cannot see it
because its unwritable-directory case accepts `(IngestionError, OSError)` and so passes
either way. It is asserted **as observed** rather than as promised, so the day the fix lands
that case fails and forces the row and the assertion to move together.

**Platform note.** The disk variant runs its write inside a Linux container because the
Windows host it was executed on cannot constrain a filesystem without administrator rights —
an NTFS quota or a mounted VHD both need elevation, and a test may not demand it. The tmpfs
is a real filesystem returning a real `ENOSPC` to the real `Journal`; what is containerised
is where the write lands, not whether the failure is genuine. The same case runs unchanged on
a Linux or macOS host.
