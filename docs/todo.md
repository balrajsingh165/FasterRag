### S3 — Ingestion core

- [x] TASK-0030: Implement contextual enrichment (P2) — `core/chunking/enrichment.py` prepends a document-level context to each chunk before embedding and indexing. The parent document leads every prompt verbatim so it stays a cacheable prefix; without that, cost scales with document length times chunk count rather than chunk count alone. Calls run concurrently, since one round trip per chunk in sequence would make ingestion latency the sum of every chunk's call. **A failed enrichment is never fatal** — the chunk indexes unprefixed and carries `enrichment_failed`, because a slightly worse chunk beats a dead-lettered document, and an unflagged failure would be indistinguishable from the feature being off. `chunking.context_tokens` is interpolated into the prompt rather than hardcoded; a setting the prompt ignores silently does nothing. **Verified against the live provider** on a policies fixture: the model returned the section, region, year, and the referents the chunk's shorthand depends on, with `original_text` preserved and zero failures. 16 tests — ✅ 2026-08-04
- [x] TASK-0185: Wire enrichment into ingestion — `chunking.contextual_enrichment: true` now changes what is indexed. The process-boundary constraint resolved as documented: parsing stays in the process pool, the parsed text comes back on `ParseOutcome.document_text`, and the provider call happens on the async side after the executor returns — so parsing stays parallel and CPU-bound while an I/O wait sits on the event loop where it belongs. The parent text is carried **only when the toggle is on**, or every parsed document would double what it sends through IPC for a field nothing reads. The enrichment model is built only when the toggle is on, and a missing model leaves the flag inert rather than raising — a toggle cannot conjure a provider. **Verified against the live provider through the real pool**: two documents in, two enriched, originals preserved. 4 wiring tests on top of the 16 unit tests. `fasterrag estimate` does not yet account for the extra calls — TASK-0186 — ✅ 2026-08-04
- [x] TASK-0186: `fasterrag estimate` accounts for contextual-enrichment calls — reported as its own block rather than blended into the embedding figure, because enrichment is a generation charge on a different model at different rates and one combined number hides which knob to turn. The prompt cost is document tokens × chunk count, which is the term that makes it expensive and the term a per-chunk figure would conceal. Quoted **uncached** and the basis string says so: prompt caching is what makes enrichment affordable, but its discount depends on the provider and cache window, so a number fasterRag cannot verify would understate a real bill. An unpriced model reports `unknown`, never zero — zero reads as free. Verified on the policies corpus: 12 calls, $0.0011, against $0.0000 for local embedding. 8 tests, including one asserting the estimator loads no tokenizer — a preflight that pulls a multi-gigabyte model is not a cheap preflight — ✅ 2026-08-04
- [x] TASK-0113: Implement the pooling half of late chunking in the embedding pool (embed the document in one long-context pass, then pool token representations over each chunk's span); the boundary half and the `late_pooling` marker already ship — ✅ 2026-08-05 (`core/chunking/pooling.py` runs the model over the whole document and mean-pools the token states inside each chunk's span. Documents beyond the model's context are processed in overlapping windows, each token taking its state from the window that gave it the most surrounding context, so a 1,440-token document on a 512-token model pools correctly instead of being truncated. A hosted provider cannot supply token-level output, so the pool falls back to ordinary embedding rather than failing — `late` is then no better than `recursive`, not broken. The document text reaches the embedding stage as one shared string object attached on the parent side, so it costs a pointer per chunk rather than a copy: measured 1 distinct object across a document's chunks. **A corpus-corrupting hazard was found while wiring it** — pooling regroups a batch by document, so writing the original batch order against pooled vectors pairs every chunk with another chunk's vector, producing a corpus that indexes cleanly and retrieves nonsense; the write now follows the regrouped order and a test fails if that is reverted)
