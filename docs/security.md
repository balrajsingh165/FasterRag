# security.md — Secrets, Auth, Multi-Tenancy, Supply Chain

## 1. Secrets handling and `.env` policy

- **`config.yaml` never contains secrets.** It drives all behavior; credentials live ONLY in `.env` (or the process environment). Config references secrets exclusively by env-var name: `api_key_env: OPENAI_API_KEY`.
- `.env` is git-ignored; `.env.example` documents every variable with placeholder values.
- Startup validation confirms every referenced env var exists — a missing one is a fatal `ConfigError` that names the variable but **never logs its value**.
- Secret values never appear in logs, traces, problem responses, or the dashboard. Provider keys are redacted to `sk-***` in any diagnostic output.
- Provisioner-generated secrets (Langfuse `NEXTAUTH_SECRET`/`SALT`/`ENCRYPTION_KEY`) are written once to `.env` and never regenerated on re-provision ([observability.md](observability.md)).

### `.env.example` inventory (beta)

| Variable | Used by | Notes |
|---|---|---|
| `FASTERRAG_API_KEY` | API auth (`security.auth`) | Key material for the control plane. |
| `QDRANT_API_KEY` | Qdrant adapter | Sent by the client; the server enforces it via `QDRANT__SERVICE__API_KEY`. |
| `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `COHERE_API_KEY` | Embedding/LLM adapters | Only those actually referenced by config are required. |
| `LANGFUSE_INIT_*`, `NEXTAUTH_SECRET`, `SALT`, `ENCRYPTION_KEY` | Langfuse provisioning | Generated by the provisioner if absent. |

## 2. API authentication

- `security.auth: true` requires `Authorization: Bearer <key>` on every control-plane endpoint (API); the CLI and library read the same key from the environment when pointed at a secured server.

**Key format.** Keys live in the variable named by `security.api_key_env` (default `FASTERRAG_API_KEY`), never in `config.yaml`. Keys are separated by `;` and scopes within a key by `,`:

```
FASTERRAG_API_KEY=secret-one:query,ingest:acme; secret-two:admin
```

Each entry is `<secret>[:<scopes>[:<tenant>]]`. A bare secret with no scopes gets all four — the single-operator case. The two separators differ deliberately: with a comma for both, `a:query,ingest` reads equally as one key with two scopes or as two keys, and the parser would have to guess.

**An omitted scope field is not an empty one, and `*` is how you ask for all four in writing (TASK-0327, 2026-11-08).** The decision the grammar now records:

| Entry | Scopes | Why |
|---|---|---|
| `k` | all four | The single-operator case. A field that was never written cannot have been written wrong. |
| `k:*` | all four | The same grant, stated. |
| `k:*:acme` | all four, bound to `acme` | The only way to name a tenant without enumerating scopes. |
| `k:query,ingest:acme` | as named | The normal case. |
| `k:`, `k::acme`, `k: , `, `k:::` | **refused at startup** | `ConfigError` naming the entry number and the `*` spelling. |

Until 2026-11-08 the last row loaded as a key with **all four scopes, `admin` included**: `_parse_scopes` ended in `frozenset(scopes or ALL_SCOPES)`, so a blank field fell through to the bare-secret default. The aggravating part was the grammar itself — `<secret>[:<scopes>[:<tenant>]]` gave an operator who wanted "default scopes, this tenant" no spelling but `k::acme`, so the natural thing to write was the one that silently produced a full admin credential. Three fields, three ways to be wrong, and this one failed **toward** privilege while `required_scope` fails **away** from it on the same kind of omission.

Failing it closed alone would only have moved the problem: the operator writing `k::acme` would have gotten a hard startup failure with no documented replacement. So the refusal ships with the replacement — `*` — and the refusal message names it. Mixing is harmless and allowed (`*,query` is all four), since the token is a union, not an override.

**This does not change what an omitted *tenant* means** (`k:query:` and `k:query` are both operator keys free to act for any tenant, §5.3). That is the same shape one field over and is a separate, deliberate grant with its own open decision (TASK-0295); fixing it is an incompatible change to every key file, which `*` is not. If that decision later lands on an explicit any-tenant marker, `*` is the token already in this grammar — note that `k:query:*` today means the literal tenant id `*`, not "any tenant".

**Three parser edges, recorded rather than rediscovered.** A trailing colon after the scopes (`k:query:`) is an empty tenant and reads as no tenant. A *third* colon is not a fourth field: `k:query:acme:extra` yields the tenant `acme:extra`, which then matches no header and fails closed. An entry with an empty secret (`:query`) is refused, naming its 1-based position.

**Enforced as ASGI middleware, not a per-route dependency.** A dependency has to be attached to each route, so forgetting one leaves an endpoint silently public. Middleware sees every request, so a newly mounted router is protected by default and a gap must be introduced deliberately. For the same reason an **unmapped path requires `admin`** rather than defaulting to open.

**`/healthz`, `/readyz`, and `/openapi.json` stay unauthenticated.** A load balancer probes them without credentials, and a health check that needs a key reports the service as down whenever the key is wrong — turning a credential mistake into an outage. Neither reveals corpus content. **`/metrics` is not public**: it exposes per-endpoint volumes and costs, so it requires `admin` like any other surface.

Auth runs **before** metrics and correlation-id middleware, so a rejected request cannot inflate per-endpoint counters or leave a trace id in the logs of an endpoint it never reached.

Key comparison uses `secrets.compare_digest` against every configured key with no early exit, so response timing does not reveal how much of a guess was correct.

Enabling auth with no usable key **refuses to start**. Starting would refuse every request afterwards, which reads as a broken deployment rather than a configuration mistake.
- **Keys carry scopes**: `ingest`, `query`, `collections`, `admin`. Admin endpoints (provisioning, export/import, collection delete) require `admin`.
- **Rate limiting is on by default once auth is enabled** (`security.rate_limit_per_minute`, per key), returning `429` + `Retry-After`. Keyed per API key, not per IP — a limit keyed on something the caller chooses is not a limit.

**Where the window is counted is a deployment choice** (`security.rate_limit_backend`, TASK-0216).

| Backend | Window | Correct for |
|---|---|---|
| `memory` (default) | One dictionary per process | A single process. With N Gunicorn workers or N replicas the effective ceiling is `rate_limit_per_minute × N`. |
| `redis` | One fixed window per API key, counted in Redis (`security.rate_limit_redis_url`) | Any multi-worker or multi-replica deployment — including the Gunicorn topology [deployment.md](deployment.md) documents as production. |

`memory` remains the default because it is correct for a single process and a default that opens a network connection is a default that can fail to start. An operator running more than one worker has to choose `redis` deliberately; nothing detects the mismatch for them, which is the remaining sharp edge here.

**How the shared window works.** The key is `fasterrag:ratelimit:<fingerprint>:<window index>`, so a new minute is a new key rather than a counter something has to reset — no replica can disagree about when the window began and no sweep is needed. The counter and its expiry (`INCR` + `EXPIRE`) are issued inside one `MULTI`/`EXEC` transaction; issued separately, a process dying between the two leaves a counter with no expiry, and an immortal counter sitting at its ceiling refuses that key forever. The `<fingerprint>` is a SHA-256 digest of the API key, never the key: Redis is shared and frequently co-tenanted, and a credential written there in plain text is a disclosure wearing a counter's clothes. The window index comes from each host's wall clock, so hosts with skewed clocks step between windows at slightly different moments and a caller may receive part of an extra window's allowance around a boundary; the alternative, asking Redis for its own `TIME`, costs a second round trip on every authenticated request. Run NTP.

**A Redis outage fails open: the request is served and the limit is not enforced for it.** Failing closed was the alternative and it was rejected. By the time the limiter runs, the request has already been authenticated and scope-checked — the limiter is an abuse control, not an authorization control, so letting one through degrades throttling rather than access. Failing closed would convert a Redis outage into a total control-plane outage for every authenticated caller, including `/metrics` and the admin endpoints an operator needs during exactly that incident, and it is the same posture FMEA row 23 already takes for this same dependency (a cache failure degrades to cache-off, never to a query failure). The trade is explicit: during a Redis outage a hostile key is unthrottled, which is why this is written down rather than discovered. **The failure is never swallowed** — each occurrence logs a `WARNING` from `fasterrag.core.rate_limit` carrying the request's `trace_id`, so the degradation is visible in the same stream as everything else the request did.

**Now run against a live server, and narrowed further (TASK-0290).** As of **2026-11-11** the `redis` backend *has* run against a real Redis server: `tests/integration/test_redis_rate_limit_server.py` drives `RedisRateLimiter` against `redis:7.4.2-alpine` (from `deploy/compose.test-backends.yml`) over a real socket, each case in its own UUID namespace so it is safe to point at a server that is not empty. All nine cases pass. One of them drives the same sequence of decisions through both the real server and `FakeAsyncRedis` and asserts the two decision lists are identical: **no divergence was found**, so the fakeredis results below stand rather than being superseded. `security.rate_limit_backend: redis` remains unproven *in production*, for the reasons in the next paragraph. What changed on 2026-11-04 is the size of the gap. `tests/integration/test_redis_rate_limit.py` drives the shipped `RedisRateLimiter` against `fakeredis` (a `dev`-extra test dependency, never a runtime one), which speaks the Redis protocol in-process behind the **real** `redis.asyncio.Redis` client — so the client library, the command encoding, the `MULTI`/`EXEC` round trip and the reply parsing are the shipped ones, and `INCR`, `EXPIRE` and the eviction of a lapsed key are performed by a server implementation rather than by this repository's idea of one. Read back out of that server, five things are now observed rather than assumed: the ceiling admits N and refuses N+1; the counter carries the TTL that was sent and the server itself drops the key when it lapses, so the immortal-counter failure is ruled out; the next window is a new key, so a refusal is not permanent; two limiter instances over one backend share one ceiling while still counting two callers apart; and the only key written is `fasterrag:ratelimit:<sha256 digest>:<window index>`, with the API key in none of it.

**What that still does not prove.** The live run above covers one Redis release on one machine, so beyond it fakeredis remains an emulation and any divergence in the version an operator actually runs — eviction under `maxmemory`, cluster-mode key routing, `EXPIRE` precision, `MULTI`/`EXEC` semantics on a replica — remains untested. Nothing crosses a socket, so connection timeouts, resets, partitions, failover and pool exhaustion are untested, and the fail-open path above is still reachable in tests only by injecting an error directly. And the two instances that share a ceiling share a Python object inside one interpreter; genuine cross-process, cross-replica sharing — the reason the backend exists at all — rests on the protocol emulation being faithful, not on an observation. Treat the backend as correct in which commands it issues and in what those commands do, and unvalidated against a production Redis topology, until an integration test against a real server lands (TASK-0290).
- Failed auth returns RFC 9457 problems (`AUTH_MISSING`/`AUTH_INVALID`/`AUTH_SCOPE`) with no information about whether a key exists.
- TLS terminates at a reverse proxy in front of the API ([deployment.md](deployment.md)); plain HTTP is acceptable only on loopback/dev.

## 3. Multi-tenancy isolation

- `security.multi_tenancy: true` scopes collections and API keys to tenants; the tenant id arrives via `security.tenant_header` (default `X-Tenant-ID`) and must match the key's tenant.
- **Isolation is enforced at the service layer** (the only writer of state) for every collection operation, cache entry, trace, job, and metric; cross-tenant access to those is `TENANT_FORBIDDEN` regardless of endpoint. **Retrieval is the exception and is opt-in** — see "What retrieval actually enforces" below.

**Shipped so far** (TASK-0179): the tenant is resolved once, in `AuthMiddleware`, from the key's own tenant and the request header, and placed on the request scope — one place decides who the caller is, so a second reader cannot disagree with the first. Three rules:

- A key **bound to a tenant** may act only as that tenant.
- A key with **no tenant** is an operator credential and may act as any tenant, but must still name one. An unstated tenant would silently read and write the untenanted namespace while multi-tenancy is supposedly on.
- A refusal **never echoes the key's own tenant**, or a caller could enumerate tenants by trying values and reading the error.

**Semantic-cache isolation is the part that matters most, and it is enforced on the entry rather than the key.** Lookup compares the query vector against *every* stored entry, so a key prefix alone would not help — the scan ignores keys. Each entry carries its owning tenant and a mismatch is skipped, so a sufficiently similar question from one tenant can never return another's answer at a cache hit's latency with no error anywhere. The tenant is also part of the key, because otherwise two tenants asking the same question collide and the second write silently overwrites the first.

**Collections are scoped by name, not by a filter — in the two routers that do it.** A vector database has no notion of our tenants, so collection isolation cannot be a field check — a tenant's collections carry a `<tenant>__` prefix and a tenant may only address names carrying its own. **`/v1/collections` and `/v1/admin` apply this; the ingest and query paths do not** (TASK-0339, below). That makes isolation a property of the identifier: a missing filter fails open, a name that does not resolve fails closed. The prefix never appears in a response — a tenant that created `docs` sees `docs`. A tenant id may not itself contain the separator, or `acme__x` could address `acme`'s collection `x`; ids are validated and refused with `TENANT_FORBIDDEN`.

**Traces and metrics are tagged too.** A trace records the query text and every retrieved chunk, so `GET /v1/traces/{id}`, `GET /v1/traces`, and `POST /v1/replay` all report another tenant's trace as **absent** rather than forbidden — a distinct error would confirm the id is real, and trace ids are guessable from a caller's own listing. The same reasoning applies to `GET /v1/collections/{name}`. Metric series carry the tenant resolved by the middleware, not one re-read from the header, so an unauthenticated request cannot label its own series.

**Ingestion jobs are scoped too.** A job record carries the source paths of the corpus it ingested, and job ids sort chronologically — so a caller holding one of their own can guess at neighbours. Another tenant's job therefore raises the same `NOT_FOUND` an unknown id does, with the same message. The tenant is recorded when the job is *created*: without that every job would be written untenanted and scoping the read path would refuse a tenant access to the job it had just started, presenting as an outage rather than as isolation.

With this, these tenant-visible surfaces are scoped: the semantic cache, collections, traces, replay, metrics, and ingestion jobs. **Retrieval itself is not among them by default** — §3's closing subsection, "What retrieval actually enforces", says exactly what it does and does not do.

**A tenant id may not contain `__` nor end with `_`.** Both rules exist for the same reason and neither is redundant: collection isolation is carried by the name (`<tenant>__<name>`), so an id that can reconstruct the separator against a caller-supplied collection name breaks it. An id *ending* in `_` did exactly that — `scoped_name("_b", "a")` and `scoped_name("b", "a_")` both produced `a___b`, giving two tenants one backend collection with read *and* write, and `visible_to` returning true for both. Fixed 2026-08-06 (TASK-0211); with both rules the encoding is injective.

`POST /v1/replay` is scoped for the same reason the read endpoints are, and it is the easier one to overlook: replay re-executes the stored question and returns a diff, so an unscoped lookup discloses another tenant's query and retrieved chunks through a write-shaped endpoint rather than a read-shaped one. It looked its trace up unscoped until 2026-08-06 (TASK-0194).
- Semantic-cache entries are tenant-scoped — a cache hit can never leak another tenant's answer.
- Per-tenant token budgets (D9, `cost.per_tenant_token_budget`) are **enforced** (TASK-0242 ✅) over a rolling 24-hour window, per tenant, checked before the provider is called. **The counter is in-process**, exactly like the per-key rate limiter's default `memory` backend: N replicas grant N times the configured budget, and for a spend cap that error permits more than was asked for rather than less. Size the value accordingly, or run one replica, until a shared counter lands (TASK-0426) — the limiter has one (`security.rate_limit_backend: redis`); the budget does not.

### What retrieval actually enforces (corrected 2026-11-09, TASK-0339)

**Until this entry, this section claimed retrieval was scoped and it was not.** The claim above read "every tenant-visible surface is scoped: queries, …"; `services/querying.py` contained the string `tenant` zero times. Two tenancy models had grown side by side and neither covered the query path:

- **Collection-name scoping** (`services/tenancy.scoped_name`) is applied by `/v1/collections` and `/v1/admin` and **by nothing else**. The ingest path and the query path both address the raw name, so a collection created through the API as `acme__docs` is ingested into and queried as `docs`.
- **A payload tag.** `workers/indexer.chunk_payload` writes `tenant` into every vector payload when the job carries one, and until TASK-0339 nothing ever filtered on it.

Executed, not inferred. `tests/unit/api/test_query_tenancy.py` drives the real router, the real `AuthMiddleware` and an in-memory adapter holding one chunk per tenant. With `auth` and `multi_tenancy` on, a valid `acme` key presenting `X-Tenant-ID: acme` observed all three of:

| Request | Observed |
|---|---|
| `POST /v1/retrieve {"collection": "globex__docs"}` | `200`, `globex`'s chunk and its text |
| `POST /v1/retrieve` with no collection | `200`, **both** tenants' chunks from the one shared collection |
| `POST /v1/query` with no collection | `200`, the other tenant's chunk in the answer context **and in `citations`** |

In every case the filter each retrieval leg received was `None`. `/v1/retrieve` took no tenant dependency at all; `/v1/query` took one and spent it only on the semantic-cache key, the cost governor and the trace.

**`security.tenant_scoped_retrieval` (default `false`) is what enforces it now.** With the flag on, `RetrievalService` injects `{"tenant": <caller's tenant>}` into the filter it pushes down, and a retrieval with no tenant is refused with `TENANT_FORBIDDEN`. Four properties, each pinned by a test:

- **Below the caller, not beside it.** The injection happens in `services/querying.py`, after `validate_filter`, at the single point where one filter object is handed to *both* legs — so a caller-supplied `filters` cannot widen it and no future change can scope one leg and forget the other. The module's own rule, that a filter applied to one leg returns an inconsistent candidate set, now carries the tenant too.
- **A body naming the tenant field is refused, never merged.** `{"tenant": "globex"}`, `{"tenant": {"$in": [...]}}` and `{"tenant": {"$ne": "acme"}}` all return `403 TENANT_FORBIDDEN` before either leg runs. Silently overriding would be equally safe for the result set and would let a caller probe isolation without ever being told it exists.
- **The caller cannot plant the field either.** `workers/indexer.chunk_payload` merged the job's `metadata` *after* writing the tenant, so an ingest carrying `metadata={"tenant": "globex"}` overwrote the tenant the credential set and dropped its chunks into another tenant's filtered view. The credential now wins: the tenant is written last. A job with no tenant is unchanged, so an untenanted deployment that uses `tenant` as an ordinary metadata label keeps it.
- **The field has one spelling.** `core/tenancy.TENANT_PAYLOAD_KEY` (re-exported by `services/tenancy`) is now what the indexer writes and what the filter reads; they named the same string independently before, and a writer and a reader that disagree make a filter that silently matches nothing.

With the flag on, the three rows above become: no chunks, the caller's chunk only, and an answer citing the caller's chunk only.

**Which collections the flag is reachable for (corrected 2026-11-11, TASK-0385).** This section previously set out the pre-enable checklist below without saying that its step 1 refuses some corpora outright, so an operator could read all of it and still not learn that the command would not run on their corpus. What the flag actually needs is a **tagged** corpus, not a single-tenant one — it filters on the payload field, and does not care which collection holds a point:

| The collection holds | With the flag on | Remedy |
|---|---|---|
| Every point tagged, one tenant | Correct | None needed |
| Every point tagged, **several** tenants | Correct — each tenant's filter returns its own rows and no other's. A mixed collection is **not** a leak under the flag | None needed |
| One tenant's points plus untagged ones | The untagged subset is invisible to everyone — fail-closed, silent | `index backfill-tenant <c> --tenant <id>`; naming the tenant *is* the statement of ownership |
| **Two** tenants' points plus untagged ones | The untagged subset is invisible to everyone | Refused with `CONFLICT` until somebody states who owns the residue — see below |

The last row is the shared unscoped collection the executed proof above found answering for everybody, so it is the case a real deployment is most likely to be in. **Nothing in the data says which tenant an untagged point belongs to**: it was written before `multi_tenancy` existed, by a path that had no tenant to record. The system cannot derive the answer, and a tool that picks one is re-committing the defect `chunk_payload` was fixed for. Two commands exist so that the operator, who can know, states it instead:

- `fasterrag index tenants <collection> --untagged <path>` writes the untagged points to a JSONL file **grouped by document** — `document_id`, `source_uri`, chunk count — because a document is the granularity an operator can actually recognise. Read-only, and it is the evidence the next command's assertion should rest on. Chunks carrying no `document_id` group into a single row with an empty id: they cannot be attributed per document at all.
- `fasterrag index backfill-tenant <collection> --tenant <id> --assume-untagged` tags **only** the untagged points, leaving every existing tag alone, and says in its report that the ownership was asserted rather than derived (`assumed: true` in `--json`). It is the right flag for a mixed collection; `--overwrite`, which claims every point including the other tenant's, is not, and passing both is refused as `VALIDATION_FAILED` because they assert different things. Both are dry-run-by-default like every other backfill run.

If the residue is **not** all one tenant's, neither flag is honest and there is no command for it: the only correct procedure is to attribute document by document, which nothing here automates (TASK-0385 follow-up in [todo.md](todo.md)). Leaving the residue untagged is a safe choice — invisible to every tenant, not visible to the wrong one — and the blackout it causes is exactly what `index tenants` prints.

**A backfilled collection does not stay backfilled if anything ingests without a tenant.** `IngestionService` writes the tag only when the job carries a tenant, and the CLI's `fasterrag ingest` builds one with no credential, exactly as the facade does for retrieval in step 4 below. So a CLI ingest into a collection served under the flag adds fresh untagged — therefore invisible — chunks, and re-creates the residue the backfill just cleared. Re-run `index tenants` after any such ingest; the backfill is a fixpoint over a corpus that stops changing underneath it, not a one-time migration. Found while writing this section, by reading the two call sites rather than by running them.

**Why there is no "split the collection" command.** The sketch TASK-0385 carried was export → partition by payload → import under `<tenant>__<name>` names. It was examined and deliberately not built, for three reasons:

1. **It is not what the shipped model needs.** `tenant_scoped_retrieval` is a filter on a payload field. Moving a tenant's points into their own collection does not make the filter work; a correct tag does, and a correct tag is enough on its own.
2. **It would move data out of reach.** The ingest and query paths address the **raw** collection name — they do not apply `scoped_name` (TASK-0381). Points relocated into `acme__docs` would stop being addressable by the queries the split was meant to fix, so the procedure would read as a repair and present as an outage. A split only becomes correct once the maintainer decision below is made in favour of name scoping everywhere.
3. **The archive is the wrong vehicle for it.** `export_archive` has no filter: it writes every point in the collection, so partitioning would mean hand-editing `chunks.jsonl`/`vectors.jsonl` and regenerating `checksums.sha256` and the manifest counts, all of which the reader verifies before it writes anything — and since TASK-0329 that list includes the manifest's own digest, so a hand-edited archive must be re-checksummed whole before any reader will accept it. Two further obstacles sit behind that one: the manifest records the **tenant-scoped** collection name, so an archive exported by `acme` over REST says `acme__docs` and re-importing it as that tenant lands in `acme__acme__docs` (TASK-0340, open); and import is not streamed (TASK-0293), so the round trip has to fit in memory on precisely the collections this problem is about.

**Why it is off by default, and what to do before turning it on.** The flag changes what an already-ingested corpus answers, so it cannot be a default:

0. **See what is untagged, before writing anything.** `fasterrag index tenants` counts every collection's points by `tenant` tag; naming one collection counts only that one. Its `untagged` number is the size of the blackout enabling the flag would cause, and the `tagged` breakdown is how a collection holding *two* tenants' chunks — which the shared unscoped collection above does — becomes visible before a backfill is pointed at it. Read-only, and it walks the same `iterate_points` traversal the export path uses.
1. **Backfill the tag.** Chunks indexed before `multi_tenancy` was enabled carry no `tenant` payload field at all, and an absent field never matches a filter. Enabling the flag over an unbackfilled collection returns **empty results, not wrong ones** — fail-closed, but silent, which is harder to diagnose than an error. `fasterrag index backfill-tenant <collection> --tenant <id>` writes it through the adapters' metadata-only `PointUpdate` path (TASK-0377, 2026-11-11). Four properties it is built around:
   - **It dry-runs by default.** Without `--apply` it audits and prints the counts, writing nothing; the printed report — scanned, untagged, already tagged, other tenants, would-tag — is the thing to read before enabling the flag.
   - **Re-running is safe and is how a dead run resumes.** A point is selected only when it carries no tag, which is the negation of the state the write produces, so a completed run is a fixpoint and a run killed halfway is finished by running it again. There is no checkpoint file, because a cursor that can be stale or corrupt is a second thing to get right. Each flushed batch prints its cumulative count, so a killed run also leaves a record of how far it got.
   - **It refuses to relabel.** A collection that already holds points tagged for a different tenant is refused with `CONFLICT`, naming the tenants found: its untagged points cannot be attributed to either, and assigning them all to one would hand that tenant another's data — the defect fixed in `chunk_payload` above, committed a second time. Two flags are the explicit answers, and the refusal names both: `--overwrite` relabels *every* point in the collection, and `--assume-untagged` tags only the untagged residue. See "Which collections the flag is reachable for" above for which one a mixed collection wants, and for the inventory to read before asserting either.
   - **The update carries the tag alone.** `update` merges metadata, so restating any other field would let a backfill overwrite a payload it only meant to extend.
2. **Index the field in the backend.** Nothing in this repository creates a payload index; `CollectionSpec` has no field for one (TASK-0378, open). Without it, every query pays an unindexed filter on both legs, which on a large collection is the worst case rather than the cheap one. Create it with the backend's own tooling (Qdrant: a tenant-optimised payload index on `tenant`). **Do this after the backfill, not before**: an index created first has to absorb one payload update per point in the corpus, where one created afterwards is built once over final data, and nothing queries the field until the flag itself is turned on anyway.
3. **Clear the semantic cache.** The cache is looked up *before* retrieval and its entries are tenant-tagged, so it cannot serve one tenant another's answer — but an entry written **before** the flag was enabled was produced by a cross-tenant retrieval and is tagged with the tenant that asked. Turning the flag on does not re-derive it, so a stale hit can still carry another tenant's content to the tenant it was already leaked to. The embedding cache is keyed on the query text alone and is unaffected: an embedding is derived from the caller's own input and carries no corpus content.
4. **Expect in-process callers to be refused.** The Python facade and the CLI build retrieval with no credential, so with the flag on they raise `TENANT_FORBIDDEN`. That is the safe direction and it is loud, but it means the flag is API-only until the facade grows a tenant argument. `POST /v1/replay` **is** wired: it now retrieves as the tenant whose trace it is replaying, which also means its spend is charged to that tenant's budget rather than to the untenanted bucket.

The flag requires `security.auth` **and** `security.multi_tenancy`; combining it with either off is refused at configuration load, because the tenant it filters on is resolved by the authentication middleware and without one every retrieval would be refused at runtime instead.

**What is still open.** The flag is the filter half of the choice; it does not make the ingest and query paths use `scoped_name`, so the two tenancy models still coexist and a tenant's chunks still share one physical collection. Which model the project commits to — name scoping everywhere, or one collection with this filter — remains a maintainer decision, and until it is made a deployment that uses `/v1/collections` to create `acme__docs` is still ingesting into `docs`.

## 4. Vector DB security (Qdrant reference)

- Authenticated access via **`QDRANT__SERVICE__API_KEY`** on the server; the client key comes from `.env` (`vector_db.api_key_env`).
- Qdrant ports (6333, 6334) stay on private networks; remote mode should ride TLS or a private link ([deployment.md](deployment.md)).
- Named-volume persistence (mandatory on Windows/WSL) keeps data off ephemeral layers.

## 5. Input hardening

- Input size limits on all endpoints: `security.max_request_mb` (bodies) and `ingestion.max_document_mb` (documents); oversize → `413 PAYLOAD_TOO_LARGE`.
- Uploaded documents are parsed with hardened parsers in worker processes (crash containment: a parser crash dead-letters the document, never kills the API).
- Metadata filter expressions are validated against the collection's schema — no raw query pass-through to backends.

### 5.1 Ingestion sources are an authorization boundary (audit, 2026-11-03)

`POST /v1/ingest` accepts three source types and two of them name something on the
**server's** side of the trust boundary. Both were unconstrained until this audit; both are
now refused by default, and each refusal is mutation-tested in both directions.

**`type: "path"` — arbitrary server-side file read.** The value named any file the process
could open, and the parsed content came back to the caller through an ordinary query. A key
holding only the `ingest` scope could therefore read `.env`, `config.yaml`, an SSH key, or
another tenant's archive. `ingestion.allowed_source_roots` now confines it. Paths are
`resolve()`d before comparison, so `..` is collapsed and a symlink planted inside a root
cannot point out of it. An empty list means unconfined, and unconfined is **refused outright
once `security.auth` is on** — forgetting the setting breaks a served deployment loudly, at
the request, naming the setting, rather than exposing it quietly. With auth off the
deployment is single-operator (the CLI case) and local paths work as before.

**`type: "url"` — SSRF, with exfiltration.** The fetcher followed redirects with no scheme
check and no address check, so a caller could reach cloud instance metadata
(`169.254.169.254` — IAM credentials), loopback services an operator believes are
unreachable (Qdrant 6333, Redis 6379, `/metrics`), and anything else inside the perimeter —
and then read the response body back out with a query. Now: only `http`/`https`, and every
host is resolved and refused unless **every** address it answers with is global and
non-multicast. Redirects are followed by hand, at most five, with the same guard applied to
each hop — `follow_redirects=True` would have sent later hops unchecked, which makes any
first-URL-only check decorative.

**DNS rebinding is closed (follow-up, 2026-11-04, TASK-0294).** The guard used to resolve
the host and then hand the *name* back to the connector, which resolved it a second time —
so a record with a near-zero TTL could answer public on the check and private on the
connection. The connection is now addressed to the literal that was checked: `_guard_url`
returns the verified address, the request URL is rewritten to it, and the hop is dialled at
that address. There is no second resolution left to poison.

Pinning an address must not cost anything else, so two things ride along. The original
`Host` header is sent explicitly, keeping virtual hosting intact. The real hostname travels
as httpx's `sni_hostname` request extension, which httpcore passes to `start_tls` as
`server_hostname` — that is both the SNI sent and the name the certificate chain is verified
against, so **TLS verification still checks the hostname, not the IP**. Connection keepalive
is also disabled for these fetches: httpcore pools by origin, and after pinning an origin is
`(scheme, IP, port)`, so two hosts sharing an address would otherwise share a TLS session
established and verified for whichever came first.

What is proven: unit tests assert that the address dialled is the first answer of a resolver
that changes its answer, that the resolver is consulted exactly once, that `Host` and
`sni_hostname` survive, that an IPv6 answer is dialled as a bracketed literal, and that a
relative `Location` is joined against the *name* rather than the pinned URL. What is not
proven here: no test completes a real TLS handshake against a pinned address — the
certificate-verification claim rests on reading httpcore's `_connect`, not on a live
handshake (TASK-0294 note). An integration test against a real server would settle it.

### 5.2 Archive import is bounded (audit, 2026-11-03)

`.fragx` import reads members into memory before verifying checksums, and gzip reaches
expansion ratios past 1000:1, so a small archive could exhaust memory. Two ceilings now
apply: `MAXIMUM_MEMBER_BYTES` (1 GiB) per member, refused on the header, and
`MAXIMUM_TOTAL_BYTES` (4 GiB) across the archive, which is what catches many members that
are individually legal. Tar member names were already validated against traversal.

**Both sides now stream (TASK-0293, 2026-11-04).** `open_archive` copies each member into a private 0700 staging directory in 256 KiB blocks, hashing as it lands and charging each block against the running budget, so peak memory is flat in archive size — measured 1.55 MB for an 18 MB archive.

**The first version of this guard was itself a memory bomb.** Spending the budget with a single `read(remaining + 1)` asked the allocator for the entire remaining 4 GiB on the first member: reading an 18 MB archive peaked at 4.33 GB. A ceiling expressed as one allocation is not a ceiling. The budget is now spent block by block, so a breach is caught on the block that crosses the line.

**One guarantee did change, and it is a real trade.** “Nothing is written before verification” now means nothing is written *to the target collection*: unauthenticated archive bytes do land on local disk first, because hashing them without holding them requires it. They land in a private temp directory, bounded by the same 4 GiB budget, refused on any member that is not a plain file at the archive root — the traversal check that was previously belt-and-braces is now what keeps members inside that directory — and removed on every failure path. An import therefore needs free temp space for the uncompressed archive, and a full disk becomes a refusal rather than a silent partial import.

### 5.3 An unbound key is now announced

A key entry is `<secret>[:<scopes>[:<tenant>]]`, so omitting the third field yields
`tenant=None`, which §3 defines as an operator credential free to act for any tenant. That
is deliberate, but it means the broader capability is what you get by leaving a field off.
Startup now logs a `WARNING` naming each unbound key — by its positional name, never its
secret — whenever `security.multi_tenancy` is on. The underlying grant is unchanged;
requiring an explicit marker instead would break every existing key file (TASK-0295).

### 5.4 Still open after this audit

- Prompt injection through retrieved content is inherent to RAG and is bounded by the P1–P4
  call-site contracts, not eliminated. The library never executes model output.

Closed since: the admin archive paths (TASK-0296, §5.6) and DNS rebinding (TASK-0294, §5.1),
both on 2026-11-04.

### 5.5 Checked and sound

Recorded so a future audit need not re-derive them: API keys compare with
`secrets.compare_digest` and the loop does not return early, so timing cannot reveal which
key matched; `required_scope` fails **closed** on an unmapped path, making a forgotten
router a 403 rather than an open endpoint; the unhandled-exception handler returns a generic
problem document and keeps the traceback in logs behind a trace id; and there is no
`pickle`, `eval`/`exec`, `yaml.load`, `shell=True`, or disabled TLS verification anywhere in
`src/`.

### 5.6 Admin archive paths are confined (follow-up, 2026-11-04)

`POST /v1/admin/export` took the file it writes from the request body and
`POST /v1/admin/import` took the file it reads the same way. An `admin`-scoped caller could
therefore write over `config.yaml`, drop a file into a web root, or read any archive on the
host. The `admin` scope is trusted to drop collections and drive provisioning; in a
tenant-operator deployment that is not the same as filesystem access (TASK-0296).

`security.allowed_archive_roots` now confines both, with exactly the rule §5.1 applies to
ingestion paths: the path is `resolve()`d before comparison, so `..` is collapsed and a
symlink planted inside a root cannot point out of it; an empty list means unconfined, and
unconfined is **refused outright once `security.auth` is on**, so forgetting the setting
breaks a served deployment loudly rather than exposing it quietly. With auth off the
deployment is single-operator and `fasterrag export` keeps working as before. Refusals are
`422 VALIDATION_FAILED` problem documents naming the setting.

**One list, not two.** Export writes and import reads the same artifact in the same
directory — the round trip is the normal case — so two lists would be set identically by
every operator and could only ever diverge by mistake. The asymmetry that would justify
splitting them (writing is more dangerous than reading) is not an asymmetry in *where* the
archives live.

The setting sits under `security` rather than beside a feature section because it bounds
what a credential may reach on the host, which is what the rest of that section decides;
`ingestion.allowed_source_roots` sits under `ingestion` only because that section exists.

### 5.7 Closed by default at the socket, and three smaller holes (audit, 2026-11-11)

An independent audit found the service **open by default twice over**: `security.auth` defaults to `false` and `app.host` defaulted to `0.0.0.0`. Either alone is defensible; together a fresh `fasterrag serve` accepted unauthenticated requests from every machine that could reach it, and with auth off the source-path guard in §5.1 is deliberately permissive, so such a caller could ingest any file the process could read and query it back. Four changes (TASK-0432, TASK-0433):

- **`app.host` defaults to `127.0.0.1`.** The container image passes `--host 0.0.0.0` explicitly and compose publishes on loopback, so neither changed. `fasterrag serve` prints a warning when it binds a non-loopback address with auth off. It is a warning rather than a refusal because a reverse proxy terminating authentication in front of the API is a legitimate deployment; making it a refusal behind an explicit opt-in is recorded in TASK-0460.
- **`POST /v1/estimate` applies the §5.1 path guard.** An estimate parses the files it is given, so unguarded it reported the existence, size and token count of any server path whatever `ingestion.allowed_source_roots` said. It also runs off the event loop now.
- **Keys are compared as bytes.** `secrets.compare_digest` raises `TypeError` on a `str` holding a non-ASCII character and the `Authorization` header is latin-1 decoded, so one such byte in a bearer token turned a 401 into an unhandled 500 for an unauthenticated caller.
- **The semantic cache is scoped by collection, filters and `top_k`** as well as by tenant. Its lookup ran before retrieval and matched on the query vector and tenant alone. A metadata filter is how an access-control restriction is expressed in a query, so an answer produced under one filter could be served to a request carrying another.

**Still open from the same audit**, each with an entry in [todo.md](todo.md): retrieved text reaches the prompt unescaped (TASK-0446); a key with no tenant may act for any tenant, `multi_tenancy` without `auth` is accepted silently, and the `.env.example` placeholder is accepted as a live key (TASK-0460); tenant scoping of the ingest and query paths remains the opt-in described in §3 (TASK-0339, TASK-0381).

### 5.8 Hostile documents cost one document (2026-11-12)

A document is attacker-controlled input whenever the corpus is, so each of these is refused as one dead-lettered document with a reason code while the rest of the job is indexed.

- **Decompression bombs (TASK-0459).** A DOCX is a zip archive and `python-docx` inflated every member it was handed, so a few hundred kilobytes could unpack to gigabytes inside a worker. The members' declared uncompressed sizes are now summed before anything is inflated, and a DOCX declaring more than 256 MiB (`MAX_UNZIPPED_BYTES` in `core/parsing/docx.py`, a constant, not a setting) is refused with `PAYLOAD_TOO_LARGE`. The declared size is a real bound: `zipfile` stops inflating a member at its declared size and fails the CRC check on one that lies, which surfaces as `PARSE_FAILED`. Both cases are tested with a real 300 KB archive that unpacks to 300 MiB.
- **Deep nesting (TASK-0489).** A 10,000-deep JSON array raised `RecursionError` in a recursive walk. The walk now keeps its own stack, and JSON nested past 512 levels is refused with `NESTING_TOO_DEEP` — a limit of the parser's, because how deep `json.loads` will go differs between interpreters. HTML is walked the same way with no limit, so a 10,000-deep page parses.
- **Damaged binaries (TASK-0489).** A truncated or bit-flipped DOCX raised whatever `zipfile`, `zlib`, `lxml` or `python-docx` met first; every such failure is now a `ParseError`, as it already was for PDF. Hypothesis generates both kinds of damage against both formats.

## 6. Supply chain

**Known accepted advisories (`chromadb`, reviewed 2026-11-03).** `pip-audit` runs over all
extras and blocks the build, with exactly four ignores — all against `chromadb`, all
reviewed rather than waved through. There is **no fixed version**: 1.5.9 is the latest
release. Every one of the four is in Chroma's **server**, which fasterRag never starts:
`PYSEC-2026-311` and `PYSEC-2026-3814` are code injection through `trust_remote_code` on
the HTTP collections endpoints, `PYSEC-2026-3813` and `PYSEC-2026-3815` are cross-tenant
authorization failures in its HTTP auth and `SimpleRBACAuthorizationProvider`. The adapter
uses an embedded `PersistentClient` against a local directory — no HTTP API is served, that
RBAC provider is never constructed, and the adapter passes vectors itself rather than
configuring a Chroma-side embedding function, which is the path `trust_remote_code` travels.
Chroma's own multi-tenancy is also unused: fasterRag isolates tenants by collection name at
its own layer (§3), so Chroma's tenant checks are not what stands between two tenants here.

That reasoning is ours, derived from the shipped code, not a vendor statement — and it holds
only for embedded use. **An operator who also runs a Chroma server in the same deployment is
exposed by these advisories independently of fasterRag**, and should treat `fasterrag[chroma]`
as unsuitable until upstream ships a fix. TASK-0299 re-checks for one; the ignores are
deleted the moment it exists.

- **Pinned, hash-locked dependencies** — `uv.lock` is committed: 135 packages, 1577 `sha256` hashes. CI runs `uv lock --check`, which re-resolves `pyproject.toml` and fails when the result differs, so a dependency added without relocking is caught at the gate rather than discovered when two machines install different versions.
- **Dependency audit is blocking**, and runs against the *lockfile* rather than an installed environment — an environment is whatever resolved on that runner today, the lockfile is what everyone actually installs. It reported no advisories across all 135 packages on 2026-08-03 — a result that CI re-establishes on every push rather than a figure quoted from a one-off run.
- **Dependency licences are checked** in the `supply-chain` job on every push: every release `uv.lock` names for the core install and every extra except `dev` is looked up on PyPI and judged against an allow-list of Apache-2.0-compatible licences (`.github/scripts/check_licences.py`). A licence not on the list fails the build, and so does a package that declares none this check can read. The accepted exceptions are named in the script with their reasons and printed on every run: `psycopg`, `psycopg-binary` and `psycopg-pool` (LGPL-3.0, reached only through the `pgvector` extra), `pypdfium2` (a prose declaration of BSD-3-Clause/Apache-2.0 plus PDFium's bundled notices), and the NVIDIA CUDA runtime packages `torch` pulls in on Linux through the `huggingface`, `rerank` and `all` extras (proprietary, or declaring nothing). An exception lapses when the package's declaration changes or the package leaves the lockfile. Measured 2026-11-12: 167 locked releases, 147 allowed, 20 by those exceptions, none refused or unreadable. *Status (2026-11-12): the exceptions were written with the check and have not yet been confirmed by the maintainer; the LGPL and NVIDIA ones are licence decisions, not engineering ones (TASK-0496).*
- **Every third-party GitHub Action is pinned to a full commit SHA**, with its version in a comment, in every workflow and composite action — a tag on another repository can be moved, a SHA cannot. `tests/unit/scripts/test_release_pipeline.py` fails on a floating reference, and Dependabot moves the pins.
- **Secret scanning in CI** (gitleaks, full history — a credential committed and later removed is still compromised, so scanning only the tip would call it clean). A detected credential fails the build.
- **Non-root containers** for every image **fasterRag builds itself** (the shipped `Dockerfile` runs as uid 10001, verified in a running container). Third-party images fasterRag provisions — Qdrant, the Langfuse stack, Grafana — run as their upstream images ship them; forcing a uid on an image that expects to own its storage volume risks an unstartable container. This is the narrowing recorded as AUDIT-0007 ✅ and already carried by [deployment.md](deployment.md); it was missed here until the 2026-08-09 claims audit.
- **SBOM generated at each tagged release** and attached to the release artifacts. The release workflow generates it (`.github/workflows/release.yml`, job `sbom`): CycloneDX 1.5 exported from `uv.lock` for the core install and every extra except `dev`, stamped with the version it describes, and attached to the GitHub release with the sdist and the wheel ([release.md](release.md) §3). *Status (2026-11-12): no release has been tagged, so no release has produced one yet (TASK-0445). A rehearsal run generates the same document as a workflow artifact.*
- Base images and provisioned tool versions (Qdrant, Langfuse, Grafana) are pinned by tag/digest — no `latest`. The `Dockerfile`'s two base images (`python:3.12-slim` and the `uv` binary's image) are pinned by digest with the tag beside each, and the image installs exactly what `uv.lock` names (`uv sync --locked`), so the same commit builds the same dependency set on any day. *Status (2026-11-12): the provisioned tool images are pinned by tag only, not by digest, and `langfuse/langfuse:3` is a major-version tag that moves.*
- Dependency update PRs run the full test pyramid plus the eval regression gate before merge. Dependabot opens them weekly (`.github/dependabot.yml`): `uv.lock`, the GitHub Actions SHA pins and the `Dockerfile` base digests, each grouped, with a major Python release on its own. Each pull request runs `ci.yml` like any other, `eval-gate` included. *Status (2026-11-12): two gaps remain. `ci.yml` runs the unit, integration, model and eval tiers but not load or soak, which run nowhere on a pull request; and nothing yet requires the run to be green before a merge — that is branch protection, TASK-0098.*

## 7. Threat-model notes (beta boundaries)

- The dashboard is read-only but displays prompts/responses — deploy it on internal networks and treat access to it as access to corpus content. It enforces the same keys, scopes, and tenant matching as the API (TASK-0184), but on its own port and with no TLS of its own.
- The trace store (D8) persists full prompts/responses locally; retention is bounded by `traces.retention_days` and the store lives inside the deployment's trust boundary.
- fasterRag never sends corpus data anywhere except the providers the operator configured (embeddings/LLM). Local-only stacks (HuggingFace + Ollama + Qdrant) keep all data on-host.
