# Changelog

All notable changes to fasterRag are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). Entries are reverse-chronological; dates are `YYYY-MM-DD`. Sections used per release: Added / Changed / Deprecated / Removed / Fixed / Security.

> **On the numbers in this file** (clarified by the 2026-08-09 claims audit, TASK-0238). Wall-clock figures quoted in entries below — load times, latencies, byte ratios — are **dated one-off observations from a developer machine**, recorded so a change's motivation is legible. They are **not** benchmark-ledger entries: they carry no isolated hardware, no dataset manifest, no repetitions, and no commit hash, and they must never be quoted as fasterRag's performance. The only citable numbers live in [benchmarks.md](benchmarks.md), which currently holds **two entries, both explicitly marked non-citable** pending the isolated-hardware run (TASK-0084). Likewise "verified against a real X" in an entry records that a manual check was run at the time; unless the entry names a committed test, nothing re-runs it.

## [Unreleased]

### Changed

- Generation and embedding price tables carry per-entry provenance and cover the configured providers (2026-08-09, closes TASK-0152): `services/estimation.py` now holds `TokenPrice` records — provider, rates, source, and the date the figure was read — instead of bare numbers under one global `prices_dated`, because a single table-wide date is only as true as its oldest row and re-checking one vendor silently re-dated every stale row beside it. `PRICES_DATED` survives as the derived minimum, so it cannot claim a freshness no entry has. Coverage grew from two generation models to 48: OpenAI's GPT-5.x/4.1/4o/4/3.5-turbo and o-series chat models, the Anthropic lineup, and Cohere's `command-r-plus-08-2024`; local providers are now documented as priced at zero by decision rather than by omission. A rate is matched on **provider as well as model**, so an OpenAI-compatible gateway serving `gpt-4o` is no longer billed at OpenAI's rate. `PRICES_USD_PER_MILLION_TOKENS` and `GENERATION_PRICES_USD_PER_MILLION_TOKENS` are renamed `EMBEDDING_PRICES` and `GENERATION_PRICES`; `PRICES_SOURCE` is removed, superseded by the per-entry `source`.
- First formal audit corrections (2026-08-02): CLAUDE.md and README no longer claim a documentation-only repository — both now state the build-phase status with shipped/partial/pending marked per surface; reliability.md, api-reference.md, glossary.md, and failure-modes.md annotate the circuit breaker, `cache_only` degradation rung, and idempotency keys as specified-not-built with their task ids; quickstart.md, cookbook.md (R5 multi-tenant warning: `security.*` validates but is **not enforced**), python-api.md (per-surface status table), and integrations.md (per-provider status; entry-point registration pending) are annotated against the implemented system; data-model.md trace ids aligned to the implemented bare 32-hex OTel form (AUDIT-0006); deployment.md non-root claim narrowed to images fasterRag builds itself (AUDIT-0007); CONTRIBUTING.md codifies multi-line `# CRITICAL:`/`# TODO:`/`# BLOCKED:` comment blocks; todo.md ledger hygiene repaired (duplicate unticked S2 block removed, duplicated TASK-0110 renumbered to TASK-0155) and audit follow-ups filed as TASK-0156–TASK-0168 with two maintainer decisions (TASK-0164 license ADR, TASK-0165 ladder-scope ADR).

### Added

- The `parsing` configuration section (2026-08-09, TASK-0218): the OCR trigger (`minimum_chars_per_page`), the OCR render resolution, the two PDF heading-inference rules, and CSV row grouping are now settings rather than constants in `core/parsing`. A corpus of scans and a born-digital corpus disagree about when a page is a scan and how sharp a render has to be, and until now tuning either meant editing source. Every default is unchanged, so no deployment behaves differently. Configuration reaches the parsers as a frozen `ParsingOptions` value object built by `create_parsing_options(settings)` — the same boundary `create_chunker` uses — which keeps `fasterrag.parsing` usable standalone with no configuration at all, and is derived inside the worker process so nothing extra is pickled per document. Changing a parsing setting does not change chunk ids or the document content hash, so an already-indexed corpus needs `fasterrag index reembed` for it to take effect; the reference says so next to the rows.
- The `redis` cache backend (2026-08-09, closes TASK-0124): `embeddings.cache.backend` and `cache.backend` have accepted `redis` since the schema was written and have refused to start on it ever since; both now work, behind `pip install fasterrag[redis]` and the new `embeddings.cache.redis_url` / `cache.redis_url`. It is the only backend more than one process can share — `memory` dies with its process and `disk` is private to one filesystem, so a pool of API replicas running either one gets a hit only when the load balancer happens to pick the replica that answered last time. The client is imported lazily inside the constructor, so a deployment that never selects the backend never pays for the dependency, and its absence is a `ConfigError` naming the extra rather than an ImportError from somewhere in the cache. **The entry ceiling is enforced by a sorted-set index rather than delegated to Redis**: `maxmemory-policy` is a server-wide setting on a server we do not own and would evict a co-tenant application's keys as readily as ours, while counting our own by scanning the keyspace is O(everything stored) and races every write. Reads restack the member's score, so eviction is least-recently-*used*, matching `MemoryStore`. The same index is what `items` walks and what `clear` deletes — `clear` is never `FLUSHDB`, because a corpus change must not wipe a neighbour's data — and the two caches take separate namespaces so one server can back both. The index is written before the value deliberately: interrupted the other way round, a value would survive that no index knows about, invisible to the ceiling, to `items`, and to `clear`, which is a leak rather than a miss. TTL is written twice, into the payload where it stays authoritative across backends and as the key's native expiry so Redis reclaims the memory. `decode_responses` is forced off regardless of the URL, since values are packed float32 behind a struct header and a decoding client would turn every entry into a permanent miss. Failures translate to `CacheError` at the boundary, so a downed Redis degrades to cache-off (FMEA row 23) instead of failing queries, and the message never echoes the URL, which can carry a password. 36 unit tests against a fake client and 9 integration tests against a real container.
- `url` and `inline` ingestion sources (2026-08-03, closes TASK-0129): all three documented source types are now accepted everywhere — REST, CLI, and facade — with the schema as the only gate. URLs are fetched with the document size limit enforced twice, on the declared `Content-Length` and again while streaming, because a limit checked only against a header the peer controls is not a limit; inline payloads decode base64-first with a UTF-8 fallback, so binary documents and pasted snippets both work without the caller declaring which. Fetched and decoded bytes stage to a per-job temp directory that is removed when the job settles, while the **canonical URI stays the document's identity** — a temp-path identity would mint a new document id per run and deduplication would never fire again. A bare string with an http(s) scheme now classifies as a `url`, so `fasterrag ingest <url>` behaves as the CLI reference always documented; `httpx` moved from the dev extra into core dependencies because the loader imports it at runtime.
- Root-cause grouping in the blockers view (2026-08-03): `docs/blockers.md` now numbers blockers as `B<root>.<child>` so one unmade decision reads as the single conversation that unblocks everything under it, and `scripts/check_blockers.py` validates the hierarchy — an orphaned child or one filed under the wrong root fails CI, keeping the view's structure as trustworthy as its citations.

- Repository hardening (2026-07-29): `.gitignore`, `.env.example`, canonical default `config.yaml` (byte-consistent with the config-reference example), GitHub PR/issue templates enforcing the contribution rules, private vulnerability-reporting policy (`.github/SECURITY.md`), `docs/glossary.md` (canonical terminology), `docs/references.md` (external evidence bibliography R1–R14), `docs/archive-format.md` (D11 portability archive spec v1.0.0), and the golden-set JSONL schema in `docs/testing-strategy.md`.
- Grafana auto-provisioning as code (2026-08-02): `fasterrag provision grafana` writes datasource, dashboard-provider, Prometheus, and dashboard manifests, then converges the containers — rewriting manifests every run while leaving running containers alone. Datasources carry `editable: false` and dashboard providers `allowUiUpdates: false` with a 30-second reload, so the repository is the source of truth and a dashboard edited in the browser is a change nobody can review and the next run silently reverts. Verified end to end against real containers: fasterRag's `/metrics` scraped by Prometheus, queried back through Grafana's *provisioned* datasource, returning the exact request counts that had been generated.
- Autopilot (2026-08-02, D6): `fasterrag autopilot run` evaluates candidate retrieval configurations against a golden set built from your own corpus and reports what each one actually scored, replacing tuning folklore with a measurement. It never writes `config.yaml` — the output is a suggested YAML *fragment* plus the measured deltas behind it, and the command re-reads the config afterwards and fails if a single byte changed, because "never auto-applies" is the promise D6 rests on and an unchecked promise is a hope. A fragment rather than a whole file, so nobody overwrites a config full of keys Autopilot never looked at. Ties never displace the current configuration: suggesting a change that measured identically asks a human to review a diff for no reason and trains them to stop reading them. The search is time-boxed and reports what it did not reach, since presenting the best of an arbitrary subset as the best available is the failure mode of every budgeted search. Only query-time parameters are searched — index-time ones would make each candidate a full corpus rebuild (TASK-0145).
- The regression gate wired end to end (2026-08-02, D7): one `fasterrag.services.evaluation` turns "a golden set plus a collection" into a scored report, so `fasterrag benchmark --suite eval` and the `index reembed` gate measure the same thing the same way — three callers scoring three slightly different ways would make their numbers incomparable. An eval dataset is a *directory*, not a file: a golden set alone cannot reproduce a score, and keeping the corpus beside it makes the pairing hard to get wrong. A blocked gate exits 5, the documented regression-gate code, so CI can tell it from a crashed run. Verified against a real Qdrant in both directions: a healthy index passes at recall@5 1.0, and an index deliberately built from four of six documents is blocked with `recall@k fell from 1.0000 to 0.3333, a drop of 0.6667 beyond the 0.0200 tolerance`.
- The committed retrieval baseline (2026-08-01, D7): the `handbook` fixture under `tests/eval/datasets/` — six short policy documents, fifteen hand-authored golden records (twelve answerable, three adversarial), and a baseline measured against a real Qdrant and a real embedding model. The set is `source: "human"` deliberately: a generated set is what the P4 generator produces, but committing one as the CI reference would move the baseline whenever the generating model moved, and a gate whose reference drifts under it detects noise rather than regressions. Ground truth is document-level, because chunk ids are a function of the chunker configuration and a chunk-level set would go stale the moment `chunking.chunk_size` changed — which is one of the very things the gate exists to let people change safely. The baseline records its own sensitivity honestly: at six documents and k=5 a retriever returns five of six, so recall@5 is close to free and detects retrieval being *broken* rather than slightly worse; MRR carries the signal, and 1.0 means the correct document ranked first for all twelve answerable queries.
- Golden-set generation (2026-08-01, P4): questions generated from a real corpus in the schema the eval harness, the regression gate (D7), and Autopilot (D6) all share. Sampling is stratified across documents rather than uniform over a flat chunk list, because one long manual beside ten short memos otherwise supplies almost the whole set — which measures retrieval *into that document* rather than retrieval. A fifth of the set is deliberately unanswerable: without adversarial records every tuning pass is rewarded for answering more confidently, and a system that has learned to guess scores identically to one that has learned to retrieve. An adversarial slot is decided by the slot, never by the model's self-report, so a model that ignores the instruction and writes an answerable question cannot quietly remove the coverage the set depends on. Generated records carry `source: autopilot` and promotion to `human` needs a person — an ungoverned generated set lets the same model family write the questions, answer them, and score the answers. Verified against a real 21-chunk PDF: 10 requested, 10 generated, 2 adversarial, 0 dropped, and the adversarial questions used the corpus's own terminology while being genuinely unanswerable from it.
- Backup and restore, and a partially-executed restore drill (2026-08-01): `fasterrag backup` and `fasterrag restore` capture and replace the artifact inventory of `disaster-recovery.md` §1 — backend-native collection snapshots plus the lockfile, journal, trace store, and `config.yaml`. `.env` is never touched: secrets belong in the operator's secret manager, and a backup routine that swept them into a tarball would put every credential wherever backups are stored. A directory without a readable manifest is refused as a restore source, because an incident is the worst moment to be guessing whether a folder is a complete backup, and a restore whose vector counts disagree with its manifest exits non-zero rather than reporting success — that mismatch is how a broken recovery gets signed off. The drill was then *executed*, not desk-checked: a live collection was snapshotted, deleted outright, and restored, after which the same query returned the identical answer citing the identical chunk id. Its scope is recorded honestly — steps 1–3 and 6 did not run, because the restore was onto the same host, so RPO and RTO remain TBD-until-measured.
- The scripted chaos suite (2026-08-01, D12): all five scenarios of `testing-strategy.md` §1.9 — kill-worker, stop-Qdrant, corrupt-document, slow-LLM, disk-full — as twelve runnable assertions under `pytest -m chaos`, with the observed behavior recorded in `failure-modes.md` rather than left implicit in a test file. Reliability anyone can re-run is the point; a suite whose results are not written down is prose again. Each fault is injected at the closest honest seam — an adapter raising what the real failure raises, a directory that genuinely cannot be written — because simulating a symptom is legitimate while simulating the handling would prove nothing, and the doc says which rows are which. The kill-worker scenario is the sharpest: re-writing the same batch produced six upsert calls carrying three distinct point ids, so the deterministic chunk id turns a retry into a replace rather than a duplicated passage.
- The first two ledger entries (2026-08-01): BENCH-0001 (parse-and-chunk) and BENCH-0002 (end-to-end non-cached query), both recorded and both explicitly marked **not citable**. They were measured on a developer laptop with Docker, an IDE, and other co-tenant load, which fails ledger rule 5's isolation requirement, so no documentation claim may be built on them and `slo.md` keeps every TBD-until-measured. They are committed anyway because a measurement taken and caveated is worth more than none, and because they prove the harness emits complete entries. The data argues for its own caveat: two invocations of the same commit minutes apart gave p50 5.5 s and 8.7 s for the same work, and cold start came out faster than the warmed median — run-to-run variance exceeding the effect being measured is exactly what the isolation rule exists to prevent.
- The benchmark suite and ledger emitter (2026-08-01): `fasterrag benchmark --suite ingest|query --ledger` implements the methodology of `docs/performance.md` mechanically rather than by convention — the hardware fingerprint and commit hash are captured automatically because a latency without a machine attached is not a measurement; cold start is reported separately from the warmed percentiles, since folding a model load into a warmed number makes a system look slower than it is and hiding it makes a first request look faster than it will ever be; three repetitions are run with the median reported and every run attached, so a reader can see the spread rather than trust the summary. Percentiles are nearest-rank, not interpolated: an interpolated p95 reports a latency no request actually had, and at benchmark sample sizes that invention is large enough to matter. A dirty working tree is recorded as `-dirty` on the commit rather than hidden, because a number measured against uncommitted changes cannot be reproduced from the commit alone. The suites measure a running deployment through the real service layer, never a mock.
- Zero-downtime reindexing (2026-08-01, D2): the vendor-neutral alias primitive (`set_alias`, `alias_target`, `delete_alias`) added to the adapter contract and implemented for Qdrant as a single atomic alias operation — a swap done as delete-then-create would leave a window in which the served name resolves to nothing, and every query arriving in it would fail, which is precisely the downtime the feature removes. `fasterrag index reembed` builds the green collection alongside the live one and points the alias at it only once the gate allows; `index rollback` flips back to a retained build, which is an alias swap rather than another rebuild — seconds instead of hours. Retention drops builds past `index.reindex.rollback_retention_hours` but never the live collection, whatever its age, and never a collection whose name it did not create. The gate distinguishes three states rather than two: approved, rejected, and *could not run*. A gate that could not run has established nothing, so it is recorded as `gate_ran: false` and reported, never as a pass. A blocked swap exits 5, the documented regression-gate code, so a pipeline can tell it from a build that crashed. Verified end-to-end against a real Qdrant: a first build, a query through the alias, a second build whose swap changed the answer in 724 ms, and a rollback that restored the previous answer with the identical citation id.
- The index lockfile and drift detection (2026-08-01, D1): every index build now writes what produced it — the retrieval-affecting config hash, the embedding model *and its version*, the chunker and its parameters, and a content hash per indexed document. The version is recorded alongside the model name because a provider can change weights behind a stable name, and without it that change is undetectable while every vector written afterwards silently belongs to a different embedding space. `fasterrag index lock verify` compares the lockfile against live configuration and corpus and exits non-zero on drift, naming each field with its locked and live values; `index list` reports drift status per collection. A missing lockfile is reported as *missing*, not as drift — nothing has changed, there is simply nothing to compare against, and conflating the two would make an un-locked index indistinguishable from a corrupted one. An unrelated edit such as `app.port` is deliberately not drift, since the hash covers only the retrieval-affecting subset. Verified end-to-end: a clean index verifies at exit 0, and changing `chunking.chunk_size` exits 1 reporting `config_hash` and `chunk_size` with both values.
- Time-travel replay (2026-08-01, D8): the four RAG spans — `retrieval`, `reranker`, `context-assembly`, `generation` — recorded against one clock origin so their offsets lie on a single timeline, and a skipped stage producing no span rather than a zero-duration one, because those two are otherwise indistinguishable. The local trace store (`fasterrag.services.traces`) persists every query's full candidate set, prompt, response, and the retrieval-affecting config it ran under; a write failure is logged and dropped, since an observability record that can fail the request it observes is worse than no record. And `fasterrag replay` / `POST /v1/replay` (`fasterrag.services.replay`), which re-executes a stored query under a candidate config and reports a *structured* diff: chunks added, removed, and reordered with their old and new ranks, beside the exact config keys that differ. "The answer is different" is not a finding; "this chunk fell out of the context and `retrieval.hybrid` went false" is. Replay refuses to run against a service with tracing enabled and never populates the cache — investigating an incident must not alter the evidence. Both halves of the D8 acceptance test verified against a real corpus: an unchanged config reproduced the retrieval set exactly, and turning off hybrid with `top_k: 1` showed the chunk that was lost and the citation that changed with it.
- The metrics catalogue (2026-08-01): every instrument in `docs/observability.md` §2, served at `GET /metrics` in the Prometheus text exposition format that the provisioned Grafana datasource reads. Implemented directly rather than on a client library — the catalogue is a fixed set, the format is a stable contract, and the approved stack names OpenTelemetry rather than a Prometheus client. Instruments record whether or not anything is scraping, and every one is declared at import rather than on first observation, because a metric that springs into existence on its first event is indistinguishable from an event that never happened — which is exactly the distinction an incident needs. RED metrics come from ASGI middleware, so a new endpoint is instrumented by existing; errors are counted in the single funnel every problem document passes through, so no handler can be added without its failures being counted. Verified against real traffic: two queries, one pipeline run and one cache hit, reported as one observation per stage and 1 hit / 1 miss.
- The REST half of the control plane (2026-08-01): the ingest, query, retrieve, collections, and admin routers, calling the same services the CLI calls so the two halves cannot diverge. `POST /v1/ingest` journals the job before starting it, so the id in the `202` is queryable the instant the caller receives it, and never blocks on a corpus that takes minutes to embed; per-document status and dead-letter retry are served from the journal (D3), and a retry starts a *new* job rather than mutating the original, which is the audit record of the failure being retried. `POST /v1/query` serves one path in two shapes — a JSON body, or `text/event-stream` when streaming — and a stream that fails after its headers have gone out emits an `error` event rather than a status, because a 200 is already committed by then; that is exactly why the contract makes the absence of `done` meaningful. Request bodies are strict: an unknown field is rejected rather than ignored, so a caller who writes `top-k` learns their override was dropped instead of silently receiving the configured default. Verified end-to-end over real HTTP against a real Qdrant and a real provider: accept → `queued` → `running` → `completed`, then a streamed answer with token deltas, citations carrying source and span, and per-stage timings.
- Build slice S8 — CLI (2026-07-31): the pipeline commands `ingest`, `query`, and `index`, each a thin front for the service the REST API calls, so the two control-plane halves cannot diverge. `index list` and `index delete` required two additions to the vendor-neutral adapter contract — `list_collections()` returning a neutral `CollectionInfo`, and `drop_collection()` — because the only alternative was the CLI reaching into a vendor client directly, which is what that boundary exists to prevent; both are covered by the shared contract suite and flagged for maintainer review as TASK-0126. `index create` embeds one throwaway probe when a local model has not reported its vector size yet, since a collection created at the wrong width cannot be widened and forces a full re-embed. `index delete` requires `--force`. Verified end-to-end against a real Qdrant and a real provider: a 20-page PDF parsed to 21 chunks, embedded, indexed with both legs, retrieved, and answered with a citation resolving to the page it came from.
- Build slice S8, in progress — CLI (2026-07-31): the `fasterrag` command (`fasterrag.cli`), built on the standard library rather than a CLI framework, since the approved stack names none and argparse covers subcommands and grouped flags without adding install weight to a package whose size is a stated concern. The diagnostic half ships first — `config validate`, `doctor`, `status`, `provision`, `estimate` — because these are the commands that must work when nothing else does, and each reports a broken environment as a *result* rather than an exception: a diagnostic that crashes on the problem it exists to find is useless precisely when it matters. Exit codes are the real contract, since a shell script branches on the code rather than the prose: `2` for invalid configuration, `3` for an unreachable dependency, `4` for a failed preflight, per cli-reference.md. `--json` prints one document and nothing else, so a stray progress line can never turn a parseable result into a parse error at the far end of a pipe; errors always reach stderr, including under `--quiet`, because a bare non-zero code with no cause is not a diagnosis. Global flags work in either position — `fasterrag --json doctor` and `fasterrag doctor --json` both mean the same thing, which needed a custom argparse action: a subparser's `store_true` default is applied *after* the root's parsed value and would silently reset it.
- Build slice S7 — caching (2026-07-31): the embedding cache (`fasterrag.core.cache`), keyed by content hash plus model plus model version, so a stale hit after a provider silently upgrades weights behind a stable name is unrepresentable rather than merely unlikely. Implemented as a wrapper around any `EmbeddingAdapter`, so a third-party adapter registered through the entry point gets caching without knowing the cache exists. Batches resolve per text: a batch that is nine-tenths cached sends only the missing tenth, and vectors come back in the caller's order because retrieval matches vectors to chunks positionally. Vectors are stored packed as float32 rather than as JSON — roughly a fifth the bytes, on a cache sized in entries. And the semantic response cache, keyed by the meaning of a query rather than its text: a paraphrase whose query vector clears `cache.similarity_threshold` is answered from the response already given, short-circuiting retrieval, assembly, generation, and grading. A hit still streams — the whole answer arrives as one `token` event after `meta`, so a client needs no separate code path. Invalidation is TTL plus event: a corpus change drops every entry immediately, deliberately in full rather than selectively, because deciding which cached answers a new document could have changed would mean knowing what each answer was derived from *and* what the new document says, and a cache that guesses wrong there serves a confidently stale answer. Degraded answers are never cached, since caching a fallback would outlive the outage that caused it. Both caches obey FMEA row 23: every backend failure is caught, counted, and stepped past, so correctness never depends on a cache being reachable — only speed does. Hit, miss, invalidation, and error counters back `fasterrag_cache_events_total` ahead of the metrics export (TASK-0042). Backends are memory (LRU-bounded) and disk (atomic writes, survives a restart); `redis` is accepted by config validation but raises a `ConfigError` naming the alternatives until TASK-0124 ships it, rather than silently falling back to a backend the operator did not choose.
- Build slice S6, in progress — generation (2026-07-30): LLM provider adapters (`fasterrag.adapters.llm`) for OpenAI, Anthropic, Cohere, Ollama, and any OpenAI-compatible endpoint, behind one contract with two call shapes: `complete` returns a whole answer and its usage, `stream` yields text deltas so time-to-first-token stays low. A streamed call cannot report usage until it ends, which is why the SSE contract sends usage as a separate late event. The Anthropic adapter keeps the system prompt as a top-level parameter rather than folding it into the messages, because that is what makes its prompt caching addressable. Adapters classify failures and never retry, so retry policy stays in one place. Plus context assembly (`fasterrag.core.context`), which packs retrieved chunks into the prompt in relevance order until the token budget is spent, so an overrun drops the least relevant material rather than letting a provider silently truncate from the middle. Near-duplicate chunks are dropped before packing, because chunk overlap guarantees neighbouring chunks share text and spending a context window on the same sentences repeatedly is how context rot happens. Every packed chunk yields a citation carrying its source, page, and character span, recorded from what was sent rather than reconstructed from the answer afterwards. The P1 answer contract (`fasterrag.core.generation`), which renders the assembled context into the prompt with one citation marker per chunk and resolves the markers the model actually wrote back to citations — a marker naming a chunk that was never supplied is dropped and logged rather than returned, because a citation the caller cannot follow is worse than no citation. And the generation service (`fasterrag.services.generation`), which joins retrieval, assembly, and the provider into one answer path with two shapes: `answer` returns the whole response, `stream` yields the documented SSE event sequence — `meta` first so a client learns the trace id and any degradation before the first token, then `token` deltas, then `citations`, `usage`, and `done`. Usage arrives late because a streamed provider call cannot report token counts until it ends. A provider failure degrades to an extractive answer built from the retrieved passages rather than returning nothing, and a failure mid-stream emits `error` and stops without `done`, so a client can always tell a completed answer from a truncated one. And grounded-or-refuse (`fasterrag.core.faithfulness`, D5): a P3 grading call scores how much of an answer its context supports, and below `generation.faithfulness_threshold` the answer is withheld for a structured `INSUFFICIENT_EVIDENCE` response carrying the score, the threshold, and the candidates that were declined — so a caller told there is not enough evidence can see what evidence there was. Grading is a separate call from generation by contract, so the grader never sees the instructions that produced the answer and cannot self-justify, and it accepts a distinct adapter for a cheaper grading model. A grader that fails or returns unparseable output yields a `null` score, which never withholds: failing closed on a grader outage would turn a monitoring problem into an availability one. Refusal and streaming genuinely conflict, since a token cannot be unsaid — with the flag on, the stream therefore buffers and grades before emitting any token, trading time-to-first-token for the guarantee. The flag defaults to `false`, so that trade is only made on request; the behavior is recorded in `docs/api-reference.md` and flagged for maintainer review as TASK-0123.
- Build slice S5 — reranking and evaluation (2026-07-30): the retrieval regression gate (`fasterrag.services.regression`, D7), which compares a run against a committed baseline and blocks a drop beyond `eval.recall_tolerance` or `eval.ndcg_tolerance`. A baseline records the embedding model and retrieval-affecting config hash that produced it, and a mismatched one is refused rather than silently compared, because comparing across a model change measures the model rather than the change under test. A missing baseline blocks rather than passing, since a gate that waves through what it cannot check looks like protection while providing none. The cross-encoder reranker (`fasterrag.core.rerank`, public surface `fasterrag.rerank`), which reads query and chunk together over the fused shortlist and truncates to `retrieval.top_k`. A reranker that cannot load or score degrades the response to `hybrid_only` rather than failing the query, the first rung of the degradation ladder (D4). Candidates are only widened to `retrieval.rerank_top_n` when a reranker will actually consume them. The retrieval eval harness (`fasterrag.core.evals`, public surface `fasterrag.evals`) with the golden-set JSONL format shared by the harness, the regression gate, and Autopilot, plus recall@k, MRR, and nDCG@k. Adversarial records are counted separately rather than averaged in as zeroes, because a query the corpus cannot answer has no ground truth to score against and averaging one in would make a system that correctly refuses look worse than one that guesses. Document-level ground truth is honored alongside chunk-level, so a golden set survives re-chunking. Faithfulness is deliberately absent until the generation slice provides its call site.
- Build slice S4 — retrieval (2026-07-30): hybrid retrieval (`fasterrag.services.querying`) running the dense and keyword legs concurrently, both receiving the same pushed-down metadata filter so they search the same subset, and Reciprocal Rank Fusion (`fasterrag.core.retrieval.fusion`, public surface `fasterrag.retrieval`) combining them on ranks rather than scores at the documented k=60. Fusion runs in fasterRag rather than in the backend so `retrieval.rrf_k` and the leg weights are the values that actually apply. Results carry every leg's rank and score, not just the fused number, because the common retrieval question is why a chunk ranked where it did. Verified against a real Qdrant, including that the keyword leg retrieves an exact part number that dense search alone ranks poorly.
- Build slice S3 — ingestion core (2026-07-30): the parsing pipeline (`fasterrag.core.parsing`, public surface `fasterrag.parsing`) covering PDF with table extraction, type-size heading inference and an optional OCR path, plus HTML, Markdown, DOCX, plain text, CSV, and JSON — every format producing one structured `ParsedDocument` whose block offsets index exactly into its text, with committed golden-file snapshots pinning reading order, table structure, heading paths, and metadata. The chunking pipeline (`fasterrag.core.chunking`, public surface `fasterrag.chunking`) with all five configured strategies — fixed, recursive, layout, semantic, and late — sharing one assembler so the five documented invariants hold for every strategy, asserted property-based with Hypothesis. Embedding provider adapters (`fasterrag.adapters.embeddings`) for local sentence-transformers, OpenAI, Cohere, and Ollama behind one contract that separates document and query embedding, reports the model and version that drift detection anchors on, batches per `embeddings.batch_size`, and classifies provider failures without retrying — retry policy stays with the worker pool. The tiered-embedding router routes documents to cheaper or more precise models by metadata, reusing the vector database filter grammar so operators mean the same thing everywhere. The canonical identifier scheme (`fasterrag.core.identity`), including the deterministic document and chunk ids and the retrieval-affecting configuration hash the index lockfile anchors on. Checkpointed ingestion state (`fasterrag.services.journal`): job records written atomically with a checksum and a retained previous copy so a torn write degrades to resuming slightly earlier rather than losing the job, checkpoints at the configured interval, per-collection content-hash deduplication, idempotency-key replay that returns the original job, and a dead-letter queue whose entries carry a machine-readable reason code from the stable error table. The two worker pools (`fasterrag.workers`): a CPU pool that loads, parses, and chunks in worker processes and streams chunks downstream as each document completes, dead-lettering a bad document rather than failing the pass; a bounded queue that makes producers wait inside the pipeline but rejects with `QUEUE_FULL` at the API boundary; and a stateful embedding pool whose model is loaded once and reused across every batch, batching per `embeddings.batch_size`, routing tiered documents to their model, and retrying with exponential backoff and jitter only what a provider said was retryable. The indexer (`fasterrag.workers.indexer`), which closes the ingest chain: each embedded batch becomes one upsert carrying the dense vector, the BM25 sparse vector, and a payload mirroring the `Chunk` entity, so a citation's span and the model drift detection anchors on are written at index time rather than reconstructed later. The `VectorDBAdapter` contract gained optional sparse vectors on `CollectionSpec`, `Point`, and `SearchQuery` per ADR-0007, with the Qdrant adapter switching between the unnamed dense layout and the named dense-plus-sparse layout that hybrid collections require, and the shared contract suite now proves the keyword leg round-trips against a real backend. The ingestion service (`fasterrag.services.ingestion`), which runs both pools concurrently against one bounded queue so parsing and embedding overlap rather than running in phases, checkpoints as documents complete, resumes from the last checkpoint, dead-letters what the embedding pool could not place, and settles each job as completed, partial, or failed. An end-to-end integration test ingests a real corpus into a real Qdrant and retrieves it over both the dense and the keyword leg. The preflight cost estimator (`fasterrag.services.estimation`, D9), which parses and chunks a corpus for real — because token count depends on overlap and enrichment, not on file size — and reports documents, chunks, tokens, and projected embedding cost per provider before anything is embedded. Prices are dated list prices, and a model with no recorded price reports an unknown cost rather than a fabricated one; wall-clock time is deliberately not projected, because embedding throughput has not been measured yet and an unmeasured projection would be a claim without a measurement. The vector database health check is now registered with `/readyz`.
- Build slice S2 — Qdrant adapter and doctor v1 (2026-07-30): vendor-neutral `VectorDBAdapter` contract with its request and result types and a vendor-neutral metadata-filter grammar (`fasterrag.adapters.vectordb.base`); the provider factory, including third-party registration through the `fasterrag.vectordb` entry point, with built-in names taking precedence (`factory`); the Qdrant reference adapter covering the docker, external, and remote modes, both the 6333 and 6334 paths, `prefer_grpc`, API-key auth, deterministic point-id mapping, filter push-down, and translation of every vendor failure into the typed taxonomy (`qdrant`); system-managed Docker provisioning that converges rather than reinstalls, publishes both ports, uses a named volume, and hands the server key to the container by variable name rather than on the command line (`services.provisioning`); `doctor` preflight diagnostics covering Python, disk, memory, GPU, Docker, secrets, per-port reachability, and backend health, each failure carrying a concrete fix (`services.doctor`); and the shared adapter contract suite run against a real Qdrant in every mode, wired into CI.
- Build slice S1 — skeleton (2026-07-29): the first implementation code. Packaging and tooling (`pyproject.toml` with ruff, `mypy --strict`, pytest and coverage config; `.pre-commit-config.yaml`; `.github/workflows/ci.yml` running the blocking gates; `scripts/check_commit_message.py` enforcing the single-line no-trailer commit rule). Typed error taxonomy (`fasterrag.errors`) with the stable error-code table and its RFC 9457 transport metadata. Structured JSON logging with OpenTelemetry-shaped correlation ids (`fasterrag.observability.logging`). Configuration schema and fail-fast loader (`fasterrag.config`) enforcing every key, bound, and cross-field rule in `docs/config-reference.md`, including the presence of referenced environment variables. API application factory with correlation middleware, problem-document exception handlers, and the `/healthz` and `/readyz` endpoints.

### Fixed

- `docs/observability.md` §5 described the Grafana datasource as pointing at fasterRag's metrics endpoint, which is one hop short of workable: Grafana's Prometheus datasource speaks PromQL to a Prometheus *server*, so aimed at a raw exposition endpoint it would never return a series. The provisioner now stands up Prometheus alongside Grafana and the doc says so (2026-08-02).
- The provisioned Grafana datasource had no pinned uid, so Grafana minted a random one per installation while every shipped dashboard panel referenced it by name — the dashboards would have rendered completely empty, with no error anywhere. Caught by reading back the provisioned datasource and finding `P1A267FD5A9BAB99E` where the panels expected `fasterRag` (2026-08-02).
- Autopilot's candidate grid searched `retrieval.top_k`, which cannot affect the measurement: recall@k requires retrieving exactly k, so the harness fixes the retrieval depth and every top_k candidate scored identically by construction. The grid would have burned budget on trials whose ties were structural, and reported them as genuine findings. Found by running the tuner and noticing three candidates that could not possibly differ (2026-08-02).
- Autopilot's grid also generated fusion weights outside the schema's 0.0–1.0 bounds, and one invalid candidate aborted the entire search rather than being skipped — discarding every trial that had already run. Candidates are now generated in range, and an out-of-bounds one is skipped and counted rather than fatal (2026-08-02).
- A malformed baseline raised a bare `TypeError` from `load_baseline` instead of a typed error. Worse, the shape of the failure mattered: a missing baseline blocks the gate, so a baseline that could not be read had to fail loudly rather than risk being treated as absent-or-ignorable. It now raises `VALIDATION_FAILED` telling the operator to re-record it with a measured run rather than edit it by hand (2026-08-02).
- A `config.yaml` saved with a UTF-8 byte-order mark was rejected. The BOM became part of the first key, so a file whose first line reads `app:` failed with "Extra inputs are not permitted" for a key named `﻿app` — invisible in every editor that wrote it. Windows editors and PowerShell add a BOM by default, so this affected the most common way of editing config on Windows. The loader now reads `utf-8-sig` (2026-08-01).
- The API no longer reloads the embedding model on every request. The router was built per request, so a local model paid its full load on each query — measured at roughly 5.2 s added to every call against 45 ms of retrieval. It is now process-scoped like the vector database adapter, and released by the application lifespan rather than by a request handler. Measured on the same repeated query after the fix: 17.5 s cold, then 18 ms (2026-08-01).
- The semantic cache now works over HTTP at all. It too was constructed per request, so every lookup consulted a cache that had just been created empty — it could never hit, while still costing a query embedding per call, which is strictly worse than no cache. Sharing it also required `GenerationService.close()` to stop closing it: a per-query service tearing down a shared backend connection would break other in-flight queries (2026-08-01).
- `fasterrag serve --config other.yaml` served `./config.yaml`. The path was validated and then discarded, because uvicorn was handed an import string whose factory takes no arguments. The application is now built directly with the validated settings, and the reload path — which runs in a child process that cannot receive an object — passes the path through `FASTERRAG_CONFIG` (2026-08-01).
- The degradation ladder no longer absorbs failures that will never recover. A rejected credential, an unknown model name, or a missing provider extra used to serve an `extractive` answer exactly like a provider outage, so a misconfigured deployment answered every query from raw passages forever while reporting nothing more specific than `degraded: true`. Only a **retryable** failure now takes that rung; the rest surface as the typed error they already are. The degradation log also records the provider's own detail and retryability, without which a degraded response left no record anywhere of why it degraded. Found by running `fasterrag query` against a real provider with a key it rejected (2026-07-31).
- A cross-encoder that cannot **load** now degrades to `hybrid_only` like one that cannot score. Only scoring failures were classified, so a model that failed to load — no disk, no memory, no page file, a half-finished download — escaped untyped and failed the whole query, contradicting D4. Found by running `fasterrag query` on a machine whose page file was too small for a 2.2 GB reranker (2026-07-31).
- The HuggingFace embedder reads a model's vector size through whichever accessor the installed sentence-transformers exposes. The name changed in 5.x, and the old one still worked while emitting a deprecation warning, so the adapter now spans both rather than pinning a version. Found by running the adapter against a real model for the first time (2026-07-30).

- Qdrant provisioning now sets `QDRANT__SERVICE__GRPC_PORT`, without which Qdrant leaves its gRPC interface disabled and only port 6333 answers — the provisioner was reproducing the very failure recorded in `docs/failure-modes.md` row 15. Caught by the adapter contract suite running in gRPC mode (2026-07-30).
- Vector-database gRPC failures are now classified by status code, so an authentication rejection over gRPC is reported as non-retryable instead of being retried as a transport blip until the circuit breaker opened (2026-07-30).
- The Qdrant adapter now passes `https` explicitly. The Qdrant client switches to TLS on its own as soon as an API key is supplied, so every authenticated call failed with a TLS handshake error against the plain-HTTP listener a container serves by default. Added `vector_db.https` so the transport is chosen rather than inferred (2026-07-30).
- Provisioning now confirms the backend answers an API call before reporting success. An open TCP port is not readiness: a container binds its listener before it can serve, and a transport misconfiguration connects at the socket level and only fails at the first request — so the failure surfaced in whatever ran next instead of in the provisioner (2026-07-30).
- The default `vector_db.docker.image` moved from `qdrant/qdrant:v1.9.0` to `v1.18.1`. The pinned default predated the features the project depends on: the `/points/query` API needs server 1.10 or newer, as do the sparse vectors and native fusion of ADR-0007, and the client reported the old server as version-incompatible (2026-07-30).

### Security

- Documented secrets policy (`.env`-only, env-var-name references), supply-chain requirements (hash-locked deps, secret scanning, non-root containers, SBOM per release).
- Configuration validation never echoes offending input values, and validation failures are raised without chaining the underlying `ValidationError`, so a credential mistakenly pasted into `config.yaml` cannot reach logs or tracebacks (2026-07-29).
- Interactive API documentation (`/docs`, `/redoc`) is not served: it is a web interface capable of driving the RAG, and the control plane is programmatic only (ADR-0005). The machine-readable `/openapi.json` schema is still published (2026-07-29).
- The Qdrant server API key is exported into the provisioning subprocess environment and passed through with `-e NAME`, so the value never appears in `argv`, a process listing, or a log line. Vector-database authentication failures name the environment variable and are never retried (2026-07-30).
