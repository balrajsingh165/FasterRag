# Changelog

All notable changes to fasterRag are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). Entries are reverse-chronological; dates are `YYYY-MM-DD`. Sections used per release: Added / Changed / Deprecated / Removed / Fixed / Security.

> **On the numbers in this file** (clarified by the 2026-08-09 claims audit, TASK-0238). Wall-clock figures quoted in entries below — load times, latencies, byte ratios — are **dated one-off observations from a developer machine**, recorded so a change's motivation is legible. They are **not** benchmark-ledger entries: they carry no isolated hardware, no dataset manifest, no repetitions, and no commit hash, and they must never be quoted as fasterRag's performance. The only citable numbers live in [benchmarks.md](benchmarks.md), which currently holds **seven entries, all explicitly marked non-citable** pending the isolated-hardware run (TASK-0084). Likewise "verified against a real X" in an entry records that a manual check was run at the time; unless the entry names a committed test, nothing re-runs it.

## [Unreleased]

### Added

- **`chunking.strategy: semantic` runs in the ingestion pipeline** (2026-11-12, TASK-0431). The parse workers had no embedding model, so every semantic job was refused at acceptance (and, before 2026-11-11, every document was dead-lettered). Each parse worker process now builds its own sentence embedder from the configured local model (`embeddings.provider: huggingface`), once, and every worker loads it before the first document and after each pool recycle, so a model load is never counted against `ingestion.parse_timeout_seconds`. **Memory is `workers.cpu_pool_size` copies of the model**, and a pool takes one model load to start. Any other embedding provider is still refused before the job is recorded, now with a message naming `embeddings.provider`. `SemanticChunker` now applies the token-budget pass the other strategies already used — before, a group of sentences could run to several times `chunk_size` on text that tokenizes densely. Chunk ids for the semantic strategy now also depend on `chunking.semantic_percentile` and the embedding model; ids for every other strategy are unchanged, which pinned hashes prove. Proven by `test_a_semantic_job_with_a_local_model_completes_within_the_token_budget`, `test_each_parse_worker_builds_its_own_sentence_embedder_once` and `test_a_model_load_is_never_billed_to_a_documents_parse_deadline` (both on the real process pool) and `test_chunk_ids_of_every_other_strategy_are_unchanged`.

- **A release pipeline, built and not yet used** (2026-11-12, TASK-0445). `.github/workflows/release.yml` runs on a pushed `v*` tag, or by hand as a dry-run rehearsal, which is the default. It verifies that the tag matches `__version__` and is on `main`, runs the whole CI gate set, builds the sdist and wheel and checks them, generates a CycloneDX SBOM from `uv.lock`, builds and checks the image, and smoke-tests the wheel in a clean container. Only then, behind a required approval on the `pypi` environment, does it publish to PyPI by trusted publishing (no stored token), push the image to GHCR tagged with the version (never `latest`), create the GitHub release with the changelog section, the SBOM and the distributions attached, and smoke-test the published package. **Nothing has been published.** Before the first tag the maintainer must create the PyPI trusted publisher, the protected `pypi` environment and a tag ruleset — the checklist is in `release.md` §3.1. Note that any `v*` tag starts a run, including the slice tags `v0.x.0-sN`; such a run fails at the version check and publishes nothing.

- **Delete and update a document** (2026-11-12, TASK-0443). Nothing outside the adapters called `VectorDBAdapter.delete`: a document could not be removed, a re-ingested source that shrank left its old tail chunks retrievable (reproduced: 33 chunks became 1 and 32 stale ones remained), and the dedup file never forgot anything, so deleted content came back `deduplicated`. Now `DELETE /v1/collections/{name}/documents/{document_id}`, `fasterrag documents delete` and `FasterRag.delete_document` (async and blocking) delete a document's chunks by a `document_id` payload filter, tombstone its dedup record, drop it from `index.lock` and invalidate the semantic cache. Deleting a document nothing holds is not an error (`known: false`). Re-ingesting a document the journal knows trims its chunks at or past the new length once the new ones are written; a superseded hash stops counting, so a restored earlier version is indexed again. Under multi-tenancy the delete also requires the chunk's tenant tag to match. **Operators should know:** a tombstone line in `content-hashes.jsonl` is not readable by an earlier build. **Limits:** with `ingestion.dedup: false` a shrunken re-ingest still leaves its tail (TASK-0518); a delete during a running ingest of the same collection is not coordinated (TASK-0519); and with multi-tenancy on, a document ingested through `POST /v1/ingest` lives in the unprefixed collection and cannot be reached by this route until tenant scoping of ingest is decided (TASK-0381). Proven by `test_a_document_that_shrank_leaves_no_stale_chunk`, `test_a_deleted_document_is_indexed_again_by_the_next_ingest`, and five new contract cases that passed against live Qdrant, pgvector, Chroma, Milvus and Weaviate.

- **A plugin can be selected from `config.yaml`** (2026-11-12, TASK-0439). The three adapter factories have resolved entry-point plugins for some time, but the schema typed `vector_db.provider`, `embeddings.provider`, `llm.provider` and a tier rule's `provider` as closed lists, so `provider: mydb` was refused at load before any factory ran. Those fields are now validated in `config/plugins.py` against the built-in names plus the names installed distributions register under `fasterrag.vectordb`, `fasterrag.embeddings` and `fasterrag.llm`, read from entry-point metadata without importing `adapters/` or executing the plugin. Fail-fast is kept: an unknown name still stops the load, and the message now lists the built-ins and the installed plugins. **Changed:** `vector_db.provider: pinecone` used to validate and fail later in the factory; it is now refused at load, citing TASK-0049 — including under `fasterrag config show`. **Changed:** for a plugin provider, `llm.api_key_env` and `vector_db.api_key_env` must be written out (a variable name, or `null`): a plugin is never handed `OPENAI_API_KEY` or `QDRANT_API_KEY` by default. The wording of a bad-provider validation message changed. Proven by `tests/unit/test_plugin_selection.py::test_a_plugin_named_in_config_yaml_ingests_and_answers_a_query`, which installs a fake distribution, loads a `config.yaml` naming it through the real loader, ingests through the production pipeline and answers a query. Chunkers, parsers and rerankers still have no plugin point (TASK-0513).

- **A test that runs the real process pool** (2026-11-12, TASK-0455). Every pool and pipeline test injected a thread pool, which is why serial parsing went unnoticed for fourteen slices. `tests/unit/workers/test_real_process_pool.py` now ingests three documents through the default `ProcessPoolExecutor`, carries a typed failure back across the process boundary, and kills a worker with `os._exit` to assert the typed error and a job settled `failed`; all are `must_run`, and they ran in both the Ubuntu and Windows lanes. Pickling of `Settings` and the queue dataclasses was sound. The real pool did expose one defect: an error raised in a worker carried a trace id the worker minted for itself, so a dead-letter entry could not be joined to its job's log lines; the pool now re-stamps it with the job's trace id (`test_a_worker_failure_is_filed_under_the_trace_id_of_its_job`).

- **The Milvus and Weaviate contract suites ran against real servers for the first time, and found four defects neither fake could show** (2026-11-11, TASK-0396; TASK-0352's CI wiring stays open). `deploy/compose.test-backends.yml` had never been executed — the machine it was written on had no Docker daemon. On one that does, it **did not come up**: upstream's `minio/minio:RELEASE.2023-03-20T20-16-18Z` answers *"pull access denied"*, and `docker manifest inspect minio/minio:latest` answers *"unauthorized"*, so the whole Docker Hub repository is closed to anonymous pulls while `redis` and `quay.io/coreos/etcd` pulled fine in the same session; `quay.io/minio/minio` answers 401 and `bitnami/minio` is gone. **MinIO is removed** in favour of `COMMON_STORAGETYPE: local`, verified before committing (healthy on `/healthz`, `get_server_version()` → `2.5.14`, create/insert/search round trip), and the stack is one container smaller and reaches all-healthy in **17.5 s** from a `down -v`. Then the suites ran: Milvus **2 failed, 7 passed, 37 errors**; Weaviate **hung indefinitely** and was killed after 12 minutes. Both are now **46 of 46** and **54 of 54** green.
  - **Milvus could not create a single collection.** `schema.description = description` → `AttributeError: property 'description' of 'CollectionSchema' object has no setter`; it is read-only in pymilvus 3.x and goes in at construction. One line, all 39 non-passing cases.
  - **Weaviate's `iterate_points` never terminated.** Paging with `islice(cursor, batch_size)` re-entered `_ObjectIterator.__iter__`, which **rewinds the walk to the first page** — 400+ gRPC round trips for a *one-object* collection, re-yielding the same objects forever. A full-collection walk is what snapshots, export, tenant backfill and re-embedding are built on. The cursor is now advanced with `next()`.
  - **Weaviate's `restore_snapshot` could never clear a collection.** Its "match everything" filter was `fr_id != ""`, and a real server tokenizes the empty string to nothing and refuses the whole batch delete with *"invalid search term, only stopwords provided"*. It is now an id filter against the nil UUID, which no tokenizer touches and a UUIDv5 object id can never equal; four candidates were tried against the server and two were rejected by it.
  - **Weaviate classified HTTP 401 as retryable.** `test_invalid_credentials_are_not_retryable` was predicted to assert nothing against an anonymous-access server. It *failed* instead: the client still sends the key, Weaviate answers 401 *"oidc auth is not configured"*, and none of the adapter's auth phrases (`unauthorized`, `forbidden`, …) appear in that wording, so a rejected credential came back `retryable=True` — a caller retrying it forever. The status code is now checked before the prose. **So the stack buys 46/46 and 54/54, not the 44/52 estimated**: an open server rejects a bad credential differently, not never.
  - **Both test doubles were made faithful in the same change**, so each defect is reachable from the unit tier rather than only from a server: `FakeSchema.description` is read-only, and `FakeObjectIterator.__iter__` rewinds. This is the finding under the findings — the adapters carried the **highest** unit coverage in the set (`milvus.py` 94%, `weaviate.py` 95%) entirely against fakes their own authors wrote, and a coverage number taken against a double measures how thoroughly the tests agree with the double.

- **`RedisRateLimiter` ran against a real Redis server, and `FakeRedis` agrees with it** (2026-11-11, TASK-0290 narrowed). `security.rate_limit_backend: redis` shipped with "never run against a live Redis server" recorded honestly in its own module docstring. `redis:7.4.2-alpine` is now in the test stack — one service, no command override — and `tests/integration/test_redis_rate_limit_server.py` drives the shipped limiter against it over a real socket, each case in its own UUID namespace so it is safe to point at a server that is not empty. All **9 cases pass**, including one asserting the `MULTI`/`EXEC` reply shape is `[1, True]` and one that drives the same sequence of decisions through both the real server and `FakeAsyncRedis` and asserts the two decision lists are identical. **No divergence was found** — the fixed-window `INCR` + `EXPIRE` arithmetic, the TTL and the server-side eviction behave the same — which is a weaker result than a divergence would have been and is now measured rather than assumed. - **The degradation ladder has a registry, so "that rung is not built" is now decidable** (2026-11-11, closes TASK-0394). TASK-0369 closed the umbrella-id hole for vector-DB, embedding and LLM providers by reading `_BUILTIN_ADAPTERS`, and for test tiers by reading the pytest marker list, then stopped: the ladder had no registry, so `hybrid_only` was a bare constant, `extractive` was not even that, `cache_only` appeared nowhere in `src/`, and the only way to ask the tree whether a rung existed was a grep that answers *yes* off `cross_encoder.py`'s docstring. `services/degradation.py` is the registry, modelled on the adapter factory: `_BUILTIN_RUNGS` maps each rung to the implementation that serves it, `_PLANNED_RUNGS` names the specified-and-unbuilt ones, and `DegradationMode` is checked against both **at import**, so a rung added to the enum and to nothing else makes the module fail to load. **A registry you can forget is not one, so the ladder dispatches through it**: `serving()` is the only producer of a degraded `mode`, it resolves the registered implementation before returning the value, and it refuses a planned rung — shipping `cache_only` without registering it raises at the moment it tries to label its first response. **The wire form did not move.** `serving()` returns `str`, the three module constants are still the same plain strings, and `mode` is still typed `str` wherever it is carried, serialized, cached or used as a metric label; `DegradationMode` is an internal vocabulary that never reaches a response body. `scripts/check_unbuilt_claims.py` reads the two literals with `ast` and decides rung denials the way it decides adapter ones, with its own two vacuity guards (no rung registered; every declared rung implemented) and the existing per-path ratchet. **Measured over four trees** (237f6f5, 671156a, 650943b, HEAD): 146 rung clause-mentions, 40 denial clauses naming a rung, **0 findings and 0 false positives** — and zero findings is not zero discrimination, because moving `cache_only` into `_BUILTIN_RUNGS` to simulate TASK-0159 landing makes the rule report the 4 stale denials in README.md, api-reference.md, quickstart.md and reliability.md that no gate could previously see. Six further `cache_only` denials are correctly left to review: the subject of the denial is not the rung alone.

- **`fasterrag ci-status` and the `branch-verdict` CI job — a red `main` now fails a run somebody reads** (2026-11-11, TASK-0313 — the API half; branch protection stays TASK-0098). Nothing in the repository read the GitHub Actions API, which is why `main` was red for 81 days (TASK-0261) and again from 2026-11-08 to 2026-11-11 with every local signal green. `services/ci_status.py` and its 28 tests were salvaged intact from an abandoned 2026-09-13 worktree (TASK-0284) and ran 45/45 green against today's `src/` before a line was changed; what was added is the gate on top of them. **The listing is never filtered by trigger**, which is the whole defect: on 2026-11-07 `main` was green on the `ci` *push* run and simultaneously red on the `security` and `nightly` *scheduled* runs of the same commit, so reading the trigger a human opens reproduces the bug. **Four states collapse to a non-zero exit** — a red run, a `cancelled` one (`cancel-in-progress` left 21 commits with no verdict), a workflow with no completed run, and an API that could not be read at all; `0` requires a `success` that was actually read. The workflow set is **discovered** from `.github/workflows`, so a fourth workflow is gated the day it lands, and an empty set is a failure rather than an empty success.
  - **`skipped` is reported, because `skipped` reading as `fine` is the same blindness one level down.** On run `42522906097` (`6be46f9`, 2026-11-08) the `quality` job failed at `Typecheck` and the **thirteen** steps after it — nine named gates, the unit suite, both coverage gates and the doctor smoke test — were all reported `skipped`. A reader told only "red on `Typecheck`" fixes the typecheck and expects green; in fact thirteen checks never ran and never objected to anything else in that commit. The count and the names are in the report and in `--json`. Runner bookkeeping is excluded, and a step skipped by its own `if:` inside a job that *passed* is a decision, not a gap.
  - **A run whose every job was skipped is not green** either. GitHub concludes such a run `success`; a workflow that ran nothing found nothing.
  - **`ci.yml` excludes itself, and that is required rather than convenient.** A workflow gating on its own previous conclusion has no working state: treat its own last red as a failure and the push that fixes the cause still reads that red, so the branch can never return to green; excuse it and it excuses every red, because the latest completed `ci.yml` run on `main` is always an ancestor of the commit under test. Deadlocked or vacuous, with nothing between. Its own push run is attached to the commit and emailed on failure — the invisible workflows are exactly the ones whose latest run came from a `schedule`, and those are what the step checks.
  - **Authentication is opt-in and explicit.** The client passes no `auth` and sets `trust_env=False`, so no `GITHUB_TOKEN`, `GH_TOKEN` or `.netrc` is ever picked up; `--token-env NAME` is how CI opts in, because the anonymous budget is 60 requests an hour **per address** and a runner shares its address. Nothing logs a URL: an origin remote may embed a credential, and only the owner and repository parsed out of it survive.
  - **Proven against the real thing, not a hand-shaped fake.** The red fixtures are this repository's own payloads as `api.github.com` returned them — run `42522906097` step for step, and nightly run `42603353729` — replayed through the real client and the real CLI, where the exact command `ci.yml` runs exits `1`. Flags and exits are in [cli-reference.md](cli-reference.md).

- **`@pytest.mark.must_run` and the `must-run` CI job — a test that skips on every platform now fails the build** (2026-11-11, closes TASK-0349). `-rs` (TASK-0328) prints every skip with its reason, which makes one legible to a reader; it does not make one impossible to ignore, and the census that found "all seven unit-lane skips skip on both platforms" took a progress-dot diff against a local collection count to produce. The marker is a claim about one test — *this one executes somewhere in CI* — and the new job is what the claim costs. **The rule is ran-at-least-once, never ran-everywhere**: the symlink confinement cases cannot run on a Windows account without `SeCreateSymbolicLinkPrivilege`, so skipping there while running on Linux stays green and skipping on **both** fails. `tests/conftest.py` writes a per-lane JSON report when `FASTERRAG_MUST_RUN_REPORT` names one, the ubuntu and windows unit lanes upload theirs, and `scripts/check_must_run.py` reads both against a roster collected separately by `pytest -m must_run --collect-only` — separately because a lane can only report on tests it collected, and "absent from every report" must not read as "nothing to check". **17 cases carry it**: the two symlink confinement tests, and the four functions proving `FASTERRAG_LIVE_PROVIDER_TESTS` is checked before the credential (TASK-0341 left that module deliberately unmarked, which is a convention one line of `pytestmark` can undo with a billed call at the other end). A marker on every test is a marker that means nothing, so the criterion is narrow and written down in [testing-strategy.md](testing-strategy.md) §3.2. **The gate fails rather than passes** on a missing artifact, an empty reports directory, a roster with zero marked tests, reports holding no outcome, a collect-only document offered as evidence, an unknown report version, or a lane naming a test the roster lacks — each named separately and each pinned by a test.

- **`--assume-untagged` and `index tenants --untagged` — the mixed collection's remedy, and the split that was argued down instead of built** (2026-11-11, closes TASK-0385). TASK-0377's backfill refuses a collection holding two tenants' points plus untagged ones, which is exactly the shared unscoped collection TASK-0339's executed proof found leaking, and `--overwrite` answers it by handing one tenant the other's chunks. **That task's own premise needed correcting first**: `tenant_scoped_retrieval` filters on the payload tag and never reads the collection name, so a collection holding several tenants' chunks is already correct under the flag provided every point is *tagged* — what makes a corpus unreachable is the untagged residue, which is invisible to everyone. [security.md](security.md) §3 now opens its pre-enable checklist with the four shapes a collection can have and which of them step 1 refuses. **`backfill-tenant --assume-untagged` tags only the residue** and leaves every existing tag alone, the operation the tree lacked; it is refused together with `--overwrite`, since the two assert different things about the same collection, and the report carries `assumed` so an assertion the operator made can never read back as one the system derived. **`index tenants --untagged <path>`** writes the residue as JSONL grouped by document — `document_id`, `source_uri`, chunk count — because a document is the granularity an operator can recognise; chunks with no `document_id` collapse into one row with an empty id rather than pretending to be attributable. A residue that is genuinely several tenants' still has no command, and saying so is the honest answer: nothing guesses an owner. **The export → partition → import split was examined and deliberately not built** — relocation does not produce the tag the filter needs, the ingest and query paths address the raw collection name (TASK-0381) so moved points stop being addressable, and `export_archive` takes no filter at all, quite apart from the manifest recording the tenant-scoped name (TASK-0340) and import not being streamed (TASK-0293). **Not verified against a real vector database**; 12 tests against the in-memory double and the CLI's fake adapter.

- **`fasterrag index tenants` and `fasterrag index backfill-tenant` — the step that makes `security.tenant_scoped_retrieval` turnable-on** (2026-11-11, closes TASK-0377). The flag filters both retrieval legs on the `tenant` payload field, and a chunk indexed before `security.multi_tenancy` was enabled carries no such field, so enabling it over an unbackfilled corpus returned **empty results rather than wrong ones** — fail-closed, but silent. `index tenants` counts every collection's points by tag and names the tenants present, so what a backfill would touch is discoverable before anything is written; `index backfill-tenant <collection> --tenant <id>` writes the tag through the adapters' metadata-only `PointUpdate` path. It **dry-runs by default** and prints the counts a human reads before flipping the flag; `--apply` writes. **Idempotent by predicate rather than by bookkeeping** — only an untagged point is selected, which is the negation of the state the write produces, so a completed run writes nothing the second time and a run killed halfway is finished by running it again, with no checkpoint file to go stale. **A collection already holding another tenant's points is refused with `CONFLICT`**, naming them: its untagged points cannot be attributed to either tenant, and `--overwrite` is the explicit answer that relabels the whole collection. Both read through the `iterate_points` traversal added under TASK-0079 rather than a second walk. **Not verified against a real vector database** — the proofs are an in-memory adapter that applies the merge `update` promises, including a failure injected mid-run; no backend executed a `PointUpdate` here. The payload index of step 2 still does not exist (TASK-0378), so with the flag on both legs pay an unindexed filter. [security.md](security.md) §3 carries the ordering.

- **`reliability.idempotency` — lifetime, lease and kill switch for `Idempotency-Key`** (2026-11-09, closes TASK-0356). `ttl_seconds` (default `86400`) and `in_flight_lease_seconds` (default `900`) were hard-coded constants; the loader now refuses a lease longer than the lifetime, because an unfinished request outliving a completed one inverts the intent. `enabled` **defaults to `true`**, deliberately against CLAUDE.md's default-false rule for risky features, and the deviation is the decision: the rule exists for features that *start* doing something, while this one starts nothing — a request without the header touches no store and writes no byte — and defaulting it off would make a published contract false for every deployment that never read the setting, with a client whose retry silently executed twice having no way to notice. It is a kill switch for a misbehaving store, not a feature gate, and a kill switch that ships already pulled is not one. With it `false`, a keyed request is passed straight through: nothing recorded, nothing replayed, nothing refused.
- **The idempotency store is a substitutable interface** (2026-11-09, TASK-0357 — the seam, not the backend). `IdempotencyStore` is now abstract (`enabled`, `begin`, `commit`, `release`) with `FileIdempotencyStore` as the one implementation, in the shape `security.rate_limit_backend` already uses for the other control with a one-host window. Two changes make the substitution real rather than nominal: the interface is **async**, because a network backend cannot be made synchronous and offloading to a thread is the file store's business rather than its caller's; and a `Reservation` no longer carries a `Path`, so nothing filesystem-shaped reaches the middleware. Proven by a test that drops an in-memory backend into the running application and replays a request through it with no change to `api/idempotency.py`. **No shared backend ships** — whether to add one or to require shared storage is TASK-0357's open decision, and nothing in the documented behaviour depends on it.

- **`Idempotency-Key` on every mutating endpoint** (2026-11-08, closes TASK-0318). Any `POST`/`PUT`/`PATCH`/`DELETE` may now carry the standard header: `POST /v1/ingest`, the DLQ retry, collection create and delete, `doctor/fix`, provisioning up and down, export and import. A replay returns the original response byte for byte with `Idempotent-Replayed: true`, and every keyed response echoes `Idempotency-Key` back. The header is optional and inert — a request without it is passed straight through and touches no store — so no existing client changes behaviour.
  - **Scope is `(tenant, key)` over a fingerprint of method, path, query string and body.** A key names one request, so reusing it for a different body, or on a different endpoint, is `422 IDEMPOTENCY_KEY_REUSED` rather than the wrong endpoint's answer returned as a success. Two tenants that both choose `retry-1` never meet.
  - **The concurrent duplicate is handled, which is the case that usually ships broken.** The reservation is an `O_CREAT | O_EXCL` create, so exactly one of two simultaneous copies wins and the loser is refused `409 IDEMPOTENCY_IN_PROGRESS` with `Retry-After: 1` instead of executing. `tests/unit/api/test_idempotency.py` drives both copies through the real ASGI stack and asserts the handler ran once.
  - **Only 2xx is remembered**, so a `503` can be retried under the same key and a `422` can be resent with a fixed body. Errors release the key, as does a success larger than 256 KB.
  - **Lifetime**: 24 hours for a completed record, a 15-minute lease for an unfinished one so a killed worker does not hold a key for a day. Expiry is lazy. Both are configurable, with the kill switch, under `reliability.idempotency` (TASK-0356, below).
  - **`/v1/query`, `/v1/retrieve`, `/v1/estimate` and `/v1/replay` are deliberately excluded** — they are `POST` for the body, not for an effect, and `/v1/query` can be an SSE stream that cannot be captured and replayed. A key sent to one is ignored, not refused.
  - **Implemented as middleware over a service**, not as a per-route dependency: the failure mode of forgetting a route is then an endpoint that is silently not idempotent, which is how this gap persisted. A mutating router added later is covered when it is mounted. New error codes `IDEMPOTENCY_KEY_REUSED` and `IDEMPOTENCY_IN_PROGRESS` join the stable table in [api-reference.md](api-reference.md).
  - **Known limit, stated rather than hidden**: records are files under the ingestion journal root, which covers every Gunicorn worker on one host — a deployment spread over several hosts needs that directory on shared storage, or idempotency is per host. The store is an interface with one filesystem implementation (TASK-0357, below), so a shared backend is a second class rather than a change to any caller.

### Deprecated

- **`idempotency_key` as a `POST /v1/ingest` body field** (2026-11-08, TASK-0318). Superseded by the `Idempotency-Key` header, which is what a client library already knows how to send. **It still works and is removed in 1.0.** Both may be sent together; the header is resolved first, in middleware, so the body field never sees a header replay. A request that uses the field gets `Deprecation: true` and `Link: <...>; rel="deprecation"` on its response, and the field is flagged `deprecated` in `/openapi.json`. The two are not equivalent: the field dedupes only the job and compares nothing about the rest of the request, while the header replays the original response and refuses a changed one.

### Security

- **Supply-chain statements made true** (2026-11-12, TASK-0496). `security.md` said images are pinned by digest, that dependency updates run the full test pyramid, and that an SBOM is generated at each release; none had anything behind it, and there was no licence check. Now: the container image installs exactly `uv.lock` (`uv sync --locked`) on digest-pinned `python:3.12-slim` and `uv` bases, so **an image build fails if `uv.lock` is out of date with `pyproject.toml`**, and `--build-arg EXTRAS=` takes a comma-separated list; Dependabot opens grouped weekly pull requests for uv, Actions and Docker (squash-merge them under the PR title — their own commits carry a body, which the commit-message rule refuses); a new CI step fails on a dependency licence outside an Apache-2.0-compatible allow-list, currently 147 allowed and 20 accepted by named, unconfirmed exceptions (NVIDIA CUDA packages reached through torch, `psycopg` under LGPL-3.0, `pypdfium2`); and every third-party action is pinned by full commit SHA, each to the commit its floating tag pointed at, so behaviour is unchanged. Proven by `tests/unit/scripts/test_check_licences.py` and `test_every_workflow_and_composite_action_pins_its_actions_to_a_commit`.

- **`app.host` now defaults to `127.0.0.1`** (2026-11-11, TASK-0432). `security.auth` defaults to `false`, so the previous default of `0.0.0.0` made a fresh `fasterrag serve` an unauthenticated service on every interface, through which any reachable caller could ingest a server-side file and query it back. The container image and both compose services already pass `--host 0.0.0.0` and publish on loopback, so they are unaffected. `fasterrag serve` prints a warning when it binds a non-loopback address with auth off. **Upgrade note**: a deployment that relied on the old default must now set `app.host` or pass `--host` — and should enable `security.auth` when it does.
- **`POST /v1/estimate` is confined to `ingestion.allowed_source_roots`** (2026-11-11, TASK-0432). It parses the files it is given and applied no path guard, so it reported the existence, size and token count of any path on the server. It also parsed the whole corpus on the event loop; it now runs in a worker thread.
- **A bearer token containing a non-ASCII byte is refused with 401** (2026-11-11, TASK-0432); `secrets.compare_digest` raised `TypeError` on such a `str`, and an unauthenticated caller received an unhandled 500. Keys are compared as bytes.
- **The semantic cache no longer answers across collections, filters or `top_k`** (2026-11-11, TASK-0433). Its lookup matched on the query vector and tenant alone, so a question asked under one metadata filter could be answered from an entry stored under another. Entries carry a scope digest; entries written before this change can no longer hit.

- **The retrieval path was not tenant-scoped, and `security.tenant_scoped_retrieval` (default `false`) is the opt-in that scopes it** (2026-11-09, TASK-0339 — the filter half; the model choice is still a maintainer decision). Two tenancy models were running side by side and neither covered retrieval: `scoped_name` was applied by `/v1/collections` and `/v1/admin` and by nothing else, while `workers/indexer.py` wrote a `tenant` field into every payload that nothing read. `services/querying.py` contained the string `tenant` zero times. **Observed, not inferred** — `tests/unit/api/test_query_tenancy.py` drives the real router, the real `AuthMiddleware` and an in-memory adapter holding one chunk per tenant: with `auth` and `multi_tenancy` on, an `acme` key retrieved `globex`'s chunk by naming `globex__docs`, retrieved both tenants' chunks from the unnamed shared collection, and had `POST /v1/query` put another tenant's text into the answer **and into `citations`**. The filter each leg received was `None` in every case; `/v1/retrieve` took no tenant dependency at all.
  - **With the flag on, the tenant is injected below the caller's `filters`**, in `services/querying.py` after `validate_filter`, at the one point where a single filter object reaches *both* legs — so a request body cannot widen it and no later change can scope one leg and forget the other. A body naming the `tenant` field is refused `403 TENANT_FORBIDDEN` rather than silently overridden, and a retrieval with no tenant is refused outright.
  - **The caller could also plant the field at ingest.** `chunk_payload` merged the job's `metadata` after writing the tenant, so `metadata={"tenant": "globex"}` relabelled a job's own chunks into another tenant's filtered view. The credential now wins; a job with no tenant is unchanged, so an untenanted deployment that uses `tenant` as a metadata label keeps it. The field also has one spelling now, `services/tenancy.TENANT_PAYLOAD_KEY`, shared by the writer and the reader.
  - **Off by default because it changes what an existing corpus answers**, not because it is unfinished: chunks indexed before `multi_tenancy` was on carry no `tenant` field, and an absent field never matches, so an unbackfilled collection returns empty results. Backfill, and add a backend payload index on `tenant`, before enabling; nothing here creates that index. The flag requires `auth` and `multi_tenancy` and is refused at configuration load without them. The in-process facade and CLI carry no credential, so with the flag on they refuse; `POST /v1/replay` now passes the trace's own tenant, so it retrieves as that tenant and its spend is charged there rather than to the untenanted bucket. The semantic cache is looked up before retrieval and is already tenant-tagged, but entries written before the flag was enabled were produced by cross-tenant retrieval — clear it when enabling. [security.md](security.md) §3 carries the full account, including the claim it corrects.

### Fixed

- **Embedded Chroma calls time out** (2026-11-12, TASK-0476). A wedged embedded Chroma store held a query forever. `reliability.timeouts.vector_db_ms` now bounds every Chroma call, raising the same retryable provider error pgvector raises; at most four calls hold a thread at once, so a store that wedges cannot take the whole thread pool. Proven by `tests/unit/adapters/test_chroma.py::TestCallTimeout`.

- **A Redis that never answers no longer holds requests** (2026-11-12, TASK-0453). Neither Redis client set a socket or connect timeout, so a server that accepted connections and never replied held queries and authenticated requests for as long as the installed redis-py allowed — indefinitely on the 5.x releases the dependency range admits, 5 s per call on the locked 8.1.0. New key **`reliability.timeouts.redis_ms`** (default 1000) sets both timeouts on the cache and rate-limit clients, so a hung server degrades as a stopped one does: the cache misses and the limiter fails open with a WARNING. A single cache read is now 2 round trips instead of 3, and a write 2 instead of 4. Proven by `tests/unit/core/test_redis_timeouts.py` against a real socket that never replies.

- **The circuit breaker admits one probe, not everyone** (2026-11-12, TASK-0450). When the reset timeout expired, every waiting caller went through at once, although the breaker's own docstring promised a single probe, and a call admitted before the circuit opened could close it again with a late success. `check()` now returns an admission token stamped with the state's generation; half-open issues exactly one token, outcomes from an earlier generation are ignored, and a probe that never reports back loses its slot after `reset_timeout_ms`. **Internal API change:** `record_success` and `record_failure` take the token `check()` returned. Proven by `tests/unit/core/test_breaker.py::test_n_waiters_on_an_open_circuit_admit_exactly_one_probe`, `::test_threads_racing_into_half_open_admit_exactly_one_probe` and `::test_a_late_success_from_before_the_outage_does_not_close_it`.

- **A job left `running` by a process exit stayed `running` for ever, and shutdown drained nothing** (2026-11-12, TASK-0436). Ingestion ran as a background task nothing referenced, and `asyncio.CancelledError` was caught by no handler, so a stopping process closed its adapters under running jobs and left their records `running` for good; nothing looked for such jobs afterwards and nothing could resume one. Now jobs run as tasks held by a registry (`services/jobs.py`). **On shutdown** the API refuses new jobs with 503 `NOT_READY`, waits `reliability.shutdown_grace_seconds` (default 20), cancels the rest and only then closes its adapters; a cancelled job stops both halves of its pipeline, waits for a checkpoint write already in flight, and is settled `failed` with the new `reason_code: INTERRUPTED` (a new field on the job record and on `GET /v1/ingest/{job_id}`). **On startup** a server settles `running` jobs whose record and document log have been quiet for `reliability.stale_job_seconds` (default 120), and looks a second time one window later, so an orphan from a crash seconds before the restart reads `running` for up to that long. **On request** `fasterrag ingest --resume <job_id>`, or a replay of the job's `idempotency_key` body field, runs it again from its checkpoint; `--metadata` and `--priority-class` are not stored with a job and must be passed again. Nothing resumes on its own, and the `Idempotency-Key` header does not resume — the middleware answers it from the stored response. **Operators should know:** `docker stop` kills after ten seconds by default and the compose files set no stop period, so the default grace is cut short in a container until one is set; and under uvicorn the listening socket closes before the drain begins, so a client sees a refused connection, not the 503. Proven by `test_a_job_that_outlives_the_grace_period_is_cancelled_and_settled`, `test_nothing_keeps_working_on_a_cancelled_job`, `test_a_stale_running_job_is_settled_and_a_fresh_one_is_left_alone`, and the kill-and-restart drill `test_a_killed_process_leaves_no_job_running_after_a_restart`.

- **The embedding cache was implemented and wired to nothing** (2026-11-12, TASK-0442). `embeddings.cache.enabled` had no effect. Wiring the cache as it stood would have been wrong: its key ignored the provider, `embeddings.dimensions` and whether a text was embedded as a document or as a query; it read and wrote one entry at a time; and the disk store listed its whole directory on every write. The key now includes all of those; stores gained `get_many`/`set_many` (two round trips per batch on Redis, one thread hop on disk); disk eviction is counted and amortised, with the entry ceiling unchanged. The cache is applied in the new `services/composition.py`, which every entry point now uses. The wrapper reports its provider's name so spend is still priced, keeps late chunking working, and never caches pooled vectors. **What an operator will notice:** with the default settings every embedding now writes a file under `.fasterrag/cache/embedding/` in the working directory, apart from a disk semantic cache; `fasterrag_cache_events_total{cache="embedding"}` is emitted for the first time; the query benchmark runs with the embedding cache off; and entries written under the old key format are never served again. Proven by `test_reingesting_an_unchanged_corpus_with_dedup_off_makes_no_provider_calls`. The cost of the default disk write on the embedding path is unmeasured (TASK-0516).

- **Three provider adapters did not work against the libraries they wrap** (2026-11-12, TASK-0441). They had been written against hand-built fakes. Run against the real client libraries with recorded replies: the **Cohere generator** built the v1 `AsyncClient` and called `chat(messages=…)`, a `TypeError` on every call — reported as "unreachable, retryable" and so served as a degraded answer indefinitely; the **Ollama generator** looked for a `dict` where `ollama>=0.4` returns typed objects and returned empty text and an empty stream with no error; the **Ollama embedder** raised "returned an empty embedding" on every call. The Cohere embedder was sound. The Cohere generator now builds `AsyncClientV2`; the Ollama adapters read typed responses; the Ollama embedder uses the batch `/api/embed` route, reports token counts, and borrows `llm.base_url` only when the LLM is Ollama too (before, it sent embedding requests to whatever `llm.base_url` named, including an `openai_compatible` gateway). A `TypeError` or `AttributeError` raised while an LLM adapter drives its client is now a non-retryable `INTERNAL` error, not an outage. Floors are `cohere>=5.8` and `ollama>=0.4`, measured by replaying the recordings through older releases, and both libraries are in the `dev` extra so the tests that import them run in CI. Proven by `tests/unit/adapters/llm/test_real_clients.py` and `tests/unit/adapters/embeddings/test_real_clients.py`; each hand-written fake is now held to the real object's shape by a fidelity test. **Limit:** the recordings follow the vendors' API references and were not captured from live servers.

- **A parser that hung stalled its job for ever** (2026-11-12, TASK-0473). The pool future was awaited with no timeout. `ingestion.parse_timeout_seconds` (default `600`; `0` restores the old unbounded behaviour) now bounds each document's time in the pool, counted from submission. A running process-pool task cannot be cancelled, so an overdue document costs its pool: the workers are killed, a new pool is started and warmed, documents that were in flight beside it are parsed again with a fresh deadline, and the overdue one alone is dead-lettered as `PARSE_TIMEOUT` (a new error code, 422, seen only as a dead-letter reason). **The default is on**: a legitimately slow document — long OCR, for instance — that needs more than ten minutes is now dead-lettered where it used to finish; raise the key for such corpora. The pool now also starts one worker before it accepts documents, so a pool that cannot start says so at once. Proven on the real pool by `test_a_hung_parser_costs_one_document_and_its_worker_is_recovered` and `test_documents_in_flight_beside_a_hung_one_are_parsed_again_not_lost`. The cost of a recycle is unmeasured.

- **An empty document was recorded as indexed, and its hash poisoned deduplication** (2026-11-12, TASK-0470). A document that parsed to zero chunks — zero bytes, or whitespace only — was journalled `indexed` and the hash of empty content was written to the dedup file, so every later empty file was reported `deduplicated` against a document the index never held. Reproduced before it was fixed. Such a document is now `skipped` with reason `EMPTY_DOCUMENT`: decided before the dedup check, settled without a commit, counted apart (`counts.skipped`, and `status="skipped"` on `fasterrag_ingest_documents_total`), and not a failure — a job of nothing but empty files is `completed`. A dedup file written by an earlier version is harmless, because emptiness is checked first. `GET /v1/ingest/{job_id}/documents?status=skipped` lists them. Proven by `test_an_empty_document_is_skipped_rather_than_recorded_as_indexed` and `test_an_empty_document_never_enters_the_dedup_file`.

- **`answer()` and `stream()` were two hand-kept copies of one pipeline, and they had diverged** (2026-11-12, TASK-0438). A streamed query over its token budget got `meta` and then an SSE `error` over HTTP 200. A retryable provider failure ended a stream with `error` where the JSON path served the extractive rung. The streamed path recorded no `generation` span, stored no trace for a withheld answer, never incremented `fasterrag_degraded_responses_total`, and reported neither `truncated` nor `evidence_dropped`. Now `GenerationService._pipeline` runs every query and yields typed stages; `answer()` collects them and `stream()` maps them to events. The budget is charged before the first stage and the router awaits the first event before answering, so a refusal — or any failure before `meta`, such as a retrieval failure — is the same status and problem document as with `stream: false`. A retryable failure before any `token` is sent serves `extractive` on a stream: a second `meta` announcing `mode: extractive, degraded: true`, the passages, `citations`, `usage`, `done`; after the first token it is `error` without `done`, because sent text cannot be taken back. `usage` now carries `mode`, `degraded`, `truncated` and `evidence_dropped`; `meta` always carries `cache`. **What a client will notice:** response headers for a stream are sent after retrieval rather than immediately, and a consumer that stops at `done` still leaves a trace. Proven by `tests/unit/services/test_generation.py::test_both_surfaces_leave_the_same_outcome` — eleven cases through both surfaces; it failed seven of nine against the old code — and `tests/unit/api/test_query.py::test_a_streamed_query_over_the_budget_is_a_402_problem_not_an_event_stream`. Not changed: streamed token counts remain local estimates and streamed `truncated` is inferred from them (TASK-0458).

- **Running the test suite from a commit hook in a linked worktree modified the real repository** (2026-11-12). git exports `GIT_DIR` and its siblings to a hook, and the pre-commit hook runs the unit tier. In a linked worktree `GIT_DIR` names the real repository, so five tests in `tests/unit/services/test_ci_status.py` that build a throwaway repository in a temporary directory ran `git init` and `git remote add` against the real one: they failed in every worktree, and `git init` set `core.bare = true` in the shared configuration, which left the main checkout refusing every work-tree command until it was reset by hand. Found when seven parallel worktrees all failed their first commit. `tests/conftest.py` now removes the variables git exports to a hook for the whole test process, at import. Proven by `tests/test_git_environment_is_clean.py`, and by running the affected module with `GIT_DIR` set: 5 failed before, 67 passed after, configuration untouched.

- **Four documents described behaviour the code does not have, found while verifying facts for the task briefs** (2026-11-12). `security.md` §6 said an SBOM is generated at each tagged release, that images are pinned by tag or digest, and that dependency-update pull requests run the full pyramid — there is no SBOM tooling, the `Dockerfile` base is pinned by tag and installs outside the lockfile, and nothing opens such pull requests (TASK-0496). `cookbook.md` recommended running `fasterrag worker` as a separate process with no note that it does no work (TASK-0440). `architecture.md` §9 said chunks record a document version and an ingestion timestamp and that identical content is version-bumped; the payload stores neither (TASK-0443). `prompts.md` said the P1 and P3 template versions are part of the trace `config_snapshot`; they are not (TASK-0446). Each now carries a dated status note citing the open task.

- **Two journal writes for one job could collide, which the ledger introduced and its first real-backend run caught** (2026-11-11, TASK-0427 follow-up). Once "indexed" was decided on the embedding side, a checkpoint could be triggered there and on the parse side (a dead-lettered document settling) at the same moment, and the journal rewrites a job record through one fixed temporary file name — so the second rename failed with `FileNotFoundError` and the job stopped. It passed the unit tier and one CI run by timing and failed the next in `tests/integration/test_ingest_pipeline.py`. Every journal write of a job — commits, checkpoints, and the parse side's dead-letter and dedup records — now takes `IndexLedger.journal_lock`. The underlying weakness, a shared temporary file name with no lock for writers in *different* processes, is unchanged and stays open as TASK-0437.
- **A document whose embedding failed was remembered as indexed, so retrying it did nothing** (2026-11-11, TASK-0427). `record_indexed` and the dedup hash were written when the chunks were enqueued. The retry found the hash, reported the document `deduplicated`, and it was never indexed; a crash between enqueue and upsert left the same lie in an append-only file. A failed document is now dead-lettered once (it was once per chunk) and leaves no dedup entry.
- **Parsing ran one document at a time behind a process pool** (2026-11-11, TASK-0428). Each document was awaited before the next was submitted. Up to `workers.cpu_pool_size` documents are now in the pool at once, consumed in submission order. No throughput figure is claimed for this; it is unmeasured (TASK-0454).
- **A parser raising an untyped exception aborted the whole job** (2026-11-11, TASK-0428). It is converted to `PARSE_FAILED` inside the worker and costs one document.
- **A refused vector-database write ended the embedding worker and could hang the job forever** (2026-11-11, TASK-0429). The write sat outside the retry block; the batch was lost with no dead-letter entry, and once every worker had died the parser blocked on a full queue. Writes are retried when retryable and otherwise recorded as per-document failures; the parse side and the embedding side now fail together.
- **A job could be left `running` forever** (2026-11-11, TASK-0429). `IngestionService.run` settles the job `failed` before re-raising any exception, typed or not, and the API's background runner guarantees a terminal status. Staged sources and the enrichment client are released in `finally`.
- **`chunking.strategy: semantic` dead-lettered every document of a corpus** with the same configuration error. The job is now refused before it is recorded, with the strategies that do run named in the message; running it in the pipeline remains open (TASK-0431).
- **The reranker model was reloaded for every REST query, and no circuit breaker could open on the REST path** (2026-11-11, TASK-0430). Both were instance state on objects the API builds per request.
- **A streamed query stored no trace**, so replay had nothing for the default path (2026-11-11, TASK-0434).
- **The README and quickstart Python examples failed as written** — a `wait()` method `JobRecord` never had, and a folder the facade did not expand (2026-11-11, TASK-0435).

- **Journal I/O ran on the event loop, and stalled every other request on the worker** (2026-11-11, closes TASK-0399). `IngestionService.accept` called the synchronous `Journal.create_job` from inside an `async def`, so an ingest submission's file reads and writes happened on the thread serving every other request. TASK-0358 measured what that costs when the deprecated `idempotency_key` body field triggers the journal scan — **633 ms p50 at 10,000 jobs** — but the defect was never confined to that path: `save_job` wrote on the loop for *every* submission, keyed or not, and the same shape was in `load_job`, `counts`, `documents`, `dead_lettered`, `record_document`, `remember_content` and `known_content`, reached from `GET /v1/ingest/{job_id}`, its `/documents` and `/retry-dlq` siblings, the background job runner and the per-document parse loop. CLAUDE.md requires all I/O paths to be `async`; this was a standing violation with a measured price.
  - **The offload lives inside the journal, not at each call site.** Every filesystem operation is now an `async` method that runs a public `*_blocking` twin in a worker thread — the shape `FileIdempotencyStore` already took under TASK-0357 (`begin`/`claim`) and `core/cache/store.py` before it, on the reasoning that whether a backend needs a thread is the backend's business. The alternative the ledger named — an `asyncio.to_thread` at each caller — was rejected because it is a rule a future caller must remember and forgetting it is silent; **every** production caller of the journal was already inside a coroutine, so there was no synchronous caller for a two-sided interface to serve except tests, the CLI's own fakes and the benchmark harness, which is exactly what the twins are for.
  - **Composite operations are one thread hop, not several.** `create_job` covers the key lookup and the write together; `dead_letter` covers the record and its log line; and the per-document pair — a `documents.jsonl` append plus a dedup-hash append — was given a single `record_indexed` method precisely so the hot loop pays one handoff instead of two.
  - **Measured before and after, in one process, back to back** (BENCH-0006 in [benchmarks.md](benchmarks.md), non-citable hardware). A heartbeat coroutine sleeping 5 ms at a time served **19** wake-ups across six accepts while the blocking call was on the loop and **234** with it offloaded — 12× — and the lag p95 fell from **601 ms** to **11.3 ms** against an idle floor of **11.5 ms**, i.e. to indistinguishable from nothing happening at all. The caller still waits: nothing here makes the scan faster, and TASK-0358 decided not to index it.
  - **The offload is not free on the per-document path, and that is reported rather than assumed.** `record_indexed` costs **1.887 ms p50 blocking** and **2.422 ms p50 off the loop** — **+0.54 ms, +28%** for the handoff, on something that runs once per document. It is paid deliberately: it buys back 1.9 ms of loop-blocking per document on a worker that is also serving API traffic, and the single-hop pairing above is what keeps it to one. This is the trap TASK-0365 recorded — a thread handoff on a tight loop can cost more than the call it moves — and it was measured rather than waved away.
  - **Forgetting it later fails the build.** `tests/unit/test_no_blocking_journal_in_async.py` walks every module under `src/` with `ast` and fails if a coroutine calls a `*_blocking` twin, with its own case proving the guard catches the defect it was written for. `mypy --strict` catches the rest, since a synchronous caller cannot use a coroutine's return value.
  - **Not fixed, and listed rather than left to be found**: `LockStore.write` (once per settled job, offloaded at the one call site with a `# TODO` naming the follow-up, because the lock store still has synchronous callers in `facade.index_lock`, the CLI and `archive_import`), `TraceStore.load`/`recent` (per request on `GET /v1/traces` and `/v1/traces/{id}` and `POST /v1/replay`, and `recent` is O(traces) when tenant-scoped), the archive reader and writer (per `POST /v1/admin/export` and `/import`), `resolve_sources`' staging writes, and `services/backup.py` and the provisioning writers on the CLI's loop.

- **`FileIdempotencyStore` leaked one file per keyed request, and now reclaims them** (2026-11-11, closes TASK-0365). Expiry was lazy: `_expired` was consulted only inside `claim`, on a `FileExistsError` for that exact path, so only a key that came back was ever cleaned up — and the usage the docs recommend, a fresh UUID per request, never brings one back. Every keyed request therefore left a permanent file under `.fasterrag/journal/idempotency/`, in a feature that is **on by default**, and `ttl_seconds` bounded how long a record was *replayable* rather than how long its file existed, so the setting an operator would reach for did not help. `FileIdempotencyStore.reclaim` removes records a grace minute past their lifetime, records that fail their checksum, and `*.tmp` files a crash left behind — a second leak in the same directory, found while fixing the first.
  - **It runs beside a request, not inside one.** `begin` starts the pass as a task and does not wait for it, and every step runs in a worker thread, so neither the caller nor the event loop waits for a directory walk. The alternative the ledger proposed — an opportunistic prune of the tenant bucket on write — was rejected on a measurement, not on taste: a pass costs one cold file open per record removed, which is **seconds** once a day of garbage has accumulated, and charging that to an ordinary request is worse than the leak (BENCH-0004 in [benchmarks.md](benchmarks.md)). The steady-state walk that finds nothing is **21.8 ms over 8,200 records** — 2.65 µs each, because an entry too young to be expired is rejected on its `mtime` and never opened. A concurrent claim measured against a pass running in another thread pays **+0.07 ms at p50 and +0.27 ms at p95**, with a **16 ms worst case** in 200 samples: the median cost is small and the tail is not, and both are recorded.
  - **One worker of N sweeps per interval.** The right to sweep is taken as one more record under `O_CREAT | O_EXCL` (`.sweep.json`), re-taken when its holder dies, so several Gunicorn workers sharing a directory do not each walk it. The due check before that is an in-process timestamp, so a request that is not due performs no filesystem operation at all.
  - **A record is removed only once it has been expired for a minute.** `claim` takes an expired record over by rewriting it in place, so unlinking on expiry alone could delete a fresh reservation a concurrent takeover had just written and free a key whose request is still running. The margin plus an envelope re-read immediately before the unlink narrows that window to a read and a syscall; it does not close it, and the residual is written down in [api-reference.md](api-reference.md) §Reclamation rather than left to be discovered.
  - **It is not on the `IdempotencyStore` interface**, because a backend that expires keys natively has nothing to sweep (TASK-0357). The one thing that did join the interface is `close`, which is resource release rather than reclamation and is what `core/rate_limit.py` already names; the API lifespan calls it so shutdown never leaves a pass orphaned. Empty tenant directories are deliberately left in place: removing one races the `mkdir` every write performs.

- **`cost.per_tenant_token_budget` could not be reached through the REST API** (2026-11-09, closes TASK-0337). `api/query.py` builds a `GenerationService` per request and the service built its own `CostGovernor` in `__init__`, so the rolling 24-hour window was created and discarded **once per request** — accounting that looked like a spend cap and enforced nothing. The caveat in [config-reference.md](config-reference.md) said "N replicas grant N times this budget"; the real multiplier was one window per request. Separately, TASK-0312 had charged embedding spend to the process-wide `shared_governor`, so ingest recorded into one window while queries checked another and never saw it. The service now takes `shared_governor`, which is the same instance the embedding pool records into, and accepts an injected governor for tests. **`cost.per_query_token_budget` was never affected** — it is stateless, so a window rebuilt per request enforced it exactly as configured, and a test pins that it still does.
  - **The shared-governor cache key was a subset of its inputs** and is now read off the governor's own dataclass fields, so a configuration field added later joins the key instead of letting two differently-configured governors become one. Keying on the whole `cost` section was rejected: it would split the window over `cost.estimator`, giving two windows and twice the budget — the direction of error that permits more than was configured.
  - **A tenant whose spend ages out is now forgotten.** The governor's map only ever grew, one entry per tenant seen; harmless while the instance died with the request, a slow leak keyed on client-chosen input now that it lives as long as the process.
  - **Proof, not inspection.** `tests/unit/services/test_budget_sharing.py` drives the cap through repeated `GenerationService` calls — a new service per query, as a request does — and asserts the refusal, and runs a real `EmbeddingWorkerPool` ingest and then asserts a later query is refused on what the ingest spent. Both fail against the previous implementation; the per-query test passes against it, which is how the gap stayed invisible.

- **`Journal.find_by_idempotency_key` was not tenant-scoped** (2026-11-08, TASK-0318). It globbed every job record on the host and matched on the key alone, so under `security.multi_tenancy` a tenant replaying a key another tenant had used was handed **that tenant's job id** and had its own ingest silently dropped — an id disclosure and a lost corpus from one collision on a client-chosen string. The lookup now matches tenant as well as key, so an untenanted deployment behaves exactly as before and two tenants cannot collide.

### Changed

- **The import direction between layers is enforced** (2026-11-12, TASK-0456, partly). `scripts/check_layering.py` reads every import in the package at any depth — including function-level imports, which had hidden the cycles — and fails CI on any import that points up the layer order; the violations that remain are named as a backlog, and an exception nothing matches fails too. The service builders moved out of the REST layer into `services/composition.py`, which the API, the CLI, the Python facade and the eval harness now share, so **`import fasterrag` and the `FasterRag` facade no longer load FastAPI or Starlette** — the prerequisite for making the web framework an optional install (TASK-0444). Proven by `test_the_facade_builds_its_services_without_the_web_framework` and the gate's own `test_the_repository_breaks_the_contract_only_where_it_says_it_does`.

- **The REST API reuses one LLM provider client** (2026-11-12, TASK-0466). `POST /v1/query` built a new provider client for every request and closed it when the answer was sent. The API now builds one adapter per application, on first use, lends it to each request's `GenerationService`, and closes it once at shutdown. Services stay per request because they carry the caller's tenant. Proven by `tests/unit/api/test_shared_llm.py` and `test_two_tenants_answered_through_one_shared_llm_each_see_only_their_own`.

- **`cost.per_tenant_token_budget` is now accurate to within an hour, and errs only towards refusing** (2026-11-11, closes TASK-0366). The rolling window held one `(timestamp, tokens)` entry per charge, which TASK-0337 turned from a per-request structure into a process-lifetime one. Measured before deciding (BENCH-0005): **122.5 bytes per charge**, so one tenant at 1M charges a day held **116.8 MiB**, every `check` summed the lot at **128 ms p50**, and the writer was quadratic because it pruned by calling a method that also summed — **127 ms** to charge a single request at that fill, paid by ingest as well as by queries. Spend is now accumulated into at most 26 hourly buckets per tenant (**4,862 bytes**, flat at every scale; read **7.5 µs**, charge **3.6 µs**). **The behaviour change is in one direction only**: a bucket is dropped once its *newest* charge ages out, so no charge is ever forgotten early, the amount counted inside the window is unchanged and still exact, and a tenant can stay refused for up to an hour after an exact 24-hour window would have released its budget. It can never be admitted past the cap. Operators who set this expecting a to-the-second window should read the revised entry in [config-reference.md](config-reference.md).

- **Portability archive `format_version` `x.1` — migration note** (2026-11-11, closes TASK-0329). `checksums.sha256` now covers `manifest.json`, and an export declares `2.1.0` when it carries the keyword leg and `1.1.0` when it does not. Until this change the manifest was written *after* the checksums member and so was covered by nothing — while being the member the vector-copy guard reads, so an archive whose `embedding.model` had been rewritten and repacked passed verification and then permitted a copy of vectors from one embedding space into another.
  - **Who must act.** Anyone holding an archive written before this build: a `1.0.0` or `2.0.0` archive is **refused**, because its manifest is unverified. Convert it by appending `<sha256 of manifest.json>  manifest.json` to `checksums.sha256` and raising the manifest's minor to `1`; no data member changes. Re-exporting produces the same thing.
  - **Why the requirement is unconditional** rather than gated on the declared version: the manifest is the member being verified, so a reader that asked it whether it must be checksummed would accept a stripped line beside a lowered `format_version`.
  - **Why a minor and not a major.** `checksums.sha256` has been read as a *list* of names by every reader that ever shipped, so an older reader handed a `x.1` archive verifies the manifest too and drops nothing — which is the test this format applies to a major bump.
  - **What it is not.** Checksums are integrity, not authenticity: they stop a corrupted or partially rewritten archive, not someone who repacks the whole file and recomputes the list. A second rule raises that cost — the manifest's embedding and chunking fields must agree with the archived `index.lock`, which is where they came from — and only signing would settle it. The format does not sign yet.
  - **One deliberate consequence**: `checksums.sha256` now differs between two exports of an unchanged collection, because the manifest carries `created_at`. Every other member stays byte-identical.

- **The portability manifest records the tenant-visible collection name** (2026-11-11, closes TASK-0340). `collection.name` was written as the backend's scoped name, so an archive exported by tenant `acme` said `acme__docs`; import then scoped it again into `acme__acme__docs` and answered `200` with a backend-prefixed name. The exporter unscopes before building the manifest — a no-op for a single-tenant deployment and for the CLI — and `tenant` keeps the provenance. An archive is therefore portable between tenants: one exported by `acme` imports under `globex` into `globex__docs`, which is the chosen property, since an archive is a corpus and not a grant.

- **Portability archive `format_version` 2.0.0 — migration note** (2026-11-04, TASK-0302). A `.fragx` now carries the keyword leg: each `vectors.jsonl` row may hold an optional `sparse` object (`indices`, `values`), and the manifest declares `includes_sparse`. **The bump is conditional** — an export with no postings still declares `1.0.0` and writes byte-for-byte what it wrote before, so an archive that gained no new data is not stranded over a feature it does not use.
  - **Who must act.** Nobody, to keep reading old archives: this build accepts majors `1` and `2`, and a 1.0.0 archive still has its keyword leg recomputed from chunk text under the target's `bm25_k1`/`bm25_b`, exactly as before. `--reembed` also keeps recomputing, by design.
  - **What breaks, deliberately.** A reader older than this change accepts major `1` only, so it **refuses** a 2.0.0 archive instead of importing it. That refusal is the point: such a reader validates only the major and ignores unknown fields, so without the bump it would import a hybrid archive and silently rebuild the keyword leg with different BM25 parameters — a collection that ranks differently from its source, with nothing anywhere reporting it. A loud refusal is the cheaper failure.
  - **Converting 2.x → 1.x** (for an older reader): drop `sparse` from every `vectors.jsonl` row, set `format_version` to `1.0.0`, remove `includes_sparse` from the manifest, and recompute `checksums.txt`. The keyword leg is then re-derived on import rather than transplanted. Specified in [archive-format.md](archive-format.md) §Versioning.
  - **Not verified against a real backend.** Every test covering this runs against fake adapters. The assertion that matters — that a restored collection's keyword *ranking and float scores* match the source's, with the source indexed at non-default `k1=0.4, b=0.1` so a recompute could not match — is `tests/integration/test_archive_round_trip.py::test_the_keyword_ranking_and_scores_survive_the_round_trip`, and all twelve tests in that file skip for want of a Docker daemon. No archive has carried a keyword leg through a real vector database.

- The `redis` cache backend (2026-08-09, closes TASK-0124): `embeddings.cache.backend` and `cache.backend` have accepted `redis` since the schema was written and have refused to start on it ever since; both now work, behind `pip install fasterrag[redis]` and the new `embeddings.cache.redis_url` / `cache.redis_url`. - Build slice S7 — caching (2026-07-31): the embedding cache (`fasterrag.core.cache`), keyed by content hash plus model plus model version, so a stale hit after a provider silently upgrades weights behind a stable name is unrepresentable rather than merely unlikely. Implemented as a wrapper around any `EmbeddingAdapter`, so a third-party adapter registered through the entry point gets caching without knowing the cache exists. Batches resolve per text: a batch that is nine-tenths cached sends only the missing tenth, and vectors come back in the caller's order because retrieval matches vectors to chunks positionally. Vectors are stored packed as float32 rather than as JSON — roughly a fifth the bytes, on a cache sized in entries. And the semantic response cache, keyed by the meaning of a query rather than its text: a paraphrase whose query vector clears `cache.similarity_threshold` is answered from the response already given, short-circuiting retrieval, assembly, generation, and grading. A hit still streams — the whole answer arrives as one `token` event after `meta`, so a client needs no separate code path. Invalidation is TTL plus event: a corpus change drops every entry immediately, deliberately in full rather than selectively, because deciding which cached answers a new document could have changed would mean knowing what each answer was derived from *and* what the new document says, and a cache that guesses wrong there serves a confidently stale answer. Degraded answers are never cached, since caching a fallback would outlive the outage that caused it. Both caches obey FMEA row 23: every backend failure is caught, counted, and stepped past, so correctness never depends on a cache being reachable — only speed does. Hit, miss, invalidation, and error counters back `fasterrag_cache_events_total` ahead of the metrics export (TASK-0042). And the generation service (`fasterrag.services.generation`), which joins retrieval, assembly, and the provider into one answer path with two shapes: `answer` returns the whole response, `stream` yields the documented SSE event sequence — `meta` first so a client learns the trace id and any degradation before the first token, then `token` deltas, then `citations`, `usage`, and `done`. Usage arrives late because a streamed provider call cannot report token counts until it ends. A provider failure degrades to an extractive answer built from the retrieved passages rather than returning nothing, and a failure mid-stream emits `error` and stops without `done`, so a client can always tell a completed answer from a truncated one. And grounded-or-refuse (`fasterrag.core.faithfulness`, D5): a P3 grading call scores how much of an answer its context supports, and below `generation.faithfulness_threshold` the answer is withheld for a structured `INSUFFICIENT_EVIDENCE` response carrying the score, the threshold, and the candidates that were declined — so a caller told there is not enough evidence can see what evidence there was. Grading is a separate call from generation by contract, so the grader never sees the instructions that produced the answer and cannot self-justify, and it accepts a distinct adapter for a cheaper grading model. A grader that fails or returns unparseable output yields a `null` score, which never withholds: failing closed on a grader outage would turn a monitoring problem into an availability one. Refusal and streaming genuinely conflict, since a token cannot be unsaid — with the flag on, the stream therefore buffers and grades before emitting any token, trading time-to-first-token for the guarantee. The flag defaults to `false`, so that trade is only made on request; the behavior is recorded in `docs/api-reference.md` and flagged for maintainer review as TASK-0123.
- Build slice S5 — reranking and evaluation (2026-07-30): the retrieval regression gate (`fasterrag.services.regression`, D7), which compares a run against a committed baseline and blocks a drop beyond `eval.recall_tolerance` or `eval.ndcg_tolerance`. A baseline records the embedding model and retrieval-affecting config hash that produced it, and a mismatched one is refused rather than silently compared, because comparing across a model change measures the model rather than the change under test. A missing baseline blocks rather than passing, since a gate that waves through what it cannot check looks like protection while providing none. The cross-encoder reranker (`fasterrag.core.rerank`, public surface `fasterrag.rerank`), which reads query and chunk together over the fused shortlist and truncates to `retrieval.top_k`. A reranker that cannot load or score degrades the response to `hybrid_only` rather than failing the query, the first rung of the degradation ladder (D4). Candidates are only widened to `retrieval.rerank_top_n` when a reranker will actually consume them. The retrieval eval harness (`fasterrag.core.evals`, public surface `fasterrag.evals`) with the golden-set JSONL format shared by the harness, the regression gate, and Autopilot, plus recall@k, MRR, and nDCG@k. Adversarial records are counted separately rather than averaged in as zeroes, because a query the corpus cannot answer has no ground truth to score against and averaging one in would make a system that correctly refuses look worse than one that guesses. Document-level ground truth is honored alongside chunk-level, so a golden set survives re-chunking. Faithfulness is deliberately absent until the generation slice provides its call site.
- Build slice S4 — retrieval (2026-07-30): hybrid retrieval (`fasterrag.services.querying`) running the dense and keyword legs concurrently, both receiving the same pushed-down metadata filter so they search the same subset, and Reciprocal Rank Fusion (`fasterrag.core.retrieval.fusion`, public surface `fasterrag.retrieval`) combining them on ranks rather than scores at the documented k=60. Fusion runs in fasterRag rather than in the backend so `retrieval.rrf_k` and the leg weights are the values that actually apply. Results carry every leg's rank and score, not just the fused number, because the common retrieval question is why a chunk ranked where it did. Verified against a real Qdrant, including that the keyword leg retrieves an exact part number that dense search alone ranks poorly.
- Build slice S3 — ingestion core (2026-07-30): the parsing pipeline (`fasterrag.core.parsing`, public surface `fasterrag.parsing`) covering PDF with table extraction, type-size heading inference and an optional OCR path, plus HTML, Markdown, DOCX, plain text, CSV, and JSON — every format producing one structured `ParsedDocument` whose block offsets index exactly into its text, with committed golden-file snapshots pinning reading order, table structure, heading paths, and metadata. The chunking pipeline (`fasterrag.core.chunking`, public surface `fasterrag.chunking`) with all five configured strategies — fixed, recursive, layout, semantic, and late — sharing one assembler so the five documented invariants hold for every strategy, asserted property-based with Hypothesis. Embedding provider adapters (`fasterrag.adapters.embeddings`) for local sentence-transformers, OpenAI, Cohere, and Ollama behind one contract that separates document and query embedding, reports the model and version that drift detection anchors on, batches per `embeddings.batch_size`, and classifies provider failures without retrying — retry policy stays with the worker pool. The tiered-embedding router routes documents to cheaper or more precise models by metadata, reusing the vector database filter grammar so operators mean the same thing everywhere. The canonical identifier scheme (`fasterrag.core.identity`), including the deterministic document and chunk ids and the retrieval-affecting configuration hash the index lockfile anchors on. Checkpointed ingestion state (`fasterrag.services.journal`): job records written atomically with a checksum and a retained previous copy so a torn write degrades to resuming slightly earlier rather than losing the job, checkpoints at the configured interval, per-collection content-hash deduplication, idempotency-key replay that returns the original job, and a dead-letter queue whose entries carry a machine-readable reason code from the stable error table. The two worker pools (`fasterrag.workers`): a CPU pool that loads, parses, and chunks in worker processes and streams chunks downstream as each document completes, dead-lettering a bad document rather than failing the pass; a bounded queue that makes producers wait inside the pipeline but rejects with `QUEUE_FULL` at the API boundary; and a stateful embedding pool whose model is loaded once and reused across every batch, batching per `embeddings.batch_size`, routing tiered documents to their model, and retrying with exponential backoff and jitter only what a provider said was retryable. The indexer (`fasterrag.workers.indexer`), which closes the ingest chain: each embedded batch becomes one upsert carrying the dense vector, the BM25 sparse vector, and a payload mirroring the `Chunk` entity, so a citation's span and the model drift detection anchors on are written at index time rather than reconstructed later. The `VectorDBAdapter` contract gained optional sparse vectors on `CollectionSpec`, `Point`, and `SearchQuery` per ADR-0007, with the Qdrant adapter switching between the unnamed dense layout and the named dense-plus-sparse layout that hybrid collections require, and the shared contract suite now proves the keyword leg round-trips against a real backend. The ingestion service (`fasterrag.services.ingestion`), which runs both pools concurrently against one bounded queue so parsing and embedding overlap rather than running in phases, checkpoints as documents complete, resumes from the last checkpoint, dead-letters what the embedding pool could not place, and settles each job as completed, partial, or failed. An end-to-end integration test ingests a real corpus into a real Qdrant and retrieves it over both the dense and the keyword leg. The preflight cost estimator (`fasterrag.services.estimation`, D9), which parses and chunks a corpus for real — because token count depends on overlap and enrichment, not on file size — and reports documents, chunks, tokens, and projected embedding cost per provider before anything is embedded. Prices are dated list prices, and a model with no recorded price reports an unknown cost rather than a fabricated one; wall-clock time is deliberately not projected, because embedding throughput has not been measured yet and an unmeasured projection would be a claim without a measurement. The vector database health check is now registered with `/readyz`.
- Build slice S2 — Qdrant adapter and doctor v1 (2026-07-30): vendor-neutral `VectorDBAdapter` contract with its request and result types and a vendor-neutral metadata-filter grammar (`fasterrag.adapters.vectordb.base`); the provider factory, including third-party registration through the `fasterrag.vectordb` entry point, with built-in names taking precedence (`factory`); the Qdrant reference adapter covering the docker, external, and remote modes, both the 6333 and 6334 paths, `prefer_grpc`, API-key auth, deterministic point-id mapping, filter push-down, and translation of every vendor failure into the typed taxonomy (`qdrant`); system-managed Docker provisioning that converges rather than reinstalls, publishes both ports, uses a named volume, and hands the server key to the container by variable name rather than on the command line (`services.provisioning`); `doctor` preflight diagnostics covering Python, disk, memory, GPU, Docker, secrets, per-port reachability, and backend health, each failure carrying a concrete fix (`services.doctor`); and the shared adapter contract suite run against a real Qdrant in every mode, wired into CI.
- Build slice S1 — skeleton (2026-07-29): the first implementation code. Packaging and tooling (`pyproject.toml` with ruff, `mypy --strict`, pytest and coverage config; `.pre-commit-config.yaml`; `.github/workflows/ci.yml` running the blocking gates; `scripts/check_commit_message.py` enforcing the single-line no-trailer commit rule). Typed error taxonomy (`fasterrag.errors`) with the stable error-code table and its RFC 9457 transport metadata. Structured JSON logging with OpenTelemetry-shaped correlation ids (`fasterrag.observability.logging`). Configuration schema and fail-fast loader (`fasterrag.config`) enforcing every key, bound, and cross-field rule in `docs/config-reference.md`, including the presence of referenced environment variables. API application factory with correlation middleware, problem-document exception handlers, and the `/healthz` and `/readyz` endpoints.

### Fixed

- `cost.estimator: false` now genuinely disables the D9 estimator (2026-08-09). It was declared, documented as the switch for D9, and read by nothing: `fasterrag estimate`, `POST /v1/estimate`, `fasterrag ingest --dry-run`, and `FasterRag.estimate` all priced a corpus regardless. Each now refuses with `VALIDATION_FAILED` naming the setting — a refusal and not an estimate of zero, because a report of no tokens and no cost is indistinguishable from a corpus that is free to ingest. The dry run is gated because it *is* the estimator, so leaving it open would have been the documented way around the switch; `benchmark --suite ingest` is deliberately exempt, since it reuses the same parse-and-chunk work only to time it.
- `autopilot generate-golden-set --size` now defaults to `autopilot.golden_set_size` instead of a second hardcoded 100 (2026-08-09). The two agreeing by coincidence is why a configured value being ignored looked like nothing at all: `golden_set_size: 40` generated a hundred records and nothing said otherwise. An explicit `--size` still wins, and the resolved value is reported in the `--json` document.
- `docs/observability.md` §5 described the Grafana datasource as pointing at fasterRag's metrics endpoint, which is one hop short of workable: Grafana's Prometheus datasource speaks PromQL to a Prometheus *server*, so aimed at a raw exposition endpoint it would never return a series. The provisioner now stands up Prometheus alongside Grafana and the doc says so (2026-08-02).
- The provisioned Grafana datasource had no pinned uid, so Grafana minted a random one per installation while every shipped dashboard panel referenced it by name — the dashboards would have rendered completely empty, with no error anywhere. Caught by reading back the provisioned datasource and finding `P1A267FD5A9BAB99E` where the panels expected `fasterRag` (2026-08-02).
- Autopilot's candidate grid searched `retrieval.top_k`, which cannot affect the measurement: recall@k requires retrieving exactly k, so the harness fixes the retrieval depth and every top_k candidate scored identically by construction. The grid would have burned budget on trials whose ties were structural, and reported them as genuine findings. Found by running the tuner and noticing three candidates that could not possibly differ (2026-08-02).
- Autopilot's grid also generated fusion weights outside the schema's 0.0–1.0 bounds, and one invalid candidate aborted the entire search rather than being skipped — discarding every trial that had already run. Candidates are now generated in range, and an out-of-bounds one is skipped and counted rather than fatal (2026-08-02).
- A malformed baseline raised a bare `TypeError` from `load_baseline` instead of a typed error. Worse, the shape of the failure mattered: a missing baseline blocks the gate, so a baseline that could not be read had to fail loudly rather than risk being treated as absent-or-ignorable. It now raises `VALIDATION_FAILED` telling the operator to re-record it with a measured run rather than edit it by hand (2026-08-02).
- A `config.yaml` saved with a UTF-8 byte-order mark was rejected. The BOM became part of the first key, so a file whose first line reads `app:` failed with "Extra inputs are not permitted" for a key named `﻿app` — invisible in every editor that wrote it. Windows editors and PowerShell add a BOM by default, so this affected the most common way of editing config on Windows. The loader now reads `utf-8-sig` (2026-08-01).
- The API no longer reloads the embedding model on every request. The router was built per request, so a local model paid its full load on each query — measured at roughly 5.2 s added to every call against 45 ms of retrieval. It is now process-scoped like the vector database adapter, and released by the application lifespan rather than by a request handler. Measured on the same repeated query after the fix: 17.5 s cold, then 18 ms (2026-08-01).
- The semantic cache now works over HTTP at all. It too was constructed per request, so every lookup consulted a cache that had just been created empty — it could never hit, while still costing a query embedding per call, which is strictly worse than no cache. Sharing it also required `GenerationService.close()` to stop closing it: a per-query service tearing down a shared backend connection would break other in-flight queries (2026-08-01).
- `fasterrag serve --config other.yaml` served `./config.yaml`. The path was validated and then discarded, because uvicorn was handed an import string whose factory takes no arguments. The application is now built directly with the validated settings, and the reload path — which runs in a child process that cannot receive an object — passes the path through `FASTERRAG_CONFIG` (2026-08-01).
- The degradation ladder no longer absorbs failures that will never recover. A rejected credential, an unknown model name, or a missing provider extra used to serve an `extractive` answer exactly like a provider outage, so a misconfigured deployment answered every query from raw passages forever while reporting nothing more specific than `degraded: true`. Only a **retryable** failure now takes that rung; the rest surface as the typed error they already are. The degradation log also records the provider's own detail and retryability, without which a degraded response left no record anywhere of why it degraded. Found by running `fasterrag query` against a real provider with a key it rejected (2026-07-31).
- A cross-encoder that cannot **load** now degrades to `hybrid_only` like one that cannot score. Only scoring failures were classified, so a model that failed to load — no disk, no memory, no page file, a half-finished download — escaped untyped and failed the whole query, contradicting D4. Found by running `fasterrag query` on a machine whose page file was too small for a 2.2 GB reranker (2026-07-31).
- The HuggingFace embedder reads a model's vector size through whichever accessor the installed sentence-transformers exposes. The name changed in 5.x, and the old one still worked while emitting a deprecation warning, so the adapter now spans both rather than pinning a version. Found by running the adapter against a real model for the first time (2026-07-30).

- Qdrant provisioning now sets `QDRANT__SERVICE__GRPC_PORT`, without which Qdrant leaves its gRPC interface disabled and only port 6333 answers — the provisioner was reproducing the very failure recorded in `docs/failure-modes.md` row 15. Caught by the adapter contract suite running in gRPC mode (2026-07-30).
- Vector-database gRPC failures are now classified by status code, so an authentication rejection over gRPC is reported as non-retryable instead of being retried as a transport blip until the circuit breaker opened (2026-07-30).
- The Qdrant adapter now passes `https` explicitly. The Qdrant client switches to TLS on its own as soon as an API key is supplied, so every authenticated call failed with a TLS handshake error against the plain-HTTP listener a container serves by default. Added `vector_db.https` so the transport is chosen rather than inferred (2026-07-30).
- Provisioning now confirms the backend answers an API call before reporting success. An open TCP port is not readiness: a container binds its listener before it can serve, and a transport misconfiguration connects at the socket level and only fails at the first request — so the failure surfaced in whatever ran next instead of in the provisioner (2026-07-30).
- The default `vector_db.docker.image` moved from `qdrant/qdrant:v1.9.0` to `v1.18.1`. The pinned default predated the features the project depends on: the `/points/query` API needs server 1.10 or newer, as do the sparse vectors and native fusion of ADR-0007, and the client reported the old server as version-incompatible (2026-07-30).

### Security

- Documented secrets policy (`.env`-only, env-var-name references), supply-chain requirements (hash-locked deps, secret scanning, non-root containers, SBOM per release).
- Configuration validation never echoes offending input values, and validation failures are raised without chaining the underlying `ValidationError`, so a credential mistakenly pasted into `config.yaml` cannot reach logs or tracebacks (2026-07-29).
- Interactive API documentation (`/docs`, `/redoc`) is not served: it is a web interface capable of driving the RAG, and the control plane is programmatic only (ADR-0005). The machine-readable `/openapi.json` schema is still published (2026-07-29).
- The Qdrant server API key is exported into the provisioning subprocess environment and passed through with `-e NAME`, so the value never appears in `argv`, a process listing, or a log line. Vector-database authentication failures name the environment variable and are never retried (2026-07-30).
