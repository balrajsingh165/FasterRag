# release.md — Release Procedure for the `fasterrag` Package

The package releases to PyPI under the name **`fasterrag`** (as declared in `pyproject.toml`). This document is the complete, ordered procedure — preconditions, mechanics, publication, post-release, rollback — and the **confidence threshold that authorizes it**. The maintainer executes releases. §3's mechanics run as a workflow, but deliberately not end to end: the irreversible acts, pushing the tag and approving the upload, are a human's, and so were the irreversible decisions before them (license, version).

> **Standing rule for release notes and announcements**: the provable-claims policy applies to them exactly as to docs — no performance or superiority claim without a [benchmarks.md](benchmarks.md) ledger entry. Until the isolated-hardware baseline lands (TASK-0084), announcements describe capabilities and goals, never speed.

## 1. The release gate: confidence threshold

A release is authorized only when **all three** hold:

1. **Release-confidence score ≥ 85/100**, re-derived in [release-readiness.md](release-readiness.md) **within 7 days** of the intended tag, using that document's method (gates re-run, claims probed, docs-vs-code swept). A stale score does not count — a confidence number that is not re-derived is exactly the unbacked claim this repository forbids. *(Current: 62/100 as of 2026-08-10 → not releasable.)*
2. **Zero open items in the release-gating checklist** (release-readiness.md §3.1). Items may close by building **or** by an honest narrowing recorded in the docs and the ledger — "cut the surface" is a legitimate close; "leave it ambiguous" is not.
3. **CI fully green on the exact tag commit** — every job, including integration, models, Windows, and the doc gates.

Threshold by release type: **beta (`0.x.0-betaN`) ≥ 85** as above. **First stable (`1.0.0`) ≥ 90**, additionally requiring the measurement program complete: citable ledger baselines (TASK-0084), SLO targets set from them, chaos recovery times (TASK-0136), and the clean-host DR drill with published RPO/RTO (TASK-0085). The name is "fasterRag"; a stable release with an empty ledger would be the contradiction the whole doctrine exists to prevent.

## 2. Pre-release checklist (the current §3.1 items, resolved in this order)

**Irreversible decisions first** — these can never be amended after the first upload, because **a PyPI version number can never be reused**, even after deletion:

- [x] License ADR (TASK-0164) — **done 2026-09-13**: Apache-2.0, recorded in [ADR-0008](adr/ADR-0008-apache-2-license.md); `LICENSE`, `NOTICE`, and the wheel metadata agree. The uploaded artifact fixes the license grant for that version forever, which is why this was ordered first.
- [x] Identity encoding (TASK-0210) — **done 2026-09-13**: the digest is length-prefixed (netstring form), `IDENTITY_VERSION` is 3, and the property suite proves the version-2 forgery impossible by construction — the property was run against the old digest and failed, then against the new one and passed. Every id changed, which is why it had to happen before the tag: `IDENTITY_VERSION` is frozen by it, and after it, changing ids forces every adopter through a reindex.
- [x] Version number (TASK-0020) — **decided 2026-09-13**: `0.1.0-beta.1` (tag `v0.1.0-beta.1`, PEP 440 `0.1.0b1`). `0.1.0` because the surface is complete enough to use and not stable enough to promise; `-beta.1` rather than `-alpha` because what is shipped is tested, not exploratory; a numbered pre-release so `-beta.2` follows without burning a minor. The **stamp** is step 3 below, not now: a beta label on an unfrozen tree names builds that are not the beta, and a dated CHANGELOG heading for a release that has not happened is a false record. `scripts/stamp_release.py --check` holds the tree to one of the two coherent states until then.

**Then the engineering closes** (build or narrow, each with its task): cost governor (TASK-0242) · D7 gate into CI (TASK-0244) · REST provisioning parity (TASK-0251) · coverage reconciliation (TASK-0252) · LLM breaker consult-or-remove (TASK-0245) · disk-full typing (TASK-0234) · reranker default decision (TASK-0175, B6) · ladder-scope ADR (TASK-0165, ships or formally defers TASK-0159) · the batched maintainer reviews of the adapter surface (TASK-0126/0133/0182/0191 — after the tag they are public API).

## 3. Release mechanics (execute in order; stop on any failure)

Publishing is done by `.github/workflows/release.yml`, and only by it: no credential for PyPI exists anywhere, so there is no manual upload to fall back on. A human still takes the two decisions that cannot be undone — pushing the tag and approving the `pypi` environment — and everything else the workflow does is checked before either of them matters.

1. **Re-derive confidence** per §1. Record the score in release-readiness.md; proceed only at threshold.
2. **Freeze**: no feature commits on `main` between the readiness run and the tag; fixes found during the freeze restart step 1.
3. **Stamp**: `python scripts/stamp_release.py 0.1.0-beta.1` — it writes `__version__` in `src/fasterrag/__init__.py` (hatch reads it), converts CHANGELOG `[Unreleased]` into `## [0.1.0-beta.1] — YYYY-MM-DD` keeping an empty Unreleased above it, and moves the Trove development-status classifier to `4 - Beta`. It then **reports what is left to do by hand**: the three pre-release banners (README's status line, python-api.md's "not yet published" rows, how-to-use.md's substitute-this-command note — TASK-0256), which are prose and are deleted by a human. `--check` is the gate, and it runs in CI on every push: it fails unless the tree is wholly in the development state or wholly in the released one, so a half-finished stamp cannot be committed. Finish with the single-line commit `chore(release): stamp 0.1.0-beta.1`.
4. **Full verification**: [verification.md](verification.md) tiers 0–3 and 6 on the stamped commit; tier 4/5 walkthrough at least once on Linux **and** Windows. CI green on the commit.
5. **Rehearse**: run the `release` workflow by hand on `main` (Actions → release → Run workflow; `dry_run` is ticked by default — leave it). A rehearsal does everything except publish: the version check, the whole `ci.yml` gate set (called as it stands, not copied), `scripts/check_package.py` and `twine check --strict` on the built sdist and wheel, the CycloneDX SBOM, the container image built and checked (uid 10001, `fasterrag` entrypoint, `/readyz` healthcheck, the reported version), and the smoke test of the built wheel in a clean container. Every publishing job shows as *skipped*. Read the `release-notes` artifact: it is the GitHub release body the tag run will use. The local equivalents still work — `python scripts/check_package.py`, `uvx twine check dist/*`, and `fasterrag config init && fasterrag doctor` in the venv it built, read with your own eyes.
6. **Tag**: annotated, single-line message — `git tag -a v0.1.0-beta.1 -m "fasterrag 0.1.0-beta.1"`, then `git push origin v0.1.0-beta.1`. The push starts the release run. Its first job refuses, and nothing after it runs, when the tag is not the tree's `__version__` in SemVer spelling (`v0.1.0-beta.1` against `0.1.0b1`), when `stamp_release.py --check` fails, or when the tagged commit is not on `main`. Any other `v*` tag — a slice tag such as `v0.14.0-s14` included — is refused the same way, as a red run that publishes nothing. The workflow never creates a tag itself (`gh release create --verify-tag`).
7. **Approve the `pypi` environment**: the run stops at `publish-pypi` and waits for a reviewer. Before approving, check that every job above it is green — the gate set is CI green **on the tag** (§1 condition 3). **Approving is the irreversible moment**: the version and its license grant are permanent from here.
8. **The workflow publishes**, in this order, each step only after the one before it succeeded:
   - **PyPI**, through trusted publishing: `id-token: write` in that one job, exchanged by PyPI for an upload token scoped to this repository, this workflow file and the `pypi` environment. No token is stored anywhere. The two files uploaded are the ones built and smoke-tested earlier in the same run, with PEP 740 attestations.
   - **The container image** to `ghcr.io/balrajsingh165/fasterrag`, tagged with the version in both spellings (`0.1.0b1` and `0.1.0-beta.1`) and never `latest`. It pushes the bytes the `image` job built and checked, not a rebuild, then pulls them back and runs `--help`. The published image is the default build, without extras.
   - **The GitHub release**, from the tag: title `fasterrag 0.1.0-beta.1`, marked as a pre-release, body = the CHANGELOG section verbatim (no additional claims), with the sdist, the wheel and the SBOM attached. GitHub accepts at most 125,000 characters in a body; a longer section is cut at a paragraph boundary with a link to the rest, and the complete section is attached as well.
   - **The post-publish smoke test**: `pip install fasterrag==0.1.0b1` from the public index, in a clean container from the `Dockerfile`'s digest-pinned base, retried for up to ten minutes while the upload reaches the index; then the checks the rehearsal ran — version, imports, parsing, chunking, fusion, `config init`, `doctor`. It does not ingest or query: that needs the zero-infrastructure profile (TASK-0444).
9. **If the run fails part-way**: before `publish-pypi`, fix the cause; if the fix changes the tree, the tag must move to a new stamped commit, because a version is never uploaded with bytes other than the ones tested (§4). After `publish-pypi` succeeded, use **Re-run failed jobs** on that same run — it repeats only what failed and what depends on it, so the upload is not attempted twice. Dispatching the workflow on the tag with `dry_run` switched off also publishes; it exists for a tag run that never reached `publish-pypi`. After a successful upload it fails at `publish-pypi`, because PyPI refuses a file it already holds, and skips everything after it.
10. **Post-release verification**: on a machine that has never seen the repo — `pip install "fasterrag[huggingface]"` on Linux and Windows, then quickstart steps 0–6 from [how-to-use.md](how-to-use.md). Any failure here is a `0.1.0-beta.2` driver, filed in todo.md.
11. **Close the loop**: tick TASK-0020/TASK-0087 in todo.md with the date · re-derive release-readiness against the *next* milestone · start the new Unreleased section.

The workflow does not publish to TestPyPI first. The rehearsal in step 5 covers what TestPyPI was for here — the metadata PyPI will render, and an install of the exact files into a clean environment — and a second index would need a second trusted publisher kept in step with the first.

### 3.1 One-time repository settings (the maintainer, before the first tag)

The workflow cannot create any of these, and nothing in this repository can check them.

1. **PyPI trusted publisher.** On pypi.org, *Your account → Publishing → Add a new pending publisher* (the project does not exist yet): PyPI project name `fasterrag`, owner `balrajsingh165`, repository `FasterRag`, workflow name `release.yml`, environment name `pypi`. A pending publisher does not reserve the name; the first successful upload creates the project. Afterwards, check that the project lists exactly this one publisher. Without it, `publish-pypi` fails and nothing is uploaded.
2. **The `pypi` environment.** GitHub, *Settings → Environments → New environment* `pypi`: **Required reviewers** = the maintainer; *Deployment branches and tags* = **Selected branches and tags** with the single tag rule `v*`; no secrets and no variables. Create it before the first tag run: a workflow that names an environment that does not exist gets one created with no protection rules, and the upload would then wait for nobody.
3. **Who can create a release tag.** *Settings → Rules → Rulesets → New tag ruleset* targeting `v*`, restricting creation, update and deletion to the maintainer. Anyone who can push a `v*` tag can start a release run; the environment's reviewer is the second lock and this is the first.
4. **GHCR.** The first push creates the package `ghcr.io/balrajsingh165/fasterrag`, linked to this repository and **private**. After the first release, make it public in the package's settings if it is meant to be pulled anonymously. If a package of that name already exists and is not linked to this repository, grant the repository *Write* under the package's *Manage Actions access*, or the push is refused. The job asks for `packages: write` itself; no token or secret is involved.
5. **Actions allow-list.** If *Settings → Actions → General* limits which actions may run, allow the ones the workflows pin: `actions/checkout`, `actions/setup-python`, `actions/upload-artifact`, `actions/download-artifact`, `astral-sh/setup-uv`, `pypa/gh-action-pypi-publish`.
6. **Dependabot pull requests** (TASK-0496). `.github/dependabot.yml` turns version updates on with no setting. Its commits carry a body and a `Signed-off-by` trailer, which the `commit-messages` job rejects, so its pull requests are merged by squashing under their single-line title — *Settings → General → Pull Requests → Allow squash merging → Default to pull request title* makes that the default.

## 4. Rollback and bad-release handling

A published version is **yanked, never deleted** (`pip` will refuse it for new resolutions but existing pins keep working; deletion breaks pinned users and the number stays burned either way). Procedure: yank on PyPI → fix on `main` (git-revert playbook in [deployment.md](deployment.md)) → release the next patch/beta number → GitHub release note updated to point at it. Never re-upload different bytes under any version, and never rush the fix past §1 — a bad release does not lower the gate.

## 5. Cadence and support

Pre-1.0: only the latest release line receives fixes ([.github/SECURITY.md](https://github.com/balrajsingh165/fasterrag/blob/main/.github/SECURITY.md)). Betas ship when the gate passes, not on a calendar. Every release re-runs this document top to bottom; if a step was wrong or missing, fixing this file is part of the release.
