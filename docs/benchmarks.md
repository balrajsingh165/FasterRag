# benchmarks.md — The Benchmark Ledger

**Doctrine: a claim without a measurement is a bug.** This file is the single source of truth that backs every performance or superiority claim anywhere in fasterRag's documentation, README, release notes, or marketing. If a claim is not linked to a ledger entry here, the claim is a bug — file it in [todo.md](todo.md) and rewrite the claim as a goal.

## Ledger rules

1. Every entry records: **claim · method · dataset · hardware · date · numbers · commit hash · provenance**. All eight fields mandatory; rule 7 defines the eighth.
2. Entries are **append-only** — corrections are new entries superseding old ones (`supersedes: BENCH-XXXX`), never edits.
3. "Fastest"/"faster than X" may only cite an entry that measured **X itself** with the same harness, dataset, and hardware, with the harness committed to this repo.
4. Unmeasured statements in docs must be phrased as goals ("targets sub-second p95 retrieval"), never as facts.
5. Entries are produced by `fasterrag benchmark --ledger` (hardware fingerprint + commit hash auto-captured) and reviewed like code.
6. Docs are periodically grepped for superlatives ("fastest", "best", "most"); each hit must link here or it is filed as a bug.
7. **A number without its tree state is not a measurement.** Every entry added from 2026-11-11 carries a `Provenance:` field holding the four-line header `tests/conftest.py` prints verbatim — checkout path, commit, working-tree state, and the directory `fasterrag` was imported from — or, for a run that is not a pytest run, the same four facts gathered by hand. An entry whose `Provenance:` field is missing, abbreviated, or paraphrased is **incomplete and may not be cited**, exactly as an entry with no `Commit:` may not be.

### Why rule 7 exists, stated as a cost rather than as a rule

TASK-0322 spent an entire session deciding whether a test-count discrepancy between two runs was a real defect or two different trees, and the answer was in neither log because neither log said which tree it measured. The two facts that would have settled it in seconds — the commit, and whether the checkout was dirty — are free to print and impossible to reconstruct afterwards. The instrument that prints them has already earned itself twice since: it caught a worktree measuring a different source tree than the one under review, and it flagged a measurement taken mid-session as non-reproducible before it reached a document.

Three things a `Provenance:` field makes legible that a `Commit:` field alone does not:

- **A dirty tree invalidates the commit.** `Commit: 24ccc56` describes what was pushed, not what ran. The conftest header says `working tree: 7 uncommitted path(s) - A NUMBER MEASURED HERE IS NOT REPRODUCIBLE`, which is the honest label for that number. BENCH-0003 below carries this by hand inside its `Commit:` field, written before the instrument existed; it is the precedent rule 7 generalises, and it is why that entry can still be audited.
- **The import path says which code ran.** An editable install, a stale `site-packages` copy, or a second worktree all produce a plausible number from code the reader will never find at the recorded commit.
- **A missing field is visible; a missing assumption is not.** A reader can see that `Provenance:` is absent. A reader cannot see that the author forgot to check.

The three entries below predate this rule and are not retrofitted — they are append-only, and an entry is a record of what its author verified. All three are already non-citable for other reasons.

The generator does not yet emit this field: `fasterrag benchmark --ledger` captures the hardware fingerprint and commit hash and says nothing about the working tree, so rule 7 is a human step until that changes. That gap is reported, not papered over.

### The nightly comparison is not a source of entries

`.github/workflows/nightly.yml` compares each night's `fasterrag benchmark --json` with the previous night's using `scripts/compare_nightly.py`, and fails when a tracked metric moves more than **125%** in the worse direction ([performance.md](performance.md) §3.7). **This changes nothing about what qualifies for this ledger.** Those runs happen on a shared GitHub runner and fail the same isolation requirement that makes BENCH-0001 and BENCH-0002 non-citable, and a comparison is a change detector rather than a measurement: it reports whether two non-citable numbers moved relative to each other, which is a reason to go and measure, not a measurement.

**What it compares is the ingest suite, and only that** (2026-11-08, TASK-0323). `--suite ingest` is parse-and-chunk; the query suite needs an LLM credential a hosted runner does not hold, and is not run. So the nightly watches chunking throughput for night-over-night movement and watches nothing else — no retrieval, no embedding, no indexing, no generation. A reader looking here for evidence that query latency has not regressed will not find it, and the nightly is not where it will appear. [performance.md](performance.md) §3.7 carries the credential decision this is waiting on.

The job therefore never writes to this file. Appending an entry stays a human act performed against a run on documented, isolated hardware (TASK-0084), and the one mechanism that produces entries is still `fasterrag benchmark --ledger` under rule 5.

**The 125% tolerance is measured, and it measures the runner rather than judging what size of regression matters** (2026-11-11, TASK-0350). The controlled case is the one to remember: **three `workflow_dispatch` runs of the identical commit `882a07e`, inside twenty minutes** — 42973481640, 42973944898, 42974619023 — recorded warmed median p50 of **1.98 ms, 2.87 ms and 1.39 ms**, a 2.07× spread against a tree that did not change by one character. The old 10% gate failed the middle one outright: *"ingest.p50_ms moved from 1.98 to 2.87, 44.9% worse, beyond the 10.0% tolerance"*. Across seven runs of the same workload the figures are 3.05, 2.17, 3.03, 3.07, 1.98, 2.87 and 1.39 ms (runs 42419161973, 42468563494, 42603353729, 42800995556, 42973481640, 42973944898, 42974619023) — mean 2.51 ms, sd 0.67 ms, **CV 26.5%**, worst adverse move **120.9%** — with nothing on the parse-and-chunk path changed between them.

The spread decomposes, and the decomposition is what chose the fix: repetitions inside one run agree to **0.19–2.54%**, while three runs of one commit differ by up to **106.5%** and the full sample by **120.9%**. Enlarging the corpus — the other remedy the ledger named — attacks only the first term, because the dominant one is a multiplicative host-speed difference that a bigger corpus scales rather than cancels. The spread is log-normal with sd **0.3026** on log(p50), and a comparison draws two independent samples, so a two-sided 2σ band spans **3.35×** — a 235% tolerance is what this instrument honestly supports. The gate is set tighter, at **125%**, because 235% fires at nothing; it therefore **detects nothing finer than a 2.25× slowdown** and carries a published residual false-red risk. [performance.md](performance.md) §3.7 carries the full derivation, the three options refused, and the paired-measurement design that would make a tight tolerance possible again.

This is a further reason the nightly cannot feed this ledger, and a sharper one than "a shared runner has neighbours": **an instrument whose readings vary 2× on an unchanged input is not measuring the input.** It is kept as a smoke alarm and is not to be widened again; the answer to another false red is the paired measurement, not a larger number.

## Entry template

```markdown
### BENCH-0001 — <short claim>
- Claim: <exact sentence the docs are allowed to state>
- Method: <suite + flags, warm/cold, repetitions, percentile rules>
- Dataset: <name@version, doc/token counts>
- Hardware: <CPU, RAM, GPU, storage, OS>
- Date: YYYY-MM-DD
- Numbers: <the measurements, all percentiles>
- Commit: <sha>
- Provenance: <the four lines tests/conftest.py prints, verbatim>
    checkout: <path>
    commit: <full sha>
    working tree: clean | N uncommitted path(s) - A NUMBER MEASURED HERE IS NOT REPRODUCIBLE
    fasterrag imported from: <path>
- Supersedes: <BENCH-XXXX | none>
```

A `working tree:` line that is anything but `clean` does not disqualify the entry — it *labels* it. An entry measured on a dirty tree is an indicative datapoint whose claim line must say so, which is a weaker thing than an unlabelled number and a stronger thing than no number.

## Ledger

**No entry below may currently be cited as a claim.** Every one was measured on a developer workstation running an IDE and other co-tenant load, which fails ledger rule 5's isolation requirement (`docs/performance.md` §Methodology: "no co-tenant load; background jobs disabled"). They are recorded because a measurement taken and caveated is worth more than none, and because they establish that the harnesses produce complete entries — not because they license a claim. The SLO targets in [slo.md](slo.md) therefore remain TBD-until-measured, and [performance.md](performance.md) still contains goals only. Superseding entries from isolated reference hardware land with TASK-0084.

BENCH-0003 carries a **second, independent** reason it may not be cited, which isolated hardware would not cure: its quality numbers are smaller than their own standard error on a 16-query golden set, and two of its three comparisons separate the candidate models by nothing at all. An entry can be non-citable because of where it ran *and* because of what it found, and conflating the two would let a bigger machine look like an answer to a question that is actually about dataset size.

### BENCH-0003 — what cross-encoder reranking costs, and what the committed golden sets can say it buys, on non-isolated hardware
- Claim: **Not citable.** Isolation requirement unmet (ledger rule 5), and the quality half is additionally *inconclusive by its own statistics* — see Numbers. Recorded as an indicative datapoint and as input to TASK-0175, which it does not resolve. **No documentation claim may be built on it**, in particular none of the form "reranking improves retrieval quality by X" or "the large reranker is better than the small one".
- Method: `python scripts/measure_rerank.py --repetitions 3 --probe-candidates 100 --json <path>`, plus a second invocation adding `--dataset tests/eval/datasets/policies --chunk-size 128 --repetitions 1`. Three configurations per dataset — `retrieval.rerank: false`, `cross-encoder/ms-marco-MiniLM-L-6-v2`, and the shipped `BAAI/bge-reranker-v2-m3` — scored with the repository's own eval harness (`fasterrag.core.evals.evaluate`: recall@k, MRR, nDCG@k, adversarial records excluded from the averages), at the dataset's committed `k=5`. Quality is deterministic here, and the three repetitions agreed exactly; the repetitions therefore buy latency samples, not quality variance. Quality deltas are **paired per query** against the rerank-off run and reported with the standard error of that per-query difference; a delta is called resolvable only when it exceeds **two** standard errors. Model size counts only the files a sentence-transformers load reads — alternate ONNX/Flax serializations and README screenshots are excluded, and the largest weight file is reported separately. Cold load is a first load from an already-populated hugging-face cache **in a process that has already imported torch and transformers**, and includes one single-pair forward pass; the download is measured separately and excluded. Latency is wall-clock around `CrossEncoderReranker.rerank`, CPU-only (`torch 2.13.0+cpu` — the machine's GPU is present but unused). **Substitution:** the vector database is replaced by an exact in-process brute-force store so the run needs no container; the parser, chunker, embedder, BM25 encoder, RRF fusion, reranker, and `build_retrieval` wiring are the shipped ones. Every configuration is scored against the same store, so the comparison is unaffected, but the absolute numbers are not a reproduction of a Qdrant deployment.
- Dataset: `tests/eval/datasets/handbook` (6 documents → 6 chunks at the shipped 768-token chunk size; 15 golden records, 12 scored, 3 adversarial) and `tests/eval/datasets/policies` (12 documents → 12 chunks at 768 tokens, 24 at 128 tokens; 19 golden records, 16 scored, 3 adversarial). Both golden sets are human-authored with document-level ground truth.
- Hardware: Intel64 Family 6 Model 183 (16 cores), 39.7 GB RAM, NVIDIA GeForce RTX 3050 6 GB Laptop GPU (**present but unused — CPU-only torch build**), 242.8 GB storage, Windows 11, Python 3.14.7 — **with co-tenant load (IDE, concurrent agent sessions editing this same tree)**
- Date: 2026-11-03
- Numbers:
  - **Cost, and the correction it forces.** `BAAI/bge-reranker-v2-m3` occupies **2.14 GB** on disk (2.12 GB of it one `model.safetensors`); `cross-encoder/ms-marco-MiniLM-L-6-v2` occupies **87.56 MB** (86.66 MB of weights). Cold load from a warm cache was **8.3–9.3 s** for the 2.2 GB model and **7.3–7.7 s** for the 90 MB one — so the marginal load cost of the large model is about **1 s**, not minutes. The **357 s** this entry measured for the large model is its *download* (2.14 GB over a domestic connection, once). The "over 400 s to load" recorded in TASK-0174 and quoted by TASK-0175 therefore describes a first run that downloads, not a load: on a populated cache the load is a few seconds. Rerank latency, CPU-only: over the real eval shortlists, **4.15 s** p50 at 6 candidates and **12.88 s** p50 at 12 candidates for the large model, against **0.22 s** and **0.65 s** for the small one. At the shipped `retrieval.rerank_top_n: 100`, the standalone probe gives the large model **55.7 s** p50 (handbook chunks) and **86.9 s** p50 (policies chunks, 768-token), against **2.26 s** and **5.18 s** for the small one — a **17–25× gap**, with the absolute figures dominated by total tokens reranked rather than by candidate count alone (the same 100-candidate probe over 128-token chunks costs 29.8 s and 3.1 s respectively). These are CPU numbers and a GPU would change them by orders of magnitude; nothing here measures one. **The latency figures are order-of-magnitude, not precise**: repeating the 6-candidate small-model measurement afterwards on an otherwise idle machine gave **53.0 ms** p50 against the **220.1 ms** recorded above — the same code, the same data, a 4× swing from co-tenant load alone. The 17–25× ratio between the two models survives that swing comfortably; the absolute milliseconds do not.
  - **Quality, and why it settles nothing.** `handbook` is **saturated**: all three configurations score recall@5 = MRR = nDCG@5 = 1.0000, so the dataset carries no information about reranking at all. On `policies` at the shipped chunk size, rerank-off scores recall 1.0000 / MRR 0.9062 / nDCG 0.9308 and **both** rerankers score **1.0000 / 1.0000 / 1.0000** — identical to each other. The paired gain is **MRR +0.0938 ± 0.0504** and **nDCG +0.0692 ± 0.0372** over 16 queries, i.e. **1.86 standard errors — inside the two-sigma band, so not resolvable.** On the deliberately harder 128-token variant of `policies` (24 chunks) the small model scores MRR 0.9688 / nDCG 1.0000 and the large model **0.9583 / 0.9957**, i.e. the 2.2 GB model is *marginally behind* the 90 MB one; the two gains over rerank-off are +0.0625 ± 0.0427 (1.46σ) and +0.0521 ± 0.0449 (1.16σ), both again inside the band. recall@5 is 1.0000 in every configuration measured, because a 5-result window over a 6-to-24-chunk corpus returns most of it.
  - **What that means, stated as narrowly as the data allows.** Reranking moved MRR and nDCG in the right direction in every non-saturated case, and never moved recall. The move is consistently smaller than the noise of a 16-query golden set, and **no measured difference separates the 2.2 GB default from the 90 MB alternative** — on two of three comparisons they are identical, and on the third the small one is ahead. These corpora cannot distinguish them: a 12-to-24-chunk corpus is not a retrieval problem a cross-encoder is needed for. Pricing the quality side of TASK-0175 needs a golden set one or two orders of magnitude larger over a corpus big enough that recall@5 is not already 1.0 — not a re-run of this harness.
- Commit: 24ccc56350cedecccac4fc7e1f7f83fec4dadaa1 (working tree dirty: concurrent unrelated work on `chroma` settings and baseline fingerprints was present; the paths this measurement reads — `core/evals`, `core/rerank`, `core/retrieval`, `services/querying`, and both datasets' `golden.jsonl` and `corpus/` — were unmodified)
- Supersedes: none

### BENCH-0004 — what reclaiming an idempotency record costs, and what scanning the job journal for one key costs, on non-isolated hardware
- Claim: **Not citable.** Isolation requirement unmet (ledger rule 5) — the run shared the machine with nine concurrent agent sessions building and testing this same tree, and the `worst` figures below show it. Recorded because TASK-0365 and TASK-0358 are *design* decisions that turn on an order of magnitude, not on a precise millisecond, and both separations here are two to four orders of magnitude wide. **No performance claim may be built on it**, in particular none of the form "reclamation is free" or "fasterRag sweeps N records per second".
- Method: `python scripts/measure_idempotency_reclaim.py --records 10000 --expired 2000 --jobs 10000 --samples 200 --journal-samples 10 --json <path>`. Records are written by the shipped `FileIdempotencyStore.write_record`, so each is a real checksum envelope at a real `sha256(key)` path under a real `sha256(tenant)` bucket; the 2,000 expired ones have both their recorded `created_at` and their file `mtime` moved back past `ttl_seconds + RECLAIM_GRACE_SECONDS`, because the pass filters on `mtime` first and backdating only the payload would measure nothing. Two passes are timed: the **first**, which has garbage to remove, and a **steady-state** pass immediately after, which has none — that second figure is what 95 passes in 100 cost in production. Claim latency is wall-clock around the shipped `FileIdempotencyStore.claim` over 200 fresh keys, measured twice: against an idle store, and again with a thread looping `reclaim()` over the same directory, which is the cost the shipped design actually imposes on a concurrent request. Journal lookups are wall-clock around the shipped `Journal.find_by_idempotency_key` after one warm-up call, 10 samples each, for a key that is absent (the full scan, which is what submitting a **new** key does) and for keys spread evenly across the scan order. Jobs are written with `save_job` rather than `create_job`, because `create_job` resolves the key first and populating 10,000 jobs through it is the quadratic cost being measured. Nearest-rank percentiles throughout. No vector database, no model and no network are involved.
- Dataset: synthetic, generated by the harness — 10,000 idempotency records in one tenant bucket (2,000 expired), each a completed `201` with a 57-byte JSON body; 10,000 job records in one journal, each with one source and its own body idempotency key. Written in 10.1 s and 8.8 s respectively.
- Hardware: Intel64 Family 6 Model 183 (16 cores), 39.7 GB RAM, NVIDIA GeForce RTX 3050 6 GB Laptop GPU (present but unused), 242.8 GB storage, Windows 11, Python 3.14.7 — **with heavy co-tenant load (IDE plus nine concurrent agent sessions running pytest and mypy against this tree)**
- Date: 2026-11-11
- Numbers:
  - **A reclamation pass is cheap when it finds nothing and expensive when it finds something, and the gap is 1,700×.** The steady-state pass scanned 8,200 entries, opened none and removed none in **21.76 ms** — about **2.65 µs per entry**, because an entry too young to be expired is rejected on its `mtime` alone and never opened. The first pass scanned 10,200, opened 2,000 and removed 2,000 in **36,619.81 ms** — **18.3 ms per record removed**, and a `cProfile` of the same pass attributes **97%** of it to `_io.open`, not to `unlink` (0.24 ms per file) and not to the checksum (0.05 ms per file). The cost is one *cold* file open per removal: re-reading the same files immediately afterwards costs **0.06 ms** each, 300× less. This is a platform figure, not an algorithmic one — the same machine opens a plainly-written file in a flat directory in 1.08 ms — and a Linux server would be far cheaper. **The design conclusion survives either number**: a pass that removes a day of garbage is seconds here and would still be hundreds of milliseconds at Linux open costs, which is why reclamation runs beside a request rather than inside one, and why the ledger's other candidate — an opportunistic prune of the tenant bucket on every write — was rejected. That design would charge the 21.76 ms floor to *every* keyed request even with nothing to remove, growing with the bucket.
  - **What a concurrent request pays while a pass runs.** Claim latency against an idle store: **p50 0.625 ms, p95 1.629 ms, worst 2.00 ms** over 200 claims. The same 200 claims with a thread looping `reclaim()` over the same directory: **p50 0.692 ms (+0.07 ms, +11%), p95 1.898 ms (+0.27 ms, +17%), worst 16.18 ms (8×)**. The median and p95 costs are small; **the tail is not**, and it is reported rather than averaged away — one claim in 200 waited 16 ms behind the sweep's I/O. Passes are rare (at most one per `in_flight_lease_seconds` per host, 15 minutes by default), so this tail is paid by a handful of requests per pass, but a deployment that lowers the lease to seconds would pay it continuously.
  - **Scanning the job journal for one idempotency key costs 0.6 s at 10,000 jobs** — `find_by_idempotency_key` p50 **633.17 ms**, p95 807.72 ms for an absent key (the full scan, and the case a *new* key takes), and p50 **323.38 ms** for a key present at an average position. That is **~63 µs per job record**, linear in journal size as the implementation implies: an independent 300-job run on the same machine gave 34.9 ms, i.e. 116 µs per record at the smaller size. It is **not microseconds, so TASK-0358 cannot be closed as "too small to matter"** — and it is also not the worst of it: `IngestionService.accept` calls `Journal.create_job` synchronously inside an `async def`, so this scan runs **on the event loop** and stalls every other request on that Uvicorn worker, not only the one that sent the deprecated field. TASK-0358's recommendation is argued from these numbers in `todo.md`; this entry supplies them and decides nothing.
- Commit: 882a07eaf8cb86d0cf206dfd1729bd388ea24186 (working tree dirty: this measurement was taken against the TASK-0365 implementation before it was committed, and nine other agents held unrelated edits in the same tree; the paths it exercises are `services/idempotency.py`, `services/journal.py` and `scripts/measure_idempotency_reclaim.py`)
- Supersedes: none

### BENCH-0005 — what a tenant's rolling spend window costs to hold, to read and to charge, on non-isolated hardware
- Claim: **Not citable.** Isolation requirement unmet (ledger rule 5) — the run shared the machine with nine concurrent agent sessions building and testing this same tree — and rule 7's `working tree:` line is `dirty` for the same reason. Recorded because TASK-0366 is a *design* decision that turns on orders of magnitude, and every separation below is three to four orders wide. **No performance claim may be built on it**, in particular none of the form "fasterRag enforces budgets in microseconds".
- Method: `python scripts/measure_cost_governor.py --charges 10000,100000,1000000 --samples 20 --json <path>`. Both designs are measured **in one process, back to back**, so the comparison is paired against one allocator state and one level of co-tenant load: the shipped bucketed `CostGovernor`, and `ExactWindow`, a transcription of the per-charge `deque[tuple[float, int]]` the module held before TASK-0366. The transcription was validated against the real pre-change class before the change landed — at 10,000 charges both reported **1.17 MiB**, the same figure to two decimals. Charges are spread evenly across one full 24-hour window via the `now` override, never piled on one instant, because piling them would put every charge in one bucket and flatter the bucketed design. Memory is reported by two instruments that can disagree: `tracemalloc` (allocated and still held across the fill, allocator slack included) and a recursive `sys.getsizeof` walk that counts each object once (the structure's own bytes, slack excluded). Reads are wall-clock around the public `spent()` at a moment inside the window, 20 samples, nearest-rank percentiles. **Writes are sampled separately, after tracing stops, against a structure already at that fill** — a build loop would hide the per-charge cost, and the fill itself is timed only under `tracemalloc`, so `seed_s` is not a writer cost and is not quoted here. The expiry walk is one `spent()` at `window + 1` past the last charge, which evicts everything. No vector database, no model, no network, no provider.
- Dataset: synthetic, generated by the harness — 10,000 / 100,000 / 1,000,000 charges of 1–4,096 tokens into one tenant's window, spread evenly over 86,400 s.
- Hardware: Intel64 Family 6 Model 183 (16 cores), 39.7 GB RAM, NVIDIA GeForce RTX 3050 6 GB Laptop GPU (present but unused), 242.8 GB storage, Windows 11, Python 3.14.7 — **with heavy co-tenant load (IDE plus nine concurrent agent sessions running pytest and mypy against this tree)**
- Date: 2026-11-11
- Numbers:

  | charges in window | design | entries held | structure (`getsizeof`) | traced | read p50 | read p95 | write p50 | expiry walk |
  |---|---|---|---|---|---|---|---|---|
  | 10,000 | per charge | 10,020 | 1.17 MiB | 1.20 MiB | 610.9 µs | 2,199.2 µs | 768.5 µs | 5.53 ms |
  | 10,000 | bucketed | 24 | 4,862 B | 4,238 B | 5.2 µs | 22.3 µs | 3.4 µs | 0.020 ms |
  | 100,000 | per charge | 100,020 | 11.69 MiB | 12.04 MiB | 13,356.9 µs | 34,416.3 µs | 10,566.1 µs | 47.51 ms |
  | 100,000 | bucketed | 24 | 4,862 B | 4,238 B | 4.3 µs | 24.8 µs | 3.1 µs | 0.015 ms |
  | 1,000,000 | per charge | 1,000,020 | 116.83 MiB | 120.39 MiB | 128,003.4 µs | 197,082.4 µs | 127,016.2 µs | 398.89 ms |
  | 1,000,000 | bucketed | 24 | 4,862 B | 4,238 B | 7.5 µs | 26.7 µs | 3.6 µs | 0.015 ms |

  - **The ledger's "~1M tuples" was right about the count and silent about the cost, which is the part that decided the design.** A charge costs **122.5 bytes** in the per-charge structure, flat across all three scales (123.13 / 122.56 / 122.50 B), so one tenant at 1M charges a day holds **116.83 MiB** of `(float, int)` tuples — and *per tenant*, because the map is keyed on a client-chosen tenant id. `tracemalloc` agrees within 3% (120.39 MiB), which is the allocator slack the object walk cannot see. The bucketed structure is **4,862 bytes and 24 entries at every scale**, including at 1M: a **25,200×** reduction at the top scale and, more to the point, a figure that stops depending on traffic at all.
  - **Reading the window was the larger finding.** `check()` sums the window on every request, so at 1M charges a budget check costs **128.0 ms p50 / 197.1 ms p95** — on the request path, on the event loop, before the provider is called. Bucketed it is **7.5 µs p50 / 26.7 µs p95**, a **17,000×** separation. Cost per entry is **61 ns at 10k but 128–134 ns at 100k and 1M**; the small case is roughly twice as cheap per entry because 1.17 MiB of tuples fits in cache and 11.7 MiB does not. That is reported rather than smoothed, and it is the only non-linearity in the table.
  - **Charging was quadratic, and nothing in the ledger said so.** The old `record` pruned by calling `_spent_since`, which also **summed the window and discarded the total** — so one charge cost O(entries): **768.5 µs** at 10k, **10.6 ms** at 100k, **127.0 ms** at 1M. Filling a day of traffic through it is therefore quadratic and does not finish: an attempt to seed 1,000,000 charges through the shipped writer was abandoned after running without completing, which is why the harness seeds by appending and prices the writer separately. Bucketed, a charge is **3.1–3.6 µs** at every scale. An embedding batch and a query charge into the same window, so this was paid by ingest too.
  - **Bucketing is not free at every shape, and the worst case was measured rather than assumed.** A bucket costs more than a bare entry when it holds exactly one charge, so a deployment with many tenants each spending a handful of times a day pays slightly more. At 2,000 tenants, amortized bytes per tenant: **1 charge each** 928 B per-charge vs 392 B bucketed (0.42×), **4 charges** 1,192 vs 656 (0.55×), **24 charges spread one per hour** 2,952 vs 3,360 — **1.14×, the only shape where bucketing loses**, and it loses by 14% — and **100 charges** 10,696 vs 3,360 (0.31×). The penalty is bounded at roughly one bucket per hour per tenant and the gain is unbounded; a design whose worst case is 14% and whose best is four orders of magnitude is the trade this entry supports. (This probe is a separate invocation of the same structures, not part of the table above.)
  - **The approximation costs nothing in the counted amount, and that is measured, not argued.** Both designs report the **identical** in-window total at every scale — 18,416,648 / 202,814,800 / 2,047,486,240 tokens — so bucketing changes *when* spend is forgotten and never *how much* is counted. The harness asserts this equality, and a run where the two disagreed would be a bug in the bucketing rather than a trade-off.
